## 5. Coverage focus per unit

These are **added to** gen-testcases' full coverage walk, not a replacement.

**Common to every unit**

- **Real-API behaviour**: the server `userMessage` is shown verbatim for every code the screen can receive (`E-APP-001`…`005`, `E-VAL-001`, `E-AUTH-103`). A `401` mid-session (corrupt the token in the `SESSION` cookie) goes through the shared session handling, with nothing half-saved. Data persists after reload and after re-login. 状態 and carried-over values come from the server and are never recomputed by the client: a row's 状態 reflects the request time, so check it again after a refetch once a start time has passed.
- **Role gate both ways**: the UI gate (disabled + tooltip or 「本部」 badge, or the route `/403`) **and** the server refusal when bypassed. Manager / Staff / Observer `POST`, `PATCH`, `DELETE` or `PUT app-store-urls` → 403 `E-AUTH-103`. Trainer `GET` on list, detail or store URLs → 403 `E-AUTH-103`, with no data rendered.
- **Date-time**: 適用開始日時, 作成日時 and 更新日時 render as `YYYY/MM/DD HH:mm` in JST. Include one time just after midnight JST (the previous day in UTC) to catch a date shift. Granularity is the minute (seconds dropped).
- **UI breakage at 1024×768** (plus one wide check at ≥ 1440px): 備考 of 1000 full-width characters, an unbroken 1000-character ASCII token, 備考 with many line breaks; the widest version value `999999999.999999999.999999999（2147483647）` in all four list columns at once; long 作成者 / 更新者 names (route fake if no such staff exists — pure UI); a 2048-character store URL in its input; a long server message in a toast. Check each place the value renders: list cells (truncation + full text on hover), detail card, delete dialog, confirmation-dialog rows, store URL dialog, tooltips.

**U1 — App version list**

- Columns, order and cell formats (Δ1, Δ2). 状態 badge tone: 適用中 success, 予約 info, 終了 neutral. Carry-over cells muted with the hover text, 「—」 when nothing is in effect (Δ3), checked against the constructed chain (fixtures, §8).
- Filters: ブランド (全ブランド / JOYFIT / FIT365) × 状態 (全状態 / 適用中 / 予約 / 終了) combine with AND; at most one 適用中 per brand. Changing a filter returns to page 1; the title count `N件` equals the filtered total.
- URL state keeps `brandEnum`, `status`, `page` and `limit`. Reload, back from the detail and return from the form all restore it. Hand-edited invalid values (`status=foo`, `limit=7`, `page=999`) are ignored or give the defined error block, never a crash.
- Order: 適用開始日時 descending, no sort controls. Two brands at the same minute are both listed, in a stable order.
- Real paging needs more than 50 settings (fixtures `P*`): 25 / 50 / 100 (default 50), footer `全 N 件 / P ページ / X-Y を表示`, previous / next disabled at the ends, a page past the last after a filter narrows, and `全 0 件` with the footer still visible.
- Empty states: 「アプリバージョンがまだありません」 (no setting at all — fresh local DB or route fake) vs 「条件に一致するアプリバージョンがありません」 + 「条件をクリア」 (a filter is active). Error block 「アプリバージョン一覧の取得に失敗しました」 + server message + 「再試行」; for 400 / 422 the action is 「条件をクリア」; for 403 there is no action (route fake for 5xx / 403).
- Row: a click opens the detail. Menu 編集 / 削除 are enabled only for HQ / System **and** a 予約 row (Δ5). A read-only role sees the 「本部」 badge; an 適用中 / 終了 row shows the status tooltip. For a read-only role on an 適用中 row, both items must be disabled — record which explanation shows; `NG` only if an item is enabled.
- **Delete dialog** (authored in full here): title (Δ6) and body `<BRAND> <YYYY/MM/DD HH:mm> のバージョン情報を削除します。この操作は取り消せません。` (Δ7). キャンセル changes nothing. 削除する → toast 「アプリバージョンを削除しました」, refetch, row gone, count and footer updated (Δ8); a double-click sends one `DELETE`.
- Delete refusals show the server message in an error toast, nothing is removed and the dialog stays: `E-APP-003` (the 予約 row started while the screen was open — fixture `R1`), `E-APP-004` (removing it would leave a later setting with a carried latest below its minimum — `S1` / `S2`), `E-APP-001` (already deleted in another tab). After any refusal, the list shows the server state once refetched.
- 新規登録 is visible for every viewing role. HQ / System → `/app-versions/create`; other roles: disabled with 「本部権限が必要です」.
- **Store URL dialog** (its own section in the TC doc, Δ9):
  - The header button 「ストアの URL の設定」 sits left of 新規登録, for every viewing role.
  - Copy: the title, the lead 「アップデートのボタンから開くストアのページを、アプリごとに設定します。」, the four inputs in order with their labels, placeholder `https://`.
  - Never-saved state (`url: null` everywhere): empty inputs, no 更新 line. Run it **before the first save** on the local DB; afterwards only a route fake can show it.
  - Save as HQ: four valid URLs → one `PUT` carrying all four, trimmed; toast 「ストアの URL を保存しました」; the dialog closes. Reopening shows the values and 「更新: <name> <YYYY/MM/DD HH:mm>」 as the API returns them (don't require every line to change).
  - Client validation per input, in this order: empty or spaces only → 「<label>を入力してください」; 2048 characters OK, 2049 → 「<label>は2048文字以内で入力してください」; not an absolute http(s) URL (`apps.apple.com/app/id1`, `ftp://…`, `javascript:…`) → 「URL の形式で入力してください」. Allowed: any host and any country / locale in the URL (`/jp/` first segment, `hl=` / `gl=` / `l=` query) — neither is checked (PO QA 2026-11-16). Several invalid inputs at once each show their own message, and nothing is sent.
  - Server field errors (`E-VAL-001` `details[].code` → message under the input for `required` / `too_short` / `too_long` / `invalid_format` / other) and errors without details (→ toast) are pre-empted by the client's identical rules. Reach them by route fake and mark those cases so.
  - キャンセル, ✕, Esc or an overlay click after edits → nothing saved; reopening shows the saved values. A load failure shows the retry block with 保存する disabled.
  - Read-only roles: the dialog opens with values and 更新 lines; the four inputs and 保存する are disabled, with 「本部権限が必要です」 (Δ10); `PUT` as Manager → 403 `E-AUTH-103`.

- Edit:
  - Pre-filled with the values entered on that setting; blank slots stay blank (carried values are not copied in). Title 「バージョン編集」, button 「保存する」.

  - A setting that started while the form was open → save refused with an `E-APP-003` toast (`R3`).
  - Two tabs editing the same 予約 setting → last write wins (no lock); record it, don't expect an error.
- Unsaved-changes guard (Δ17): dirty via any field → キャンセル, the back link 「アプリ管理に戻る」 and the sidebar ask first; a clean form leaves at once; no prompt after a successful save.
