# TC -【Fitness CRM】- [Y-13][02][パスワード再設定申請] (Password Reset Request)

> Covers `specs/029-password-reset/` User Story 1 (all), User Story 3 (all), and the multi-tab/
> device Edge Case — the self-service "forgot password" request screen: email entry, format
> validation, the identical-response confirmation state, resend cooldown, and the persistent
> Google-SSO guidance note. Driven by `specs/029-password-reset/tests/test-plan.md`, Unit 1 of 2.
> Unit 2 (Set New Password, `[Y-13][03]`) covers what happens after the emailed link is opened —
> out of scope for this document.

## Source note

- **Spec**: `specs/029-password-reset/spec.md` (read in full).
- **Requirement doc**: `crm/requirements/Y-13.md`, FR-M006 — referenced for cross-check only; not
  used as a copy source.
- **UI mockup** (read in full): `password-reset.tsx`.
- All sources were available — no `Block — needs spec/mockup` cases in this document.
- **Spec/mockup ambiguity flagged, not resolved unilaterally** (TC-016): spec FR-010 calls the
  Google-SSO guidance note "persistent" on the request screen; the reviewed mockup renders it only
  in the pre-submission form state and removes it entirely once the confirmation ("メールを送信し
  ました") state is shown. Written as an open question to verify against the real app, not assumed
  either way.
- **No test environment for the real IDaaS email delivery or token issuance** (per user
  instruction) — every case whose outcome depends on that live round-trip (an email actually being
  sent, a real token being minted) is marked `Block`-eligible in its Notes column; the CRM-side
  form, client-side validation, the identical-response confirmation state, and the resend-cooldown
  timer are written as real, executable cases.

**Data limitations**: The spec/mockup describe no concrete reset-link token format or delivery
mechanism (delegated to IDaaS, per spec Assumptions). Cases that would confirm an actual link was
emailed, or that a second concurrent request issues a genuinely distinct token, cannot be verified
without a real mailbox/IDaaS integration — marked `Block` accordingly.

## Execution record

**Executed**: 2026-08-18 · **By**: Claude (Playwright, black-box) · **Viewport**: 1400×900
(tablet-landscape / desktop — the only supported tier)

**Environment actually used** — the "no test environment for the real IDaaS" caveat in the Source
note is now obsolete for this unit: a live IdP was provided, so every `Block`-eligible submission
case was executed for real.

| Piece            | Value                                                                                |
| ---------------- | ------------------------------------------------------------------------------------ |
| CRM (frontend)   | `http://localhost:3000/password-reset`                                               |
| IdP              | cognito-local at `http://localhost:9230`, pool `local_0vvqe5UN` (Docker container)   |
| Delivery channel | the cognito-local container log prints the confirmation code — used as the "mailbox" |

Observed mechanism (black-box, from the network): submitting the form calls Cognito
`ForgotPassword` directly at POST `localhost:9230` and answers 200 with `CodeDeliveryDetails`; the
CRM's own API (`localhost:3001`) is not involved in this screen. Resend fires the identical call.
Reloading `/password-reset` always returns the initial form state (the confirmation state and its
