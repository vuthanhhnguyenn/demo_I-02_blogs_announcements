# TC -【Fitness CRM】- [Y-13][03][新パスワード設定] (Set New Password)

> Covers `specs/029-password-reset/` User Story 2 (all) and its related Edge Cases — the
> "set new password" screen reached from the emailed reset link: live 3-rule password-policy
> checklist, confirmation matching, submit gating, the invalid/expired-link terminal state, and the
> success state. Driven by `specs/029-password-reset/tests/test-plan.md`, Unit 2 of 2 — the last
> remaining unit across all three auth specs (023, 028, 029).

## Source note

- **Spec**: `specs/029-password-reset/spec.md` (read in full).
- **Requirement doc**: `crm/requirements/Y-13.md`, FR-M002 (password policy, last-3-reuse rule),
  FR-M006 — referenced for cross-check only; not used as a copy source.
- **UI mockup** (read in full): `password-set.tsx` (`variant`: `""`, `"expired"`, plus an internal
  `done` state).
- All sources were available — no `Block — needs spec/mockup` cases in this document.
- **No conflict found between spec and mockup for this screen's password policy**: unlike
  `023-first-time-login`'s screen (which requires a 4th "symbol" rule per its own spec FR-005 that
  its mockup doesn't implement), this screen's spec FR-006 explicitly states only 3 rules (8+ chars,
  upper+lower case, a number) — matching `password-set.tsx`'s `checkRequirements()` exactly. TC-005
  exists specifically to guard against a regression that cross-wires the two screens' differing
  policies.
- **No test environment for the real IDaaS token validation or cross-session invalidation** (per
  user instruction) — cases whose outcome depends on that live mechanism are marked `Block`-eligible
  in their Notes column; the client-side policy/confirmation/gating logic and the token-state
  branching are written as real, executable cases.

**Data limitations**: The spec/mockup describe no concrete reset-token value or expiry duration
(delegated to IDaaS). Each token-state case (valid-unused / expired / already-used / malformed)
needs a way to construct or seed a token in that state against the mock API — confirm the actual URL
param and how to fabricate each state at execution time.

## Common pre-conditions

| ID   | Pre-condition                                                                                                               |
| ---- | --------------------------------------------------------------------------------------------------------------------------- |
| PC-A | A valid, unused, unexpired password-reset link is open, showing the "新しいパスワードを設定" form.                          |
| PC-B | A password-reset link whose token has expired.                                                                              |
| PC-C | A password-reset link whose token was already consumed by a prior, completed password change.                               |
| PC-D | A "set new password" URL with no token parameter, or a malformed/unparseable one.                                           |
| PC-E | Having submitted a fully valid new password + matching confirmation, reaching the "パスワードを設定しました" success state. |
