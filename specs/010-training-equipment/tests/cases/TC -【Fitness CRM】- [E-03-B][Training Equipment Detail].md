**No source was missing** — every case has an oracle. Where the spec and the mockup **contradict**, the case follows the spec and the conflict is named in Notes. The conflicts on this screen are:

1. **設置状態変更 target options** — the mockup's select offers all four statuses including the record's current one; FR-018 requires the **current status not to be offered** as a target. Cases assert the spec.
2. **設置状態変更 status-field validation** — the mockup validates only 変更理由; FR-018 requires **both** dialogs to report every missing input as inline field errors with submit kept enabled. Cases expect an inline error on an unselected status too.
3. **変更履歴 ordering** — the mockup's sample rows are not in date order (2025/10/15 precedes 2025/10/16) and include a 設置中→設置中 row; FR-016 requires `changedAt` **descending** and FR-018 says a same-status change writes **no** row. Cases assert the spec.
4. **変更履歴 footer** — the mockup's footer shows computed stats (「直近1年の対応: 6回」「平均対応間隔: 61日」); the spec defines the footer as a **truncation warning** when the single large page is not enough. Cases assert the spec and record whatever stats footer exists as a finding for the PO.
5. **Exercise-name navigation (FR-020)** — FR-020 says the name MUST link to `/exercises/[id]`, but the spec's "Out of Scope" defers it with Y-08 and "Known non-defects" states the names are not clickable (the candidate catalogue `EX-011…` and the Y-08 master `EX-001…` are separate datasets). The mockup does wire a click. **Per the test plan this is authored as a known-non-defect confirmation, not a functional MUST** — see TC-091/TC-092 and escalate to the PO.
6. **Add-modal description copy** — 「…と一致するエクササイズのみ紐付けできます。」 contradicts the modal also listing mismatched types. Known non-defect 5: copy, not a bug.

**Data limitations (referenced in the affected cases' Notes):**

- **N1 — Two fixtures are needed.** A record **with links** (delete-block, tool-mismatch, unlink) and one **with zero links** (delete-success, empty link state). Re-seed between the two halves — unlink and delete are one-way and consume the fixture.
- **N2 — A freshly created record is needed** for the initial 「新規登録」 history row (FR-016). Create it in unit E-03-C first; it must have no status change yet.
- **N3 — The mock backend owns several outcomes.** Per project rule a wrong **value** from the mock API is `Block`, not `NG`. BE-owned here: `409` on delete-with-links, `422` on a forced mismatch add, server-side candidate filtering, the status-history payload and its ordering, and the status card's derived metadata.
- **N4 — Infinite scroll needs a large candidate catalogue.** FR-011 requires the candidate list to page by infinite scroll; the described pool has only 7 unlinked rows, so a second page is unreachable without extra seed data → `Block`.
- **N5 — Difficulty / body-part options must come from the API.** FR-011 forbids hard-coded label lists. Whether the served options match the mockup's list is verifiable only by comparing against the API response; a divergence is a finding to raise, not an automatic NG.
- **N6 — 変更理由 limits are specified** (free text 1–500) so no default assumption is needed there; other free-text limits fall back to the shared **Default field constraints** and are marked as assumptions.
