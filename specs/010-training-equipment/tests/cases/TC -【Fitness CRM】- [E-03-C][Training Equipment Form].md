# TC -【Fitness CRM】- [E-03-C][Training Equipment Form]

**Unit**: E-03-C Form (per [../test-plan.md](../test-plan.md), unit 3 of 3 — executed **second**, before Detail, per the plan's suggested order)
**Screen**: トレーニング機材 登録／編集フォーム (Training Equipment Create / Edit Form) — one component in two modes, routes `/training-equipment/create` and `/training-equipment/[id]/edit`
**Scope**: both form modes — every field and its validation, the 器具種別変更確認 dialog, the unsaved-changes guard, the post-create 紐づけ設定へ follow-up, role gating and create-time store scope.
**Out of scope** (per the test plan): the list screen (only that Cancel/BackLink returns to it), the detail screen (only that a successful save lands there and that the follow-up action opens its エクササイズ紐づけ tab), the status-change flow (detail-only), exercise linking itself, equipment images and split-quantity.

**No source was missing** — every case has an oracle. Where the spec and the mockup **contradict**, the case follows the spec and the conflict is named in Notes. The conflicts on this screen are:

1. **設置店舗 in edit mode** — the mockup still renders an editable store combobox in edit mode; the spec (FR-008 "editing every field **except** installation store", FR-021, US2 AS4) requires it **read-only with a note that a store move is handled as 「撤去済み＋新規登録」**. Cases assert the spec; an editable store field in edit mode is a defect, not a design choice.
2. **Unsaved-changes guard** — the mockup's キャンセル navigates away immediately; the spec's "Kept deliberately" section requires the 「変更を破棄しますか？」 dialog (a convention shared by 13 form screens). Cases assert the spec.
3. **設置状態 options in create** — the API design document allows only `installed` / `maintenance`; the spec's deviation table keeps **all four** values with 設置中 as default, because the prototype offers all four. Cases assert all four.
4. **設置店舗 submitted value** — the mockup's combobox works on store **names**; the spec requires submitting `store.id` while displaying the store code beside the name. Cases assert the spec's display requirement and note that the submitted id is verifiable only via the resulting list/detail row.

**Data limitations (referenced in the affected cases' Notes):**

- **M1 — Two edit fixtures are needed.** The tool-type decision table needs one record **with ≥1 exercise link** and one **with zero links**. The mockup's form constant says 5 links for the edit sample while its list says 6 for the same record — treat the exact number as "verify at execution" and pick fixtures by _has links / has none_, not by count.
- **M2 — The mock backend owns several outcomes.** Per project rule a wrong **value** returned by the mock API is `Block`, not `NG`. BE-owned here: server-side validation messages, whether `PATCH` really omits `storeId`/`installationStatus`, the link-release side effect of a tool-type change, and the generated 機材ID.
- **M3 — Store identifiers differ across sources.** The store combobox mockup lists demo stores (`YS-001 FIT365八潮店`, `SK-001 FIT365草加店`, …), `stores.ts` has only `S-004 FIT365八潮店`, and the spec describes internal ids `store-001` with `S-001`-style display codes. Verify the real store list at execution; a differing code set is not a defect by itself.
- **M4 — HQ cross-store creation is barely observable.** FR-022 lets HQ create in any store, but per the spec's mock-data caveat the seeded data lives in one store, so "created into another store" can only be confirmed by switching the header scope after saving. `Block` if the store master exposes a single store.
- **M5 — Field limits are mostly unstated.** The spec states no max for 機材名, 型番, 数量 or 備考. Boundary cases use the shared **Default field constraints** (single-line 255, textarea 1000, integer 9 digits) and are marked as assumptions for PO confirmation — an unbounded field with no cap and no error is a **finding**, not a pass.
- **M6 — 設置日 rules are unstated.** Neither source defines whether a future date, or a date before the store's opening, is allowed. Those cases record observed behaviour as open questions instead of asserting a rule.

| BUG-E03C-01     | High     | TC-073, TC-084                 | **FIXED (2026-08-12) — no double-submit guard.** Was: 3 rapid clicks on 「登録」 fired 3 POSTs and created **3 duplicate records**; 「更新」 behaved the same.
