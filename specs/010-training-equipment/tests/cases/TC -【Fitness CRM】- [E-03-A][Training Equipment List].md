**Data limitations (referenced in the affected cases' Notes):**

- **L1 — Pagination is unreachable with the described data.** 10 rows against a default page size of 50 means one page; multi-page navigation, page-number/ellipsis rendering, next/prev-disabled-at-ends and "current page > total pages" all need **≥ 51 rows in scope**. Without extra seed data those cases are `Block`, not `NG`.
- **L2 — Cross-store rows do not exist.** Per the spec's mock-data caveat all seeded equipment lives in one store (`store-001`), so the HQ「全店舗（本部）」view and the single-store view legitimately return the same rows. Cross-store list/CSV differentiation is `Block`.
- **L3 — Store identifiers differ between sources.** The mockup uses `S-004 / FIT365八潮店`; the spec describes `store-001` (internal id) with `S-001`-style display codes. Verify the actual store list/labels at execution rather than treating a different code as a defect.
- **L4 — 器具種別 sort order needs the master's `sortOrder`.** FR-019 orders by `mst_tools.sortOrder`; that master's ordering is not published in the spec beyond the E-03 enumeration order (なし（自重）/ マシン / ケーブル（マシン）/ スミスマシン / バーベル / ダンベル / ケトルベル / ゴムバンド / TRX / その他). Use that order as the expectation and note any divergence for PO confirmation instead of failing outright.
- **L5 — The mock backend owns several outcomes.** Per project rule, a wrong **value** returned by the mock API is `Block`, not `NG`; reserve `NG` for frontend defects. Explicitly BE-owned here: `pagination.totalAllItems`, enum sort ordering, `400`/`403` store-scope rejections, CSV byte content, and the bulk `{ updated, skipped }` result.

### Notable observations (not defects)

- **The plan's open question on Manager/Trainer resolves in the permission matrix's favour**: no sidebar entry, `/403` on direct URL, and zero equipment API requests — the app is stricter than the prototype, matching E-03.
- **All three spec-vs-mockup conflicts resolved in the spec's favour**: placeholder is 「機材名で検索」, no frontend default sort (neutral icons on load, API-owned order), and the pagination footer is hidden when everything fits on one page.
- **Enum ordering is correct** where it matters: 設置状態 sorts 設置中→メンテナンス中→撤去済み→廃棄 and 設置場所 sorts 有酸素→マシン→フリーウェイト — definition order, not label code-point order (FR-019).
- CSV export is solid: UTF-8 BOM, complete 12-column header (including a 店舗 column worth PO confirmation), filters+sort carried in the request, header-only file on zero rows, and scope-dependent filenames (`training_equipment_all_…` vs `training_equipment_S-001_…`).
- Keyword search is case-insensitive, does **not** normalise full-width input, and treats a whitespace-only keyword as "no filter" for matching while still showing it as an active condition in the banner — all recorded as PO open questions, not defects.
- Filter state is URL-bound (`?te_keyword=…&te_status=…`) and survives reload and browser-back.
- **Sorting is a three-state cycle** (ascending → descending → no sort), where the mockup cycles only two. The tooltips follow the real behaviour (「クリックで昇順ソート」/「クリックで降順ソート」/「クリックで解除」) and returning to "no sort" is consistent with FR-019's API-owned default order, so this is recorded rather than failed.
- **Two app-wide items surfaced through this screen.** Buttons compute to `cursor: default` — confirmed to be the design system's intent (no screen overrides it), so the pointer-cursor row was dropped from the shared GUI checklist and TC-008 corrected. The shared pagination footer still prints unseparated totals (「全 1011 件」) while the page badge is separated; that one is only reported, since the footer belongs to a component every list screen uses.
- The bulk flow surfaces the spec's `{updated, skipped}` as two toasts (「N件は設置状態が変わらないためスキップしました」 + 「N件の機材の設置状態を「X」に変更しました」) and writes no history row for skipped records.
