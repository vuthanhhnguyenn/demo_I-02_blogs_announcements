# TC -【Fitness CRM】- [Y-02-01][店舗一覧]

**Unit 1 of 8** — Phase 2 (real API) test cases for the store list screen 店舗一覧 (store list), route `/stores`.

**Scope**: the store list only — page header (title, count badge, 新規登録), search, the 詳細フィルター panel (4 filters), the filter-result banner, the table (6 columns + row menu), sort, pagination, URL state, role scoping, loading/error states, and the long-value layout rows of §6a assigned to unit 1 (LV-02, LV-05, LV-09, LV-14, LV-15, LV-31). Navigation targets (detail, create, edit) are checked only as far as "the right screen opens"; their behaviour belongs to units 2–8.

**Out of scope**:

- **エリア / テリトリー (B1, Phase 2 / Round 3)** — the テリトリー column, the area→territory cascade filter, territory-name keyword matching, row selection, the bulk bar, 選択中のみ表示, the select-all second step and the 「テリトリー変更」 dialog. Store-list FRs **L-FR-005, L-FR-014, L-FR-024 – L-FR-036b** and SC-002 / SC-004 / SC-004a / SC-005 have **no case by design**. The only B1 check written is the L-FR-017b regression: a stale `area_id` / `territory_id` in the URL is ignored and not counted (TC-100).
- **L-FR-039** (change history is read-only) — read in unit 3 (変更履歴 tab).
- Viewports below 1024px.

## Phase 2 execution context

- **Shared backend, no seed reset.** Other testers mutate it. Never hard-code a row count the run did not create; assert internal consistency (badge = footer, banner ≤ badge, pages add up).
- **This unit is read-only.** No case writes to a store, except the XSS case, which temporarily renames the **fixture** FX-BRAND (via the unit 2 form) and restores it. Never edit a store without the `QA-P2-` prefix.
- **Fixtures come from unit 2.** Unit 1 runs first in the suggested order, but the long-value cases need FX-LONG-J / FX-LONG-T. Search `QA-P2-` first; if the fixtures do not exist yet, run the LV cases after unit 2 creates them (or record **Block (fixture pending)** and re-run).
- **Record before the run** (§9): the Staff / Trainer / Observer accounts' linked store, the Manager's managed stores, and the HQ total. Every scope case depends on them.
- **Request evidence.** The app calls the backend host directly; watch `GET /api/v1/admin/stores` query parameters (`keyword`, `brandEnum`, `prefecture`, `fcCompanyId`, `status`, `sort`, `order`, `page`, `limit`, `includeTotalAll`) and `pagination.totalItems` / `totalAllItems`.
- **Harness**: fresh page + 1200–1500 ms wait for search/filter debounce; confirm visibility from a screenshot before flagging a missing label (`innerText` reads sr-only text); give each parallel agent its own login.

### Long-value assertion set (used by every LV case — all at 1024×768)

- **LV-A1** the strategy the screen uses is identified (truncate+ellipsis with the full value on a tooltip / wrap / scroll inside a container);
- **LV-A2** no overlap with neighbouring elements;
- **LV-A3** no button pushed out of view or made unclickable;
- **LV-A4** no page-level horizontal scroll;
- **LV-A5** the full value is readable somewhere (tooltip, wrap, or the detail view).

Each LV row has a **(J)** variant (max length in full-width Japanese) and a **(T)** variant (same length as one unbroken half-width token). (J) OK + (T) NG is a separate finding.
