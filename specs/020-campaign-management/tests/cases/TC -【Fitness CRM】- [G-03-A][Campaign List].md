## TC -【Fitness CRM】- [G-03-A][Campaign List]

**Feature**: 020-campaign-management (PO Spec G-03 — キャンペーン管理)
**Unit**: Unit 1 — Campaign List (`/campaigns`), per `../test-plan.md`
**Scope**: The campaign list screen only — search, filter panel, result banner, the eight-column table (incl. acceptance badge and promo-code marker), pagination, and the row-action menu's edit/duplicate/delete **entry points** (existence, role-gating, first navigation step only). Full edit/duplicate/delete/form behaviour is covered by the Detail and Form units, generated separately, and is **out of scope here**.

**Data limitations** (apply to all affected cases below, referenced by ID rather than repeated in full):

- **SC-005 dataset (≥200 records, both brands, all 3 acceptance states)**: neither `spec.md` nor `campaign-list.tsx` states or shows a concrete count this large. Per the assignment's explicit instruction, this is **not invented** — the dedicated case (TC-073) records Test Data as "verify at execution"; if the running environment has fewer than 200 seeded campaigns, mark that case `Block` with a note, not `NG`.
- **Capacity-reached / capacity-lowered-below-count scenarios**: require specific seeded states (an at-capacity campaign, a campaign whose limit was lowered after applications existed) not shown in the spec/mockup's example data — mark "verify at execution" where noted.
- **Promo-code-marker positive case**: requires ≥1 seeded campaign with an issued promotion code — not itself authored in this unit (that is the Detail/Promotion-Codes unit); assume the seed provides at least one, else mark `Block`.
- **Injection/XSS case (TC-068)**: requires a seeded campaign whose name literally contains markup — this list screen has no create capability of its own (registration is the Form unit), so this case is inherently dependent on either seed data or a freshly-created record from the Form unit; mark "verify at execution."
- **Loading/error states (TC-062/TC-063)**: this is a FE project with a mocked BE; the mock may resolve too quickly to observe a loading skeleton, and may have no built-in way to simulate a server error from the UI alone (would need devtools network throttling/offline toggle). Per the skill's BE-mocked guidance, these are legitimately `Block`-eligible, not `NG`, if unobservable — noted in each case.

**Retracted finding (double-submit on delete).** An initial probe fired `.click()` three times synchronously inside a single JavaScript tick and observed 3 DELETE requests plus misleading `適用中の会員または申請があるため削除できません` / `エラーが発生しました` toasts. **That was a measurement artifact, not a defect** — same-tick programmatic clicks run all three handlers before React can re-render and disable the button, which no pointer or touch input can do. Re-tested with real clicks: the guard works (see TC-046). No bug is raised. Recommend a "double-click the delete confirmation" case be added to the concurrency/abuse group (TC-070/TC-071) to lock this behaviour in — and that it be written to use **real** pointer clicks, not same-tick synthetic ones.
