# TC -【Fitness CRM】- [Y-03-B2][FC企業詳細 管轄店舗・変更履歴] (FC Company Detail — Stores & History)

**Scope**: Unit 3 of [../test-plan.md](../test-plan.md) — the **FC企業詳細** screen, route `/franchise-companies/[id]`, restricted to: the **管轄店舗** tab (helper copy, table, empty state, row navigation), the 店舗を紐づけ dialog, the 紐づけ解除 confirmation dialog, and the **変更履歴** tab's content.

**Out of scope here**: the page header, the 基本情報 tab, the status-summary card's own rendering, the 無効化 / 削除 dialogs and the 集計 tab — all unit 2. This unit _reads_ the summary card's 管轄店舗数 and the header's 削除 enablement as **side effects** of link/unlink (FR-027, FR-030), and it _asserts_ history entries that units 2 and 4 **produce**. 店舗詳細 `/stores/[id]` belongs to **Y-02 店舗管理**, a separate spec: this unit confirms only that a store row navigates to the **correct store's** detail screen and stops there.

**Conflicts / open questions flagged (do not silently resolve at execution time)**

1. **The mockup's link-candidate pool is derived only from this company's own store arrays** (`[...MANAGED_STORES, ...LINKABLE_STORES]` minus the currently linked set). It therefore cannot demonstrate the cardinality rule that a store belonging to **another** operating company must not be offered — a rule the spec states explicitly ("a store belongs to at most one operating company", Key Entities). TC-025 tests that rule against the **spec**, and is `Block` only if no store linked to a different company can be reached from the running data.
2. **The 管轄店舗 tab is deliberately not paginated** (spec Assumptions: "the managed-store list is not independently paginated"; the largest seeded count is 42). TC-014 asserts the absence of pagination as the intended design — do not log `NG` for a missing pager.
3. **"A deactivated company must stop being offered as a link candidate from the store side"** (spec Edge Case) is a **store-side** behaviour owned by Y-02, which the plan places out of scope. TC-038 records only the company-side half (already-linked stores stay listed) and flags the store-side half as out of scope rather than untested-by-omission.
4. **No route is stated for reaching a logically deleted company's change history.** FR-035 requires retention. TC-054 records an open question if the app offers no post-deletion route, rather than an `NG`.
5. **Staff (FC企業管理者職位) scoping is not modelled in V0.** Per the plan: if the mock auth/staff layer cannot express "Staff + FC-admin title + company affiliation", record `Block — needs real API/data`; a Staff user who _is_ admitted but can trigger a link/unlink is a genuine `NG`.

**Data limitations**

- **Only 2 link candidates exist** at the seed state, so the candidate pool exhausts after two links. That makes TC-023 (`紐づけ可能な店舗がありません`) reachable, but it also means the pool must be **re-seeded** before the release/return cases.
- **The cardinality case (TC-025)** needs a store already linked to a _different_ company. If the running data offers none, record `Block — insufficient seed data` with the reason; do not log `NG`.
- **Long store names and markup-bearing store names (TC-013, TC-027, TC-035, TC-053)** must be supplied from the store master (Y-02), which this feature does not edit. If no such store can be produced, record `Block` with that reason.
- **Seed-reset points within this unit** — more than one:
  - Reset/re-seed **before** the unit (units 2 and 4 mutate FC-002).
  - Re-seed **between the link-exhaustion cases (TC-016…TC-028) and the unlink-everything / empty-state cases (TC-029…TC-038)** — both directions are one-way mutations against the same store set, and the candidate pool must be restored.
  - Run the link cases **before** the unlink-everything cases so the candidate pool is exercised while still full.
  - ⚠️ Editing seed files has **no effect on a running dev server** — the mock-db is a `globalThis` singleton and HMR does not reset it. Restart the dev server fully after any seed change.
- **History cases TC-044, TC-048 and TC-049 depend on mutations made in other units** (an attribute edit in unit 4, a status change in unit 2, a registration in unit 4). Either run those units first — the plan's suggested order does — or perform the mutation inside this unit before asserting.
