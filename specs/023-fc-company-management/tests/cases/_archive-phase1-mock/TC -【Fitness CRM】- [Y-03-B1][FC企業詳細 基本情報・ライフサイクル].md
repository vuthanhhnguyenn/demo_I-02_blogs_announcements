# TC -【Fitness CRM】- [Y-03-B1][FC企業詳細 基本情報・ライフサイクル] (FC Company Detail — Info & Lifecycle)

**Scope**: Unit 2 of [../test-plan.md](../test-plan.md) — the **FC企業詳細 (FC Company Detail)** screen, route `/franchise-companies/[id]`, restricted to: the page header (back link, title, status + classification badges, lifecycle action buttons), the **基本情報** tab and its four cards, the status-summary card, the 無効化 / 有効化 dialog, the 削除 dialog including its blocked state, and the **集計** tab's phase gating.

**Out of scope here** (unit 3 owns them): the **管轄店舗** tab, the 店舗紐づけ / 紐づけ解除 dialogs, and the **変更履歴** tab's content. This unit only _triggers_ history-producing mutations (status change, deletion) and _reads_ the managed-store count; the history assertions live in unit 3. The 登録・編集フォーム is unit 4 (referenced only as a navigation target), and 店舗詳細 `/stores/[id]` is Y-02, out of scope for the whole feature.

**Conflicts / open questions flagged (do not silently resolve at execution time)**

1. **認証方式 is absent from the V0 mockup but required by the PO spec.** `Y-03.md` FR-002 (`260730_v2`, 2026-07-30) adds 認証方式（セレクト・必須）with the two values `Google SSO` / `IDaaS`; the reviewed prototype (`426a9b3`, 2026-07-23) predates it. The spec's Assumptions treat the PO spec as authoritative and place the attribute on the detail screen alongside the corporate information. TC-024 asserts its presence — per the plan's execution notes an absent attribute is an **`NG`**, not a `Block`, because it is fully FE-implementable. Only downgrade to `Block` if the attribute renders but its persistence is demonstrably BE-owned.
2. **ロイヤリティ率 phase conflict (display half).** Y-03's 補足 UI設計方針 puts the royalty rate on the Phase 1 form; the mockup phase-gates the _input_. The _display_ on the detail screen is not phase-gated in the mockup, so TC-026…TC-028 apply in the Phase 1 view. If the detail screen hides the royalty rate in Phase 1, that is an `NG` with the conflict cited (FR-042).
3. **Three different labels exist for the same classification value across the three mockup files** — `FC` (list badge, detail badge), `フランチャイズ` (detail seed's `type`), `フランチャイズ（FC）` (form select option). The **badge text is `FC`** in both the list and the detail header; that is what TC-004 asserts. The form-select label is unit 4's concern. Raise the inconsistency as a spec/design clarification, not as a case failure on its own.
4. **Staff (FC企業管理者職位) own-company scoping (FR-037) is not modelled in V0** — the spec's traceability matrix records it as "_Not modelled in V0_". Per the plan: if the mock auth/staff layer cannot express "Staff + FC-admin title + company affiliation", record `Block — needs real API/data`; a Staff user who _is_ admitted but can open **any** company is a genuine `NG`.
5. **No route is stated for reaching a logically deleted company's change history.** FR-035 requires retention; TC-057 records it as an open question if the app offers no post-deletion route, rather than an `NG`.

**Data limitations**

- **The 認証方式 attribute has no seeded value** anywhere in the reviewed mockup — TC-024/TC-025 verify the attribute renders and, when set via unit 4's form, shows the selected value.
- **The unset-attribute cases (TC-021…TC-023, TC-026) need a company registered with every optional attribute left empty** (PC-L). Created via unit 4's form; if the form is not usable, record `Block` with that reason.
- **The classification-vs-legacy-flag contradiction fixture (TC-008) must be manufactured** — no seeded record has 区分 `FC` with 直営店フラグ checked. Create it via unit 4's form (PC-K).
- **The enabled-delete branch needs FC-005** (0 stores). Use the seeded record rather than manufacturing the state by unlinking FC-002's stores — unlinking spends unit 3's link-candidate fixtures and destroys this unit's delete-blocked precondition.
- **Seed-reset points within this unit**: re-seed between the deactivate/reactivate cases (TC-030…TC-038) and the delete cases (TC-047…TC-057) — the delete case consumes the record. Re-seed again before handing off to unit 3. Editing seed files has **no effect on a running dev server** (the mock-db is a `globalThis` singleton); restart it fully after any seed change.
- **The delete-re-enable transition case (TC-053) unlinks FC-002's last store**, which mutates unit 3's fixtures. Run it **last** in this unit and re-seed immediately afterwards.
