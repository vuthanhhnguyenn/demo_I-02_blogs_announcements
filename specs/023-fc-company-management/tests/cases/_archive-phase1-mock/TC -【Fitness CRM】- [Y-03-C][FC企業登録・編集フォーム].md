# TC -【Fitness CRM】- [Y-03-C][FC企業登録・編集フォーム] (FC Company Create/Edit Form)

**Scope**: Unit 4 of [../test-plan.md](../test-plan.md) — the **FC企業登録／編集フォーム**, routes `/franchise-companies/create` and `/franchise-companies/[id]/edit`: all five sections (法人基本情報 / 担当者情報 / 契約情報 / 備考 / ステータス), every field's label, placeholder, default and constraints, required-field validation and its three reporting layers, the 離脱確認 (discard-changes) dialog, and the create-vs-edit mode differences.

**Clustering rationale** (from the plan): create and edit are two routes but **one unit** — the mockup is a single component driven by a `mode` prop, every field / validation / discard behaviour is shared, and the only differences are the title, the pre-filled values and the submit label. This document therefore carries one shared field-and-validation walk plus a dedicated **mode-difference block** (TC-076…TC-090), rather than ~40 duplicated field cases.

**Out of scope here**: the FC企業一覧 (unit 1) and the FC企業詳細 (units 2 and 3), referenced only as navigation targets and as the place created/edited values are confirmed.

**Conflicts / open questions flagged (do not silently resolve at execution time)**

1. **認証方式 is required by the PO spec but absent from the V0 mockup.** `Y-03.md` FR-002 (`260730_v2`, 2026-07-30) adds 認証方式（セレクト・必須）with exactly `Google SSO` / `IDaaS`; the reviewed prototype (`426a9b3`, 2026-07-23) predates it and has no such field. Its cases (TC-029, TC-030, TC-039, TC-082) are authored from the **PO spec**, which the spec's Assumptions treat as authoritative (parity `PAR088`). Per the plan's execution notes an absent field is an **`NG`**, not a mockup mismatch and not a `Block`, because it is fully FE-implementable. Only downgrade to `Block` if the field renders but its persistence is demonstrably BE-owned.
2. **ロイヤリティ率 phase conflict — the PO spec wins.** Y-03's 補足 UI設計方針 states the input is placed on the **Phase 1** form as a reference value; the mockup instead gates it behind `currentPhase === "2"`. The spec's Assumptions resolve this in favour of the PO spec. TC-031 asserts the input is present in the **Phase 1** view; an input missing from Phase 1 is an **`NG` with the conflict cited**, flagged for PO confirmation rather than silently passed.
3. **Cross-field date validation is deliberately deferred.** A 更新日 earlier than the 開始日 is **accepted** in Phase 1 (spec Assumptions). TC-062 is written as an **accepted** case — filing it as an `NG` would contradict the spec.
4. **Three different labels exist for the same classification value across the mockups** — the form's select offers `直営` / `フランチャイズ（FC）`, the detail seed stores `フランチャイズ`, and both list and detail badges render `FC`. TC-028 asserts the form's option labels as the mockup states them and flags the inconsistency; TC-072 then confirms the value round-trips to an `FC` badge. Raise the label mismatch as a spec/design clarification, not as a case failure on its own.
5. **No field limits are stated anywhere** for the text, textarea, number or phone fields. Every boundary case below therefore applies the common checklist's **Default field constraints** (single-line text 255, textarea 1000, integer 9 digits) and is noted `assumed default; confirm with PO/schema owner`. A field that accepts input beyond the default with **no cap and no error** is a **finding**, not a pass.
6. **法人番号 is Japan's 13-digit corporate number** by convention, but neither the spec nor the mockup states a format or length rule (the mockup's placeholder is `例: 1234567890123`). TC-050 records the observed behaviour as an open question rather than asserting a 13-digit rule the spec never set.

**Traceability note — FR-039 has no distinct surface on the form routes.** The plan's traceability map assigns FR-039 ("restricted controls rendered visibly unavailable with a permission explanation") to all four units. On `/create` and `/[id]/edit`, however, access is **all-or-nothing**: every role that may not write is refused the route outright (TC-096…TC-098), so there is no "can reach the screen but not act on it" state in which a disabled-with-explanation control could exist. FR-039's substance is therefore asserted in units 1, 2 and 3, where such controls do exist (the list's 新規登録 and row-menu items, the detail header's lifecycle buttons, the 管轄店舗 tab's link/unlink controls). This is a deliberate, stated gap for this unit — not an omission.

**Data limitations**

- **認証方式 has no seeded value** anywhere, because the field does not exist in the reviewed prototype. Its cases assert the PO spec's contract; see flagged conflict #1 for the `NG`-vs-`Block` rule.
- **The Phase toggle gates ロイヤリティ率 in the mockup.** Run TC-031 in the **Phase 1** view (where the PO spec requires the input) and TC-032 in the Phase 2 view. Switching the phase view is a prerequisite for both.
- **Server-side validation shapes, real duplicate-key handling, two-tab concurrency and 401/403 payloads are BE-owned** and not producible against the Phase 1 in-memory mock-db — those cases (TC-085, TC-089, TC-090) are pre-marked `Block`.
- **Records created by this unit persist into the other units' datasets.** Re-seed before each of the other three units, and restart the dev server fully after any seed change — the mock-db is a `globalThis` singleton and HMR does not reset it.
- This unit **produces the fixtures the other units need**: the contradiction record (区分 `FC` + 直営店フラグ checked) for unit 2's Edge Case, the all-optionals-empty record for unit 2's unset-placeholder cases, the long-string / markup records for unit 1's layout and escaping cases, and the attribute-edit that unit 3's FR-034 before/after diff asserts on. Per the plan's suggested order, run this unit **second** (after unit 1) so those fixtures exist before units 2 and 3.
