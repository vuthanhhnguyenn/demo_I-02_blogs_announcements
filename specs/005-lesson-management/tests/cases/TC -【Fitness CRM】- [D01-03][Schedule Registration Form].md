**Spec-vs-mockup / spec-internal gaps found while authoring — flagged here and again inline in the affected cases' Notes:**

1. **FR-003-021 (existing-reservation change/delete confirmation) has no implementation in this form at all.** `spec.md` User Story 5 / Acceptance Scenario 3 says the confirmation (affected-reservation count, notification summary, refund status, mandatory 変更理由 input) appears "when the user clicks '変更を保存する'" — i.e., this form's own submit button. But FR-003-021's own requirement text says the dialog "applies to edit and delete operations **from the schedule list screen**" (i.e., D01-01), which contradicts the User Story's wording. The reviewed `handleFormSubmit` in the mockup has no such dialog anywhere — it validates then submits directly. This is both a spec self-contradiction and a spec-vs-mockup gap. Since the test-plan's traceability map (§5) assigns FR-003-021 entirely to D01-03, TC-123/TC-124 are written to the spec's intent and marked **Block**, with a recommendation that the PO clarify where this dialog actually belongs (this form vs. D01-01's row actions) and get it implemented.
2. **定員 (capacity) and スタジオ (studio) are marked required (`*`) in the UI but the mockup's own `validate()` function never checks either for required-ness** — only the physical-limit/buffer overage check runs, and only when `capacityInput` is already non-empty. TC-018/TC-085 are written to the UI's own required-asterisk intent (submission should block when empty); if the app allows a blank submission, that is a genuine finding (NG), not a pass, per the "oracle is spec + mockup, not code" rule — the mockup's _visual_ required marker is itself a mockup-source signal, independent of its (buggy) validation code.
3. **毎月 (monthly) repeat pattern has no day-of-month (or any) configuration UI.** FR-003-008 only requires day-of-week toggles for 毎週/隔週; the mockup correctly hides the 曜日 toggle for 毎月, but provides no alternative control, so a user has no way to specify which day(s) of the month a monthly schedule falls on, and the date-generation logic silently reuses whatever `selectedDays` (weekday-based) were last set — invisible to the user in this mode. Neither `spec.md` nor the mockup states what should happen here; flagged as an open question (TC-028) rather than invented.
4. **The 3 buffer-setting Selects (最短受付期間/前バッファ/後バッファ) are wired with only `defaultValue`, no `value`/`onChange`/state.** FR-004-001 requires these to be read **and write**, linked to the instructor's D-04 profile. As built, changing a value in the UI has no observable effect on any state or `markDirty()` call. TC-104 is written to the spec's expected read/write behavior and marked **Block** (cannot verify persistence in the current mock).
5. **定員's "no studio selected" guidance text differs in wording between spec and mockup.** The spec's Edge Cases section states: "スタジオを選択すると物理定員の上限が表示されます"; the mockup's actual rendered string is "スタジオを選択すると物理定員が自動セットされます". Same intent, different exact wording — TC-079 flags this so the tester matches the mockup's literal string rather than failing the case over a paraphrase difference.
6. **Brand-scoping cannot be verified from the current mock data.** `D-01.md`'s constraints section states store/studio/instructor masters are managed per-brand, and this CRM's general permission pattern scopes Manager/Staff/Observer to their own brand's data — but `SCHEDULE_STORE_OPTIONS`, `STUDIOS`, and `INSTRUCTORS` are static flat arrays with no brand field anywhere in the reviewed file. TC-012/TC-129 are marked **Block** pending brand-tagged data or a real API.
7. **ボディケアセラピスト (body-care therapist) instructors can never be selected via this form** — the role filter only maps `インストラクター↔studio` and `トレーナー↔personal`, so the 2 seeded body-care instructors are permanently unreachable here. This is very likely correct/out of scope for D-01 (body-care sessions likely belong to a different module), so it is **not** written as a test case — noted here only as an observation, not a finding.
