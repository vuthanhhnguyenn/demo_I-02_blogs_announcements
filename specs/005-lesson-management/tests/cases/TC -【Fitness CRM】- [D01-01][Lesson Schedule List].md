All three sources were available and readable — no `Block`-for-missing-source cases were needed in this doc.

**Two spec-vs-mockup/requirement-doc gaps found while authoring — flagged here and again inline in the affected cases' Notes, per the oracle-conflict rule:**

1. **"エリア別" (Area) axis tab.** Both the mockup (`type ViewAxis = "store" | "my-schedule" | "area"`, a literal third `TabsTrigger value="area"`) and the raw parent requirement `D-01.md` FR-001 ("ビュー切替タブ:「店舗別」「自分のスケジュール」「エリア別」の3タブ") describe a directly-clickable third tab. `005-lesson-management/spec.md` FR-004 instead states only "two screen axes: store view and my-schedule view" and derives all-store summary purely from FR-018's 3-condition gate (context = all-store AND axis = store AND screen filter = all-store), never describing a separately-selectable "area" tab. This doc tests the control as actually built (3 clickable tabs, "エリア別" forcing summary mode directly) since that is what a tester will encounter, but flags the FR-004 wording gap for the PO/spec-owner to reconcile (see TC-006/TC-007).
2. **Manual Reservation modal (手動予約入力).** Fully implemented in `lesson-schedule.tsx` (`ManualReservationModal`, its own page-header entry button, role gate, and error copy), and it corresponds to the parent `D-01.md` FR-006 (CRM manual reservation input, Mode B) — but `005-lesson-management/spec.md` never mentions it: not in FR-001–FR-046, not in the Traceability Matrix, not in "Out of Scope for Phase 1." It is also absent from this feature's `test-plan.md` §2/§4 coverage focus for D01-01. Since `spec.md` is silent rather than explicitly excluding it, and the component is fully reachable on this same screen, this doc includes baseline coverage (TC-085–TC-096) grounded in the UI mockup + the raw `D-01.md` FR-006 wording (both agree) rather than the normally-authoritative `spec.md`. **Recommend the PO clarify** whether `spec.md` should be amended to add FR-006, or whether this modal belongs under a different unit (e.g. D01-02, which already owns the other reservation-management dialogs).

**A third finding, not a source conflict but a likely defect the spec itself calls for:** FR-037 requires functional sorting for list/area-summary table headers (confirmed by the spec's own clarification: "Should sort controls be functional in Phase 1? -> A: Keep sorting in Phase 1"). The reviewed mockup source renders the sort buttons/tooltips (`ArrowUpDown`, "クリックで降順ソート") with no wired click handler or sort state anywhere in the file. TC-052/TC-053 are written to the spec's required behavior (clicking a header re-sorts the column, descending) — if the current build only shows the decorative affordance, that is a legitimate NG, not a pass, per the "oracle is the spec, not the code" rule.
