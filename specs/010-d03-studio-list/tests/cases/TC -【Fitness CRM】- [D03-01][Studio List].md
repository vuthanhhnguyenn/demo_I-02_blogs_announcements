**Checklist rows added while authoring** (checklist-first rule): two rows in `common-gui-validate-checklist.md` → Table section — (1) a mixed sortable/non-sortable column header must show no sort affordance at all on non-sortable columns, not just "unresponsive to click"; (2) first-click sort direction must be verified against the spec explicitly, not assumed ascending (this codebase has screens that sort descending-first). Both are exercised below (TC-024–TC-030).

**Spec-vs-mockup gaps and notable findings flagged here (and again inline in the affected cases' Notes):**

1. **List-level action buttons — direct contradiction, resolved against the mockup.** `010-d03-studio-list/spec.md` User Story 5 (AS1–AS3) and FR-001-10 directly contradict each other: US5 describes edit/delete buttons rendered **inline in each list row**, while FR-001-10 states action buttons render **only in the detail-view header**, not inline in the list table. The actual `lesson-studio.tsx` `StudioTable` renders **no inline action buttons or icons in any row for any role** — only a row `onClick` that navigates to the detail view. The mockup implements FR-001-10, not US5's row-level buttons. This doc writes cases to the mockup's actual (FR-001-10-aligned) behavior and flags the spec-internal conflict for PO reconciliation — see TC-036–TC-038.
2. **"+ 新規登録" label text differs from spec's literal wording.** `010`'s spec text (US5 AS4-6, FR-001-09) refers to the button as `"+ 新規登録"`, but the mockup renders it as `新規スタジオ登録` (a `Plus` icon component + this exact text, no literal "+" character in the string). Cases use the mockup's actual rendered text as the verbatim UI copy to check against. See TC-002.
3. **利用時間 (Available Hours) column is missing from the table entirely.** The spec's Clarifications section explicitly confirms Available Hours and Brand should both be included as table columns, and FR-001-02 lists 8 required columns (ID, Name, Store, Type, Capacity, Available Hours, Brand, Status). The mockup's `StudioTable` renders only 7 headers — ID, スタジオ名, 店舗名, 区分, 定員, ブランド, ステータス — with **no 利用時間 column at all**, in either the header row or any row cell. Cases are written to the spec (8 columns are the oracle) but this is flagged as a likely gap in the as-built/mockup UI to confirm against the real app — see TC-016.
4. **Default sort order conflict.** The spec's Assumptions section and US4-AS3 both state the default order on first load is Studio ID **ascending**. The mockup applies **no sort logic at all** to `filteredStudios` (it only filters, never sorts) — rows render in the raw `STUDIOS` array order, which is ID **descending** (131, 130, 129, 128, 127, 126, 125, 124). Cases are written to the spec's stated ascending default (oracle) and flag the mockup's actual descending raw order as a discrepancy to confirm against the real app. See TC-023.
5. **Sort interaction is entirely unwired in the mockup, and its static tooltip copy implies the opposite first-click direction from the spec.** No sortable column header has an `onClick` handler, sort state, or comparator in `StudioTable` — clicking does nothing in the static mockup. Every sortable header's static tooltip reads "クリックで降順ソート" (click for **descending** sort), which — if taken as the intended first-click direction — contradicts FR-001-03/US4-AS1's explicit ascending-first behavior. This mirrors a known pattern on the sibling D02-01 list screen (`lesson.tsx`), which does sort descending-first. Cases are written to the spec's stated ascending-first behavior (oracle) and flag this tooltip/spec conflict for confirmation against the real app. See TC-024–TC-028.
6. **Search input has no wired state in the mockup.** The `Input` in the toolbar (`placeholder="スタジオ名で検索..."`) has no `value`/`onChange` bound to any state — typing into it does nothing in the static mockup. FR-001-04/US2 explicitly require functional case-insensitive partial-match search. Cases are written to the spec's required behavior (oracle) and flag that the current design-mockup prototype does not demonstrate it — verify against the real running app, not the static mockup. See TC-039–TC-043.
7. **Only the Type filter is actually wired to the displayed rows; Store/Brand/Status filter state is tracked but never applied.** `filteredStudios` in `StudioTable` is computed as `studios.filter((s) => filterType === "全区分" || s.type === filterType)` — Store, Brand, and Status filter selections update their own `useState` but are never referenced in the filter predicate. FR-001-05/FR-001-06/US3 require all four filters to narrow the table (AND semantics) and to be reset together by Clear. Cases are written to the spec's required behavior (oracle) and flag this gap for verification against the real app — see TC-046, TC-050, TC-053, TC-056.
8. **Store filter is conditionally hidden, not just for a subset of options.** The Store `Select` only renders at all when `currentStoreId === "all"` (i.e., for store-unrestricted accounts). FR-001-05 lists Store as one of "four independent filter controls" without qualifying by role; the mockup instead omits the control entirely for any role whose data scope is already a single/managed store set. This is a reasonable UX simplification (a store-scoped user has nothing to filter by) but is flagged as an assumption to confirm with the PO rather than silently treated as "the same as the other three filters." See TC-047–TC-048.
9. **Brand filter only offers 2 of the 5 enum values, and current seed data is single-brand.** The spec's Assumptions list a 5-value Brand enum (`JOYFIT`, `JOYFIT24`, `JOYFIT YOGA`, `JOYFIT+`, `FIT365`), but the mockup's Brand `Select` only lists `全ブランド`/`JOYFIT`/`FIT365` as options, and every seeded studio's `brand` is `FIT365`. Selecting `JOYFIT` (or any brand other than FIT365, were it offered) is structurally guaranteed to return zero rows against this seed set — this is the "dead filter option" pattern from `common-function-checklist.md`'s Search section. See TC-051.
10. **No pagination UI exists in the mockup at all**, unlike sibling list screens (e.g. D02-01) whose pagination controls are visually present but non-functional. FR-001-01 states the table "MUST" be paginated, but `StudioTable` renders the full `filteredStudios` array with zero pagination markup — no page-count text, no page buttons. Per gen-testcases philosophy #2, this is written from the spec alone (no executable UI detail available) and marked `Block` at execution until the as-built pagination component is located. See TC-062.
11. **Seed data is single-store, single-brand** (`STUDIOS` — all 8 rows: `store: "FIT365八潮店"`, `brand: "FIT365"`). This structurally blocks: Manager-vs-Staff store-scope differentiation, any cross-store data-scope leakage check, and Brand-filter/brand-badge verification for any value other than FIT365. Each affected case notes this individually rather than fabricating multi-store/multi-brand data.
