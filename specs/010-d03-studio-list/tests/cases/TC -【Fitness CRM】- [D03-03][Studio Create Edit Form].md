A large share of cases are still marked `Block`/finding because the **mockup itself does not implement** several spec-required behaviors (dynamic grid resize, reset, per-record form pre-fill) — noted individually and summarized below.

**Checklist rows added while authoring** (checklist-first rule): a new **"Multi-Cell Grid / Layout Editor (paint-by-click canvas with dynamic resize)"** section in `common-function-checklist.md`, inserted after "Sortable Multi-Image Gallery" — no existing section covered a paint-by-click canvas with mode-select, dynamic grid resize (preserve/discard), reset, and cross-screen legend consistency. Exercised below in the Space Layout Editor cases (TC-061–TC-079). The existing "Dialog / Confirmation Message" row ("reflects the value the user actually typed/selected, not a generic placeholder") and the Text/Numeric "default value — Create: blank" rows already cover two of this doc's key findings without needing new rows — cited directly.

**Spec-vs-mockup gaps and notable findings flagged here (and again inline in the affected cases' Notes):**

1. **スタジオ区分 (Studio Type) enum mismatch — resolved against the mockup and the parent requirement doc.** `012-studio-create-edit/spec.md`'s FR-002-02 states the options are "ノーマル, ホットヨガ, バーチャル", but the parent `D-03.md` (FR-002, line ~147: "スタジオレッスン用 / PT用 / ボディケア用 等") and the actual mockup `Select` both use `スタジオレッスン用` / `PT用` / `ボディケア用` — the same three values already confirmed on the D03-01 sibling doc's `TypeBadge`. `spec.md`'s own FR-002-02 text is internally inconsistent with the very D-03.md source it cites. Cases are written to the mockup/D-03.md's actual values (the executable UI detail a tester needs) and this conflict is flagged for PO reconciliation rather than silently written to spec.md's incorrect enum, which would produce guaranteed false NGs. See TC-010–TC-011.
2. **The create-mode form is not blank.** `StudioFormView`'s field state (`storeName`, `studioName`, `physicalCapacity`, `bufferValue`, the 3 static image previews) is hardcoded via `useState` initial values with no branching on the `mode` prop — so `mode="create"` renders the exact same pre-filled sample data ("Zumbaスタジオ", "FIT365八潮店", "16", "0", 3 stock photos) as edit mode, instead of a blank form. This directly contradicts User Story 1 AS1 ("a blank studio creation form is displayed") and the common-gui-validate-checklist's Text Box / Numeric Edit Text "default value — Create: blank" convention. See TC-007, TC-009, TC-016, TC-020.
3. **Edit-mode pre-fill accuracy is unverifiable in the current mockup.** Because of #2, there is no `studioId`-driven data fetch distinguishing which studio is being edited — the form always shows the same hardcoded values regardless of which row's "編集" link was clicked. FR-004-01's "pre-populates with the current studio's values" cannot be exercised against two different studios in this static mockup. See TC-056.
4. **利用可能時間 (Operating Hours) required-marking ambiguity** (already flagged by the test plan). FR-002-02 states it is "required per spec" but "not explicitly marked required in UI." Confirmed: the mockup's label has no `*` asterisk and `validateForm()` has no entry for this field at all — leaving a required field with zero validation is a genuine gap, not just a marking nuance. See TC-012.
5. **利用可能時間 inputs are fully uncontrolled** (`defaultValue` only, no `value`/`onChange`) — changing the start/end time in the UI is never reflected anywhere, including the confirmation dialog, which always renders the literal hardcoded string `"06:00〜23:00"` regardless of what the user entered. This violates the existing common-gui-validate-checklist "Dialog/Confirmation Message" row (dialog must reflect the live typed/selected value). See TC-014, TC-047.
6. **Confirmation dialog renders an extra field beyond FR-002-05's stated list.** FR-002-05 specifies exactly 6 summarized fields: スタジオ名, 所属店舗, スタジオ区分, 定員, 利用可能時間, ステータス. The mockup's dialog renders **7** rows — the same 6 concepts plus a separate バッファ値 row — and labels the capacity row "物理定員", not "定員". See TC-045.
7. **スタジオ区分's required-check is dead code.** The `Select` has no blank/placeholder option (unlike 店舗名's "選択してください"), so `studioType` can never actually become falsy through normal UI interaction — the `if (!studioType) newErrors.studioType = ...` branch in `validateForm()` is unreachable via the UI. See TC-028.
8. **The spec's max-500 cap on 物理定員/バッファ値 is not enforced anywhere in the mockup** — no `max` attribute on either `Input`, and `validateForm()` performs no numeric bound check. Entering 501 in either field is silently accepted with no error. This is a finding per gen-testcases philosophy #4 ("if the field accepts unbounded input with no error, that is a finding, not a pass"). See TC-035, TC-038.
9. **Grid dimension selects (列数/行数) are fully non-functional.** Both `Select` components are rendered with a literal `value="8"` / `value="2"` and **no `onValueChange` handler** — selecting a different column/row count does nothing. FR-006-03's dynamic resize (grow preserves in-bounds cells, shrink discards out-of-bounds cells) cannot be exercised at all in the current mockup. See TC-070–TC-073, TC-077.
10. **"リセット" (Reset) link button has no `onClick` handler at all** — clicking it does nothing; the grid never returns to its default state via this control in the mockup. See TC-074.
11. **Cell-paint is gated behind an undocumented two-step confirm flow, contradicting spec.md's own Assumptions section.** Clicking a cell opens an `AlertDialog` ("スペースレイアウトを変更しますか？") that must be confirmed via "変更する" before the cell actually changes type — plus an extra destructive warning banner when the clicked cell is in a hardcoded `RESERVED_CELLS` set (`"0-4"`, `"1-1"`, both currently `available`-type cells with a same-store existing reservation). FR-006-02 ("cell click paints the selected type") implies an immediate single-step change, and `012-studio-create-edit/spec.md`'s own Assumptions section states this exact confirmation dialog "will be implemented in a later Phase" — yet the mockup already implements it now. The parent `D-03.md` (制限事項 / FR-006 異常系) does require such a dialog unconditionally, so this is a 3-way inconsistency (spec.md's FR text vs. spec.md's own Assumptions vs. D-03.md/mockup). Cases are written to the mockup's actual already-implemented two-step behavior; flagged for PO reconciliation. See TC-064–TC-069.
12. **Image-upload affordance is inert** — the "画像を追加" button has no `onClick`/file-input wiring, and the 3 preview thumbnails are static stock images unrelated to any upload state. Consistent with the test-plan's "visual affordance only, per Phase 1" instruction — noted so `execute-testcases` treats it as `Block`, not `NG`. See TC-021.
13. **User Story 2 AS3's pricing/restriction warning has no corresponding fields on this form at all.** FR-002-02's field list contains no pricing or restriction fields, so the condition that should trigger `"料金や制限条件を変更すると、予約済みの会員にも影響する場合があります。"` cannot be constructed. Written as an explicit open question for PO clarification, not fabricated. See TC-083.
14. **Space-layout storage mechanism (D-Q10) is explicitly undetermined** per both specs — not testable at the UI level; informational only. See TC-084.
15. **Seed/store data is limited to 2 stores** (`選択してください` placeholder aside: `FIT365八潮店`, `旭川アモール`) — Manager/Staff store-scope narrowing on the 店舗名 select (should list only the account's managed/assigned store(s)) cannot be fully confirmed against this option set. See TC-060.

**Data limitations**: only 2 real stores exist in the 店舗名 options (plus the placeholder); no seed data distinguishes Manager-vs-Staff store scope beyond this. The form itself has no per-`studioId` data source (Finding #2/#3), so edit-mode pre-fill accuracy against a specific record (e.g. studio 126 / スタジオB vs. studio 131 / Zumbaスタジオ, per the D03-01 sibling doc's `STUDIOS` reference) cannot be exercised.

### Confirmed bugs (real app, not mockup artifacts) — fix status

- **BUG-D0303-01 (Medium) — Fixed.** スタジオ名's real max length is **100** characters (an intentional limit; spec is silent, so the 100-char cap itself is not a bug). Exceeding it previously showed a raw **untranslated English** Zod error: `"Too big: expected string to have <=100 characters"`. **Fix**: both the client (`studio-form.schema.ts`) and server (`_schemas/studio.schema.ts`) `.max(100, …)` now carry the message `"スタジオ名は100文字以内で入力してください。"`. Re-verified live: a 101-char name is blocked with this exact Japanese message, no English text anywhere on the page. See TC-040, TC-041.
- **BUG-D0303-02 (High) — Fixed.** バッファ値's required-validation was missing entirely because `z.coerce.number()` silently coerced a cleared `''` input to `0`, a value that legally satisfies `min(0)`. **Fix**: the field now runs through `z.preprocess()` that turns `''`/`null`/`undefined` into `undefined` before coercion, so a cleared field fails the required check instead of coercing to a valid `0`. Re-verified live: clearing バッファ値 and submitting shows "バッファ値は必須です。" and blocks the dialog. See TC-029.
- **BUG-D0303-04 (High) — Fixed.** Confirming either Create (`この内容で登録する`) or Edit-save (`この内容で保存する`) navigated to `/studios` (the Studio List) instead of the affected studio's detail page. **Fix**: `createMutation.onSuccess` now reads the new `id` from the mutation response and `updateMutation.onSuccess` uses the known `studioId`; both `router.push(navigate('/studios/[id]', id))`. Re-verified live: both create and edit (STU-101) confirms land on `/studios/{id}`. See TC-049, TC-050.
- **BUG-D0303-05 (High) — Fixed.** A real Create submission was assigned ID `STU-108`, colliding with an existing studio — root cause: the mock DB's `create()` computed the next numeric ID only from `_detailStore` keys (which only had 4 of the 12 seeded studios), ignoring `SEED_STUDIO_LIST`/`_rows` where the higher IDs actually lived. **Fix**: `lesson.table.ts`'s `create()` now computes the max across `_detailStore`, `SEED_STUDIO_LIST`, and `_rows` combined. Re-verified live with two independent submissions (one per dev-server reseed): each got a fresh unique ID (`STU-108`, then `STU-113`), the studios list showed each exactly once, and zero console errors (no more React duplicate-key warning). See TC-049.
- **BUG-D0303-06 (Medium) — Fixed.** 物理定員 and バッファ値 were both missing their helper/explanatory text. **Fix**: added the D-03.md-specified helper `<p>` text ("消防法・安全面に基づく…" / "物理定員を超えて…") under each field in `studio-form-basic-info.tsx`. Re-verified live on `/studios/create`. See TC-014, TC-016.
- **BUG-D0303-07 (High) — Fixed.** The confirmation dialog rendered 7 rows instead of spec's 6, adding an extra バッファ値 row and labeling capacity "物理定員" instead of "定員". **Fix**: removed the バッファ値 row and relabeled the capacity row "定員" in `studio-form-confirm-dialog.tsx`. Re-verified live: dialog now shows exactly the 6 FR-002-05 rows. See TC-044.
- **BUG-D0303-08 (Low) — Half-fixed, half not-a-bug.** Two wording mismatches were flagged: (a) create-mode header reads "新規スタジオ登録" vs. doc-assumed "スタジオ登録", and (b) 店舗名's required-error read "店舗は必須です。" vs. doc-expected "店舗名は必須です。". **Investigation**: `012-studio-create-edit/spec.md` FR-002-01 explicitly names the entry-point button/action "新規スタジオ登録", and nowhere specifies a literal page-title string — so (a) is a wrong assumption in this doc (the mockup's filename was the source, not a spec citation), not an app bug; **left unchanged, TC-001 not updated**. (b) is a real bug against FR-002-04's literal format rule ("`{項目名}は必須です。`") since the field's own label is "店舗名" — **fixed** in both client and server schemas. Re-verified live: TC-024 now shows "店舗名は必須です。". See TC-001 (unchanged), TC-024 (fixed).
- **BUG-D0303-09 (Medium) — Fixed.** The confirmation dialog's title text was inconsistent between modes (create: "以下の内容で登録します。よろしいですか？"; edit: "この内容で変更を保存しますか？"). **Fix**: aligned edit's title to "以下の内容で更新します。よろしいですか？" in `studio-form-confirm-dialog.tsx`'s `MODE_LABELS`. Re-verified live on STU-101 edit. See TC-047.
- **BUG-D0303-10 (High) — Fixed.** In an edit session, リセット reset the Space Layout Editor to a generic blank 8×2 grid instead of the studio's actual originally-loaded layout — a data-loss risk. **Fix**: `space-layout-editor.tsx` now captures the initial `{rows, columns, cells}` in a `useRef` on mount and リセット restores that captured value instead of the hardcoded blank default. Re-verified live on STU-101: painting 3 cells then リセット restored the exact original summary counts (24/14/2). See TC-072.
- **BUG-D0303-12 (Medium) — Fixed.** スタジオ名 accepted a whitespace-only value (" ") without triggering the required-field error (no `.trim()` before the length check). **Fix**: `name: z.string().trim().min(1, …).max(100, …)` in `studio-form.schema.ts`. Re-verified live: " " now correctly shows "スタジオ名は必須です。". See TC-026.
- **Edit pre-fill parsing gap (High) — Fixed.** The 利用可能時間 start-time `<input type="time">` failed to pre-fill when the seed's `usage_hours` had a single-digit hour (e.g. `"9:00-22:00"`) — native time inputs reject non-zero-padded values, leaving the field blank and blocking Save until manually retyped. Re-verified live on `/studios/create`: label now renders "利用可能時間\*". See TC-011.
