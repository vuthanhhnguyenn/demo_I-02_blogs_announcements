**Spec-vs-mockup gaps and notable findings flagged here (and again inline in the affected cases' Notes):**

1. **The Space Layout Preview Card is never absent — it is always rendered.** The mockup's own code comment states this explicitly ("未設定時も空状態でCardを常設表示" — even when unset, the Card is permanently shown in an empty state): only the _inner content_ switches between the actual grid and an `Empty` placeholder. This contradicts the spec's Edge Cases text ("Studio has no layout data: layout preview card is not displayed"), which implies the whole Card should be absent. Cases are written to the mockup's actual always-visible-Card behavior; the conflict is flagged for PO reconciliation. See TC-017.
2. **登録日 (created date) and 更新日 (updated date) are hardcoded literal strings, not derived from the studio record at all.** Every studio — regardless of which row was opened — shows the same "2025/02/10" / "2026/03/01" pair (`StudioItem` doesn't even have created/updated fields). The Status card's own "更新日:" line repeats the same hardcoded string a second time. See TC-007.
3. **The Change History tab's content is fully static, independent of which studio is selected.** `historyEntries` is a hardcoded array inside `StudioDetailView`, not keyed by `studio.id`. Opening any other studio (e.g. スタジオC, id 124) still shows the same 4 entries literally naming "Zumbaスタジオ" — including a creation note "Zumbaスタジオを新規登録" and a 物理定員 diff "12名→16名" that only numerically happens to match studio 131's actual capacity. See TC-066.
4. **An invalid or missing `studioId` URL query param silently falls back to `STUDIOS[0]` (id 131, Zumbaスタジオ)** instead of showing a not-found/error state. This is a concrete, observable instance of the spec's own flagged gap (below) — a stale bookmark or a typo'd id shows a _different, real_ studio's full detail with no indication anything is wrong. See TC-068, TC-069.
5. **Zero-linked-lessons UI state is already resolved in the mockup, contrary to the spec's own tag.** The spec's Edge Cases section marks this `[NEED CLARIFICATION]` ("Expected UI state is not defined... empty card vs message vs hidden"), but the mockup already renders a concrete `Empty` ("紐付きレッスンはありません" / "未利用のスタジオは削除できます"). Treated as resolved via the mockup; the spec's own tag appears stale. See TC-034.
6. **Spec Q&A #1's "permission enforcement mismatch" also appears stale/resolved.** The spec's own Q&A section states "the detail header currently renders Edit and Delete actions without role-based conditions in the UI code," but the mockup we read wires both buttons through `RoleGatedButton` with `allowedRoles` that match D-03.md's authority matrix exactly (Edit: System/Headquarter/Manager/Staff; Delete: System/Headquarter/Manager). Cases are written to this already-correct gating behavior. See TC-036–TC-041.
7. **Role gating checks role only, not the store-scope qualifier D-03.md's matrix states for Manager (○ 管轄店舗) and Staff (○ 所属店舗).** Nothing in `RoleGatedButton`'s `allowedRoles` check narrows by store — a Manager could edit/delete a studio outside their managed store via direct URL. Untestable with current sample data: all 8 seeded studios share the single store "FIT365八潮店." Flagged as an open question, not a confirmed bug. See TC-042.
8. **No data-scope check gates read access to the detail page at all** — any authenticated role can view any studio's full detail via direct URL regardless of store/brand assignment; only the Edit/Delete _action buttons_ are gated, not the page's read view. The common-gui-validate-checklist's "View Detail" row expects out-of-scope direct-URL access to be blocked (typically 404); the mockup implements no such check. Same single-store data limitation as #7 prevents a concrete before/after demonstration. See TC-043.
9. **The reservation-rate color scheme has an undocumented third tier.** Spec FR-003-05 only defines ≥80% (success) and ≥60% (warning). The mockup additionally renders a neutral/muted style for rate < 60%, which the spec never mentions — and no seeded lesson rate is actually below 60% (`131`'s lowest is 65%; the shared default set's lowest is 66%), so this third tier is entirely unreachable with current sample data. See TC-029.
10. **Exact boundary reservation rates (59%/60%/79%/80%/100%) called out by the test plan's coverage focus do not exist in the current sample data.** Closest available values are 65, 66, 72, 74, 78, 81, 85, 88, 92. Boundary cases are written per the plan's instruction but marked as needing a crafted test fixture at execution. See TC-030–TC-032.
11. **No sample studio combines "in-use" with "already inactive."** The "代わりに無効化する" (deactivate-instead) alternative button in the delete dialog only renders when `assignedLessonCount > 0 && isActive`; both zero-linked-lesson studios (127, 124) are already inactive, and every in-use studio (131 and the 5 studios sharing `DEFAULT_ASSIGNED_LESSONS`) is active. The button's correct _absence_ in an in-use-but-inactive combination can't be demonstrated with current data. See TC-053.
12. **No sample studio has both 設備・備品 and 備考 empty simultaneously** — each optional block is individually exercisable (hidden) but the "both hidden at once" combination isn't directly available. Noted in TC-009/TC-011's Notes rather than a separate case.
13. **Tab state is not synced to the URL.** `<Tabs defaultValue={activeTab}>` is uncontrolled — no `onValueChange` wired to a query param — so a reload always returns to 基本情報 regardless of which tab was last active, even though the component accepts an `activeTab` prop. See TC-058.
14. **Status-card active/inactive toggle and the FR-007 KPI utilization panel are present in the prototype but out of scope for this unit** per test-plan §1 (toggle belongs to FR-005; KPI belongs to FR-007, a Should/future-phase item). Neither is exercised functionally in this doc; only their visual presence is incidentally observed while testing the Status card (TC-023/TC-024).
15. **No explicit "layout configured / not configured" status label exists**, distinct from which content variant renders. Presence is only ever implied by grid-vs-Empty, matching the spec's own Q&A #3 open question. See TC-073.
