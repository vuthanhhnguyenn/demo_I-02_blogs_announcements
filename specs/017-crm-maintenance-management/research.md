# Research: Y-10 CRM Maintenance Management

**Input**: [spec.md](spec.md) — zero `[NEEDS CLARIFICATION]` tokens remain (checklists/requirements.md all pass). This document resolves the implementation-level unknowns needed before Phase 1 design, reconciling the three UI mockups against the sibling `016-app-maintenance-mgmt` (Y-06) precedent and the reference backend API design (`backend-api.md`, repo root).

## 1. Mock-DB feature closest in shape: `app-maintenances` (016-app-maintenance-mgmt), not `banners`

**Decision**: Model the `crm-maintenances` table, schema, and routes directly on `app-maintenances` (`src/app/api/_mock-db/{types,tables,seeds}/app-maintenance.*`, `src/app/api/_schemas/app-maintenance.schema.ts`, `src/app/api/crm/app-maintenances/{route.ts,[id]/route.ts}`), including its **real** authorization pattern (`getAuthUserFromRequest` + explicit role checks) rather than `banners`' hardcoded `const MOCK_ROLE` shortcut.

**Rationale**: `app-maintenances` is the closest possible sibling — literally the mobile-app counterpart of this exact feature (a start/end datetime range, a status computed on read from `now()` vs. the range and never stored, an in-progress start-date lock, an in-progress delete lock, System-only writes with Headquarter read-only). Y-10's FR-012/FR-014/FR-016/FR-019/FR-020 are FR-for-FR the same rule shape as Y-06's FR-010/FR-011/FR-014, and `backend-api.md`'s authorization section for Y-10 ("system or headquarter" reads, "system role only" writes) is a real, deliberately-designed security boundary — exactly the reasoning `016-app-maintenance-mgmt`'s research.md §4 used to justify skipping `banners`' shortcut.

**Alternatives considered**: `banners` (rejected — hardcoded mock role, no derived-status range concept beyond `computeStatus`, no in-progress lock precedent). `staffs`/`instructors` (rejected — no range+derived-status shape at all; useful only as the _joined_ master for allowed users, see §3).

## 2. Field naming: snake_case row / camelCase request-response, matched to `backend-api.md` where possible

**Decision**: The seed/row schema (`CrmMaintenanceSchema`) uses snake_case (`title`, `starts_at`, `ends_at`, `message`, `note`, `created_by`, `updated_by`, `created_at`, `updated_at`); request bodies (`CreateCrmMaintenanceBodySchema`, `UpdateCrmMaintenanceBodySchema`) and response schemas (`CrmMaintenanceItemResponseSchema`, `CrmMaintenanceDetailResponseSchema`) use camelCase (`title`, `startsAt`, `endsAt`, `message`, `note`, `allowedUserIds` on write / `allowedUsers` on read, `createdBy`, `updatedBy`, `createdAt`, `updatedAt`, `status`, `allowedUserCount` on the list item only) — each response field re-using `CrmMaintenanceSchema.shape.<snake_case_field>`, the exact pattern in `app-maintenance.schema.ts`.

**Rationale**: This is the established split across every existing `_schemas/*.schema.ts` file. On top of that, `backend-api.md` (the real backend's reference API design for Y-10) already documents these exact camelCase field names and response shapes end-to-end (list/create/detail/update). Matching them now means Phase 2's swap to the generated `hey-api` client is a pure transport change — zero field renames in application code. Where the two conventions could conflict, the existing repo convention wins (see §6 on error shape, §3 on ID format) — `backend-api.md` is a design reference to align _with_, not a spec to reproduce byte-for-byte in a Phase 1 mock.

**Alternatives considered**: All-camelCase end-to-end (rejected — diverges from every existing schema file). Copying `backend-api.md`'s UUID IDs and `E-MNT-XXX` error codes verbatim (rejected — see §3 and §6).

## 3. ID format: `M-{NNN}`; allowed users as a join table against `staffs`, not a denormalized copy

**Decision**: Maintenance record ID is `M-001`, `M-002`, … — zero-padded 3-digit sequential (`max(existing numeric suffixes) + 1`), matching the UI prototype's own static sample data (`crm-maintenance-list.tsx`'s `MAINTENANCES` array: `M-001`…`M-007`) rather than `backend-api.md`'s UUID (`01912d4e-aa00-...`). Allowed users are stored as a join table `{ crm_maintenance_id, staff_id }` (mirroring `createBannerBrandMapTable()` in `banner.table.ts`'s brand-map pattern) — no `name`/`role` columns on the join row. Every read resolves `name`/`role` by looking up `db.staffs.getList()` for each `staff_id` at response time.

**Rationale**: `M-{NNN}` matches the exact prototype IDs, and the repo-wide `PREFIX-NNN` convention (`BN-001` banners, `AM-001` app-maintenances, `STF-001` staffs) — no other feature uses a bare `M-` prefix, so no collision. The join-table shape is `backend-api.md`'s own documented behavior verbatim ("Allowed users are resolved by joining the junction table to the staff master for name / role at read time") and avoids a second, potentially stale copy of staff name/role — if a staff member's name changes in `db.staffs`, every maintenance record's allowed-user list reflects it immediately with no sync step.

**Alternatives considered**: UUID IDs to match `backend-api.md` literally (rejected — every sibling Phase-1 mock feature, including `016-app-maintenance-mgmt`, deliberately uses its own short prefixed ID instead of the backend design's UUID; consistency with the mock-DB convention outweighs contract literalism here). Denormalizing `name`/`role` onto the join row at add-time (rejected — `backend-api.md` doesn't do this, and it would require a write-side sync whenever `db.staffs` changes).

## 4. Page-level access: extend `Permission`/`PAGE_PERMISSIONS`/`ROLE_PERMISSIONS`, not a new mechanism

**Decision**: Add `Permission.CrmMaintenanceView`, `.CrmMaintenanceCreate`, `.CrmMaintenanceEdit`, `.CrmMaintenanceDelete` to `src/types/permission.type.ts` (dot-string values `crm-maintenance.view`/`.create`/`.edit`/`.delete`, following the existing `AppMaintenance*` naming). Wire `PAGE_PERMISSIONS` (`/crm-maintenance` → `View`, `/crm-maintenance/create` → `Create`, `/crm-maintenance/:id` → `View`, `/crm-maintenance/:id/edit` → `Edit`) and add `CrmMaintenanceView` to both `[UserRole.System]` and `[UserRole.Headquarter]` blocks in `ROLE_PERMISSIONS` (`permission.constants.ts`), with `Create`/`Edit`/`Delete` in `[UserRole.System]` only — the exact pattern `AppMaintenance*` already establishes (Headquarter gets view-only). `RoleGatedButton`/`RoleGatedMenuItem` gate the "新規登録"/"編集"/"削除" affordances client-side using these same permissions; route handlers re-check the underlying role server-side (FR-020's actual enforcement, matching §1).

**Rationale**: This is the only access-control mechanism in the codebase (Constitution Principle V — no new abstraction). It already has a proven Y-06 precedent for the identical "System full access, Headquarter view-only, everyone else denied" shape.

**Alternatives considered**: A new bespoke role-check util (rejected — `getAuthUserFromRequest` + a literal role comparison, already used by `app-maintenances`, is simplest).

## 5. FR-007 staff search: reuse `GET /crm/staffs` as-is; map UI role labels to the lowercase `StaffRoleSchema` client-side

**Decision**: The allowed-user search dialog (`maintenance-form.tsx`'s "CRMユーザー検索") calls the **existing** `GET /crm/staffs` endpoint (already implemented for Y-01, `src/app/api/crm/staffs/route.ts`) via the **existing** generated `useGetCrmStaffs` hook — no new mock, no new route. The UI's two separate "ユーザーID"/"氏名" text inputs are merged client-side into the single `search` query param (`GetStaffsQuerySchema`'s `search: string` already matches on `staff_id` OR `name` OR `email` substring — see `src/app/api/crm/staffs/route.ts`'s filter chain). The UI's capitalized `ROLE_OPTIONS` (`"System"`, `"Headquarter"`, ...) are mapped to `StaffRoleSchema`'s lowercase enum (`'system'`, `'headquarter'`, ...) via a small constant lookup before the `role` query param is sent; "全ロール" maps to omitting the param entirely.

**Rationale**: Verified end-to-end during `/speckit.clarify`-adjacent investigation (this plan's prerequisite Q&A): `GetStaffsQuerySchema` already has `search?: string` ("Search by name or email", also matches `staff_id`) and `role?: StaffRoleSchema.optional()` ("Filter by role"), the route's filter chain already applies both, and the generated client (`src/lib/api/types.gen.ts`'s `GetCrmStaffsData`) already exposes both typed. All three of Y-10 FR-007's search criteria (ユーザーID partial / 氏名 partial / ロール exact) map directly onto this one existing endpoint with zero backend changes — only the two UI-layer adaptations above (param merge, casing map) are new work for this feature.

**Alternatives considered**: A dedicated `GET /crm/maintenances/staff-search` proxy endpoint (rejected — pure duplication of `/crm/staffs`, violates Constitution Principle V). Adding a capitalized alias enum to `staff.schema.ts` (rejected — the casing mismatch is a one-screen display concern, not a backend contract change; a client-side label map is the smaller, more localized fix).

## 6. Error shape: repo-wide `{ error: string }`, not `backend-api.md`'s `E-MNT-XXX` codes; incremental allowed-user endpoints not built

**Decision**: Every error response uses the existing `{ error: string }` shape (optionally `+ details: string[]` for Zod validation, matching `app-maintenances`), carrying the exact Japanese messages spec.md's FRs specify — not `backend-api.md`'s structured `E-MNT-001`…`E-MNT-006` / `E-AUTH-100`/`E-AUTH-103` codes. Overlap check compares `[startsAt, endsAt)` intervals against **every** existing row regardless of status (`planned`/`in_progress`/`completed`), per `backend-api.md`'s own rule and spec.md FR-005 — touching-but-not-overlapping boundaries (`e1 === s2`) are not a conflict. `PATCH .../maintenances/{id}` accepts an optional `allowedUserIds: string[]` that, when present, **fully replaces** the record's allowed-user set (validated against `db.staffs` — unknown or inactive IDs are rejected) — this single mechanism satisfies FR-015 (edit allowed users), FR-016 (start-date lock doesn't block it), and FR-017 (permitted even while `in_progress`, since the lock only ever applies to `startsAt`). `backend-api.md`'s separate "Add allowed users (bulk)" and "Remove one allowed user" endpoints, and the unauthenticated TAS-facing "Active CRM maintenance lookup" and the "Send advance notification" endpoint, are **not implemented** — none has a corresponding control in any of the three UI mockups (the shared create/edit form always submits the complete allowed-user set in one PATCH/POST; notification and the TAS lookup are outside CRM UI entirely, consistent with spec.md's Assumptions).

**Rationale**: Matches `016-app-maintenance-mgmt`'s identical choice to keep the mock layer's existing error-shape convention rather than adopt the backend design's structured codes. Not building unused endpoints is Constitution Principle V (YAGNI) applied the same way `016-app-maintenance-mgmt` deferred its own two low-impact open items — nothing here forecloses adding them later (`backend-api.md` remains the reference for Phase 2), it just isn't work this spec's UI requires now.

**Alternatives considered**: Building the incremental add/remove endpoints anyway "for completeness" (rejected — no caller exists in Phase 1, and the full-replace `PATCH` already covers every FR).

## 7. Seed data

Seed dates are generated **relative to `now()`**, not the UI prototype's literal (already-past, 2025–2026-04) sample dates — same reasoning as `app-maintenances`' seed (data-model.md's seed table): a literal-date seed would make every row `completed` on any date after April 2026, leaving nothing to manually verify `in_progress`/`planned` behavior against. Titles/allowed-user counts are otherwise inspired by the prototype's `MAINTENANCES` array for realism.
