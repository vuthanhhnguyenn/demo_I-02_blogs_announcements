### ⚠️ Spec-vs-mockup conflict — resolved in favor of the spec (flagged per Test philosophy #1)

The mockup still models notification as `{kind: "auto"|"manual", sentAt}` plus a `notifyTargetCount` display, and its comment implies re-send was once removed. The spec's **Clarifications, 2026-07-20 (4th/final bullet)** explicitly **supersedes** this: notification is a **single `notified` boolean**, no kind/timestamp/recipient-count is displayed, and the send button **stays visible and re-clickable** after 済 (relabeled "通知を再送信"), so a System user can re-send any number of times. All cases below are written to this simplified, final spec model — not the mockup's richer display. Do not raise an `NG` if the running app shows only a boolean state with an always-available re-send button; that is correct per spec.

**Second, related conflict (resolved 2026-07-28 by PO):** the mockup also disables the notify button for 完了 records ("完了したメンテナンスには通知できません"). Confirmed: the button's whole purpose is resend, so this does **not** apply — the button stays active and re-sendable regardless of computed status, including 完了 (see TC-B-027). The "—" that FR-022/Edge Cases mention for 完了 is scoped to the **List's notification column** only, not the Detail card's send button.

**Third, related conflict (resolved 2026-07-28 by dev):** TC-B-004 originally expected the feature-specific access-denied text quoted in the spec, for a denied role hitting this screen via a stale/direct link. Confirmed not a defect — the app-wide generic 403 page is the intended behavior (same resolution as `[Y-10-A]`'s TC-A-003–007; see that doc's conflict note).
