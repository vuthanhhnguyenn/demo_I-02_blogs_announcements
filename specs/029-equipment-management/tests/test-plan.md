**Split rationale**

- **One screen = one unit.** Six routes, each with its own spec section and prototype file → six units. The two lists are not merged even though the prototype renders them in one file: the project routes them separately (008 §Routing decision) and each has its own spec, columns, filters and API.
- **Dialogs cluster into their parent.** The 一括状態変更 dialog only exists on `/equipment`; the ステータス変更 and 削除 dialogs only exist on their detail page. Splitting them out would separate state that only exists together (e.g. the controller delete guard depends on the 紐付き機器 count the devices tab shows).
- **Create + edit cluster per entity.** Each pair is one component in two modes with the same validation (FR-005: 「FR-003と同一の入力チェック」; FR-007-C: same form). Mode deltas (read-only 機器タイプ / 店舗コード on edit, prefill, 出力ポート own-port handling, stale-edit lock) are mode-tagged cases inside the one doc, so the shared field-validation walk is not duplicated.
- **The shared layout chrome is owned by unit A** for authoring. Unit D re-checks only what changes on its tab (active tab, CSV behaviour on that tab, 接点制御装置を登録 entry, its own count badge) — it does not re-test the title/header.
- **エリアマスタ is one unit (G).** One route; its sheet and both dialogs exist only there (same reason as the dialog clustering above).
- **エリア扉 stays in A / B / C.** Same three screens with one more 機器タイプ, so its cases are added to those docs (tag `[エリア扉]`), not split into a new unit.
- **Consumer cases live with the screen they test.** A rule such as 「the member detail leaves out a 主契約 the member's 性別 does not meet」 is a permanent rule of that screen, and a regression run of that screen uses its own feature doc — so the cases go there, tagged `[Ladyroom]` (§2 table). This plan keeps what only it can own: unit G, the エリア扉 cases, the shared fixtures (§8), the pre-flight gaps (§7e) and the cross-feature order (§9).
- **Superseded cases elsewhere.** G-02 `261107_v9` replaced エリア制限設定 with 利用できるエリア, so `[G-02-B][Option Form]` TC-022 / TC-042 and `[G-02-C][Option Detail]` TC-018 test a control that no longer exists. The 026 plan rewrites those three cases in place as `[Ladyroom]` cases.
