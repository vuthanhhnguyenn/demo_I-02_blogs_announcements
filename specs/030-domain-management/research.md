# Research: Y-14 Domain Master Management

**Feature**: 030-domain-management | **Date**: 2026-08-18
**Purpose**: Resolve implementation-level decisions before Phase 1 design. `spec.md` has zero `[NEEDS CLARIFICATION]` tokens (validated in `checklists/requirements.md`); the items below ground the plan in the existing codebase's conventions, confirmed by a direct code survey (not assumptions).

This is a **greenfield** feature — no `domains` route, schema, or mock table exists anywhere in the codebase today (confirmed by exhaustive search of `src/app/api/_mock-db/`, `src/app/api/_schemas/`, `src/app/api/crm/`, `src/lib/routes/routes.config.ts`). Every decision below is "build new following an existing sibling pattern," not "extend existing code."

## R1 — New `domains` mock table; string `D-0xx` IDs

- **Decision**: Add a brand-new mock table (`src/app/api/_mock-db/tables/domain.table.ts`) with string, sequential, uppercase-prefixed IDs (`D-001`, `D-002`, ...), matching both the V0 prototype's seed data (`domain-list.tsx` `INITIAL_DOMAINS`) and spec.md's own Assumptions section.
- **Rationale**: No existing table represents this concept (see codebase survey below); the ID format is already specified by the source-of-truth V0 mockup and carried into `spec.md`'s Assumptions, so there is no reason to diverge (e.g., to a UUID or a lowercase `d-001` style like FC company IDs — that convention belongs to a different feature and isn't dictated here).
- **Alternatives considered**: Extending a hypothetical Y-13 auth-routing table — rejected, no such table exists yet (Y-13's login flow currently has no domain-lookup code at all; the comment referencing "Y-14ドメインマスタ" in the login mockup is aspirational, not implemented). Extending `FranchiseCompany` (which already has a company-level `auth_method` field) — rejected, `spec.md`'s own 関連機能 section explicitly distinguishes Y-03 (company-level auth method) from Y-14 (domain-level auth method) as separate masters that merely need to "stay consistent," not merge.

## R2 — Linked staff is derived by email-domain matching, not a stored FK

- **Decision**: `Staff.email`'s domain portion (everything after `@`, lower-cased) is matched against `Domain.domain` (also lower-cased) at read time to compute `staffCount` (list + delete guard) and the linked-staff list (detail view). **No `domain_id` field is added to the Staff schema.**
- **Rationale**: `src/app/api/_schemas/staff.schema.ts` already has a required `email: z.string().email()` field on every staff record — the linkage `spec.md` FR-001/FR-010/FR-013 describes ("当該ドメインに紐づく登録済みスタッフ") is fully derivable from that field alone. Adding a parallel `domain_id` FK would require touching the Y-01 Staff feature (out of this feature's scope per spec.md, which only lists Staff as a _referenced_ entity) and would risk drifting out of sync with the actual email address if not kept in lockstep. Deriving it live is simpler (Constitution V — YAGNI) and can never disagree with the email that Y-13's real login flow will eventually key off of.
- **Alternatives considered**: A `domain_id` FK on Staff (mirroring `position_id`) — rejected per above. A join/mapping table like `ArticleCategoryMapping` — rejected as unnecessary indirection; a direct string-suffix match against the existing `staffs` table is a single query, no extra table to seed/maintain.

## R3 — `authProvider` enum values mirror `FranchiseCompanyAuthMethodSchema`, as an independent schema

- **Decision**: Define `DomainAuthMethodSchema = z.enum(['google_sso', 'idaas'])` in the new `domain.schema.ts`, using the **same string values** already established by `FranchiseCompanyAuthMethodSchema` (`src/app/api/_schemas/franchise-company.schema.ts`) — but as its own schema, not a shared import.
- **Rationale**: `spec.md`'s Assumptions state authentication method is constrained to exactly these two values, matching Y-13's two login routes; reusing the exact same string values as the existing Y-03 company-level field keeps the two masters trivially comparable (e.g., for a future consistency check) without coupling their schemas — spec.md's own 関連機能 section treats Y-03 and Y-14 as related-but-distinct masters, so importing one schema into the other would overstate the relationship.
- **Alternatives considered**: Import `FranchiseCompanyAuthMethodSchema` directly — rejected, couples two independently-owned master entities for no behavioral benefit. Invent new enum values (e.g. `'google' | 'idaas'`) — rejected, gratuitous divergence from an already-established convention in the same codebase.

## R4 — Single-route UI; extend V0's Dialog rather than add a detail page

- **Decision**: One route, `/domains`, hosts everything — list, search, create dialog, edit dialog (widened from V0's 480px to fit the additional fields), and delete confirmation — with no separate `/domains/create` or `/domains/[id]/edit` routes.
- **Rationale**: V0's `domain-list.tsx` already implements the entire feature as a single page with two dialogs; `spec.md`'s User Story 3 (edit + view linked staff + creator/created-at) adds _content_ to the existing edit dialog, not a new _surface_. Constitution IV requires "the shortest UX path" and no unnecessary modals/wizards — introducing a whole new page route for what is still a single small form plus a read-only staff list would add navigation with no corresponding user benefit, especially given the master's expected scale (a handful to a few dozen domains, one per allowed company).
- **Alternatives considered**: A dedicated `/domains/[id]` detail page (mirroring `positions`' two-pane list+preview or `brands`' tabbed detail page) — rejected as disproportionate to this entity's field count and V0's own established modal-first design; revisit only if this master grows materially more complex.

## R5 — Phase 1 excludes `status`/enable-disable entirely (no dead code)

- **Decision**: The `Domain` schema, mock table, and UI carry **no** `status` field, badge, or toggle action in Phase 1. FR-015 (enable/disable) is deferred whole-cloth to a future feature slice.
- **Rationale**: `spec.md` explicitly scopes FR-015 as "Should, Phase 2" and its own Assumptions section calls out that V0's status column/toggle must **not** be built now even though the mockup renders it. Since this is a greenfield feature (nothing to "comment out" — unlike the brownfield `021-brand-management` precedent), the correct action is simply not writing that code at all: no unused schema field, no dead toggle handler, no disabled-but-visible UI. `checklists/parity.md` already marks PAR016/PAR017 (the status Badge and toggle menu item) as explicitly out of scope for this phase.
- **Alternatives considered**: Add the `status` field now but leave the UI toggle inert — rejected, an unused schema field with no reader is dead weight (Constitution V) and risks a false signal that Phase 2 is "mostly done" when the actual login-blocking behavior (Y-13 side) doesn't exist yet either.

## R6 — Delete guard order and semantics

- **Decision**: `DELETE /api/crm/domains/{id}`: unknown id → 404; `staffCount ≥ 1` (computed per R2) → 409 with the count in the response body; otherwise physical delete → 200. No soft delete, no `is_system_managed`-style protected-row concept (nothing in spec.md calls for one). The list/detail row's delete action is additionally disabled client-side whenever `staffCount > 0`, matching the position-master precedent (`can_manage_position` delete guard) — the 409 remains defense-in-depth.
- **Rationale**: Directly matches `spec.md` FR-013 ("紐づきスタッフが存在する場合は削除をブロックし... 先にスタッフの所属変更または無効化を促す") and User Story 4's acceptance scenarios. Mirrors the exact guard-ordering convention already used by `positions` delete (`017-position-management` research R10) and `article-categories` (reassign-then-delete, though that entity's guard shape differs since it has a fallback target and this one doesn't).
- **Alternatives considered**: Soft delete — rejected, nothing in spec.md or V0 suggests domains are ever "trashed" and recovered; Reassign linked staff to a fallback domain automatically (like `article-categories`' Unclassified-category reassignment) — rejected, `spec.md` FR-013 explicitly requires a **hard block** directing the user to Y-01 first, not a silent reassignment, since silently changing a staff member's authentication routing during an unrelated domain deletion would be an unreviewed access-control side effect.

## R7 — Permissions, routing, and navigation

- **Decision**: Add `Permission.DomainsView / DomainsCreate / DomainsEdit / DomainsDelete` to `src/types/permission.type.ts`, following the existing `<Resource><Action>` enum convention. Register `'/domains': Permission.DomainsView` in `PAGE_PERMISSIONS` (`src/constants/permission.constants.ts`); grant all four to `System` (implicit, already gets every permission) and `Headquarter` explicitly — no other role receives any Domains permission, matching spec.md's 権限マトリクス (System/HQ only, all others ×). In-page actions use `RoleGatedButton`/`DataTableRowActions` with `requiredPermission={Permission.Domains*}` (the permission-based gating path both components already support), not a hardcoded `allowedRoles` array — consistent with the most recently built master screens (`article-categories`). Add a `ドメイン管理 → /domains` entry to the existing システム設定 section's 組織・店舗 group in `src/components/layout/app-sidebar.tsx` (the section already lists `スタッフ管理`, `職位マスター管理`, `店舗管理`, `FC企業管理`, `ブランド管理` — Domain management is a direct sibling of these). Sidebar visibility and the page-header's "HQ専用" badge both derive automatically from `PAGE_PERMISSIONS`/`ROLE_PERMISSIONS` via `canRoleAccessPage`/`isPageHqOnly` — no bespoke access-denied UI needed (same pattern `021-brand-management` research G7 already established for this codebase).
- **Rationale**: This is the single established pattern for every existing master-data screen; there is no reason to deviate.
- **Alternatives considered**: `allowedRoles`-array gating (V0's own style, and older screens like `positions`' original cut) — rejected in favor of the permission-based path since it is the more current convention and lets the exact same `Permission.Domains*` enum drive route-gating, sidebar visibility, and in-page affordances from one source instead of three.

## R8 — Auth-method-change confirmation is UI-only; no backend side effect beyond persisting the field

- **Decision**: The confirmation dialog required by `spec.md` FR-011 ("linked staff's authentication route changes starting from their next login") is a pure client-side confirmation gating the `PATCH` call. The mock `PATCH /api/crm/domains/{id}` does nothing beyond persisting the new `authProvider` value — it does not simulate forcing any staff session invalidation or write any Y-13-side state.
- **Rationale**: `spec.md`'s own 関連機能 section places the actual login-routing _consumption_ of this master inside Y-13, which is a separate, already-specced feature this plan does not modify. Simulating cross-feature session effects here would be speculative scope creep (Constitution V — YAGNI) with no consumer to exercise it, since Y-13's mock login flow does not read this table today (confirmed in the codebase survey) and wiring that read is Y-13's own future work, not Y-14's.
- **Alternatives considered**: Also updating Y-13's mock login route to consult this new table — rejected as out of scope; `spec.md` frames Y-13 integration as a stated dependency/relationship, not a deliverable of this feature.

## R9 — `authProvider` UI (column/filter/field) is Phase 1 scope regardless of `qa-authprovider.md` Q1-Q4 (2026-09-09 update)

- **Decision**: The 認証方式 column, list filter, and create/edit form field — built once in the initial implementation, then commented out behind `TODO(Y-14 Q&A pending, see specs/030-domain-management/qa-authprovider.md)` markers — are re-enabled as-is. The backend (`domain.schema.ts`, `domain.table.ts`) never stopped exposing `authProvider`/`staffCount`/`linkedStaff`; only the frontend was paused.
- **Rationale**: `qa-authprovider.md` Q1 and Q2 ask about _cross-system conflict/priority behavior_ between Y-14, Y-03 (FC company master), and Y-13 (login routing) when their authentication-method settings disagree — they do not ask whether Y-14 itself should collect or display an authentication method. The refreshed V0 mockup (`domain-list.tsx` @6bc1f1c, 2026-09-08) independently confirms the field/column/filter as core Y-14 UI, and `spec.md` FR-001/FR-004/FR-011 already required them from the original 2026-08-18 draft. Re-enabling this UI does not require Q1/Q2 to be answered; it only means Y-14's own recorded value may, in a rare cross-system conflict, disagree with Y-03's — a pre-existing risk the mock backend already accepts by design (R3: independent enum, no cross-validation), unaffected by whether the field is visible in this screen.
- **Alternatives considered**: Waiting for PO answers to Q1-Q4 before re-enabling — rejected; it blocks visible, spec-mandated, already-built, already-tested-against-real-seed-data functionality over questions that are orthogonal to this screen's own behavior. Q1/Q2 remain open in `qa-authprovider.md` and should still be routed to the PO, but as a Y-13/Y-03 cross-reference concern, not a Y-14 blocker.

## R4 amendment (2026-09-09) — read-only Sheet added alongside the widened edit Dialog

R4's original decision (single `/domains` route, no separate detail page) still holds — no new route is added. However, the refreshed V0 (@6bc1f1c) now splits the previously-combined edit Dialog into two surfaces: a read-only detail **Sheet** (creator/created-at, linked-staff list, opened by clicking a row) and a purely-editable Dialog (name/domain/authProvider only, opened via an explicit 編集 action). This plan follows V0's split rather than the original single-Dialog shape, reusing the existing `DataTable.onRowClick` prop (already used by ~15 sibling screens for the same Sheet-on-row-click pattern) — still no new route, no new abstraction, just one additional component file.
