# Test Cases: Domain Management (Y-14-A)

> Driven by [test-plan.md](../test-plan.md), unit "Domain Management". Covers the single `/domains` screen and its add/edit/delete dialogs (no separate detail route exists).

## Source note

- **Spec**: `specs/030-domain-management/spec.md` — User Stories 1–4, Edge Cases, FR-001–FR-014, Key Entities (`Domain`). FR-015 / User Story 5 (enable/disable) intentionally excluded — Phase 2, out of scope per spec Assumptions.
- **Requirement doc**: `.cache/fitness-spec/crm/requirements/Y-14.md` — FR-M001–FR-M004, 権限マトリクス, 業務フロー.
- **UI mockup**: `.cache/fitness-crm-ui/src/pages/domain-list.tsx` — **predates the finalized Y-14 spec** (it is the earlier "AUTH-02" draft). It does NOT show: the 認証方式 (auth method) column/field, the スタッフ数 (staff count) column, the linked-staff list on edit, delete-blocking-when-staff-linked, the auth-method-change confirmation dialog, or the auth-method search filter. These UI elements are net-new per spec Assumptions — their exact layout/wording is not shown anywhere, so cases involving them assert on the spec's plain-language description (e.g. exact error text FR-005 states) rather than a mockup screenshot, and are flagged in Notes where the presentation detail (dialog copy beyond the stated sentence, control placement) is an open question for the tester to record as observed, not to fail on.
- **Checklists used**: `tests/checklists/common-function-checklist.md`, `tests/checklists/common-gui-validate-checklist.md`. No gaps found requiring a new shared-checklist row — existing rows (Search, Add New, Update, Delete, Dialog/Confirmation "governed-field" row, Default field constraints, Output Escaping, Other Cases permission rows) cover this screen's shape.
- **Not read**: application source (`src/app/(private)/domains/**`, `src/app/api/**`, mock-db/seed files, Zod schemas) — per skill instructions, expected results are derived from the spec/mockup only, never from the implementation.

**Data limitations**:

- Exact seeded スタッフ数 per domain is unknown from spec/mockup. Before running the delete-block (TC-050) and linked-staff-list (TC-041) cases, first inspect the live list to find a domain whose スタッフ数 > 0 and one with = 0. If no seed domain has スタッフ数 > 0, mark those cases `Block` — no fixture available — rather than fabricating a link (staff-to-domain linkage is owned by Y-01, out of scope here).
- Tester-created fixtures for deterministic cases (duplicate/format/boundary validation), suggested naming to avoid colliding with seed data or other testers' fixtures on a shared dev server:
  - Fixture A: 管理名 `QAテスト株式会社`, ドメイン `qa-test-001.co.jp`, 認証方式 Google SSO
  - Fixture B: 管理名 `QAテスト株式会社２`, ドメイン `qa-test-002.co.jp`, 認証方式 IDaaS
- Whether multi-page pagination is reachable depends on total seed row count at execution time; if fewer than one page size (e.g. 25) of domains exist, note pagination cases as `Block` — insufficient data, per the plan's data-limitation guidance rather than treating an unreachable second page as a failure.
