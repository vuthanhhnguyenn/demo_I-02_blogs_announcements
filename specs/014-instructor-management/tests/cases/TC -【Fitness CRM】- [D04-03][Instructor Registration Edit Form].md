**Spec-vs-mockup gaps and notable findings flagged here (and again inline in the affected cases' Notes):**

1. **The edit form always loads the same single hardcoded record** (`INSTRUCTORS[0]`, ID 45 「タムタ タム」) regardless of which row was actually clicked from the list/detail screen — there is no route/id parameter wired into `InstructorFormView`. Pre-fill-accuracy cases can only be verified against this one record; "edit a _different_ instructor and confirm its own values pre-fill" cannot be exercised in this prototype at all. See TC-010, TC-018, TC-026, TC-065.
2. **`isTrainerSelfEdit` is computed as `isEdit && user.role === "Trainer"` — with no check that the instructor being edited is actually that Trainer's own profile.** Per FR-018, a Trainer should only be able to reach the edit form for their own record at all; attempting to edit another instructor should be blocked at the entry point, not merely field-locked the same way. Because the mockup has no per-instructor identity check here, "Trainer editing self" and "Trainer editing another" are indistinguishable in the current build — both render the identical field-locked form. Written to the spec's required behavior and marked `Block`/needs-real-access-control. See TC-058–TC-062.
3. **The registration/edit form component itself performs no role check at all.** The only gating in this prototype is the `RoleGatedButton` on the D04-01 list screen (button-level, out of scope for this doc); a direct navigation to the form URL bypasses it entirely for any role, including Trainer/Observer attempting create, or a non-self Trainer attempting edit. Per the Edge Cases section ("the action must remain disabled/blocked... consistent with the button-level gating"), this is a genuine, testable gap — written to spec, marked `Block` against the current mockup. See TC-063, TC-064.
4. **The nickname field has no React state at all** (`defaultValue` only, no `onChange`/`useState`) — whatever the user types is never captured anywhere. The confirmation dialog's ニックネーム line always shows the record's original value in edit mode (or "—" in create mode) regardless of what was actually typed into the field. This directly matches the existing `common-gui-validate-checklist.md` "Dialog / Confirmation Message" row on live-value fidelity (no new checklist row needed) — cited directly. See TC-022.
5. **Buffer settings and the CRM Account Link are not part of the `Instructor` data model at all** (confirmed against the `InstructorItem` interface — no buffer-lead-time/pre-buffer/post-buffer/crmLink fields exist). Edit mode's buffer-setting defaults (`24時間`/`15分`/`15分`) and the CRM link's always-empty starting state are hardcoded by `mode`, not derived from any specific instructor's saved data — "pre-fill accuracy" for these two sections cannot be verified per-record in the current prototype. See TC-041, TC-042.
6. **The Status card's `formStatusActive` always initializes to `true`** (`useState(true)`), regardless of `mode` or the actual instructor's stored status — edit mode does not pre-fill the real status value. Unreachable as a concrete defect in this prototype only because the hardcoded edit record (ID 45) happens to already be Active; flagged as a data-model gap rather than an observable bug today. See TC-049.
7. **The confirmation dialog's Confirm button is currently a no-op beyond closing the dialog** — `onClick={() => setConfirmOpen(false)}` performs no create/update, shows no success toast, and does not navigate back to the list/detail per spec AS2.3/AS4.3. This is explicitly BE-owned (mocked backend) and must be re-verified once the real API is wired — log as `Block`, not `NG`, per the skill's BE-mocked-caveat guidance. See TC-056.
8. **The confirmation dialog's title/action wording DOES differ between create and edit** ("〜登録します。よろしいですか？" / "この内容で登録する" vs. "〜保存します。よろしいですか？" / "この内容で保存する") — this resolves the test-plan §4 open question ("verify the actual mockup copy for both modes... record it as an open question if the two truly share identical dialog text"): they do **not** share identical text, so no open question remains here. See TC-052.
9. **No injected-markup (XSS) or near-boundary-length seed record exists** for any text field on this form — those cases must be exercised by typing the value directly during execution, not by selecting an existing row.
10. **A checklist gap was found and fixed**: `common-function-checklist.md`'s existing "Role-Locked Field (Self-Only Override)" section only covered a _single_ field forced to the current user's own identity (e.g. assignee = myself). This form's Trainer-self lock is a _multi-field partial lock_ (name + role classification lock; nickname/romaji/profile/photo/history/buffer settings/CRM link/status stay open) on the same record — a new row was added to that section covering per-field verification of a mixed lock/unlock form rather than a single locked field. See TC-058–TC-061.
