All sources were available and readable — no `Block`-for-missing-source cases were needed. Several cases are still marked `Block`/deferred for lack of **test data** or because a section is **structurally not wired per-instructor in the static mockup** — noted individually, and summarized here:

**Spec-vs-mockup gaps and notable findings flagged here (and again inline in the affected cases' Notes):**

1. **The Trainer self-vs-other edit exception is entirely unimplemented.** `RoleGatedButton`'s check is `allowedRoles.includes(user.role)` only (see `role-gated-button.tsx`) — nothing in `InstructorDetailView` compares the viewed `instructor.id` against the logged-in Trainer's own record. The spec's Edge Case ("a Trainer opens the detail page for an instructor other than themselves — edit/delete actions must reflect the standard permission matrix, not the self-edit exception") cannot be observed failing OR passing on the current prototype, because there is no self/other branch at all — a Trainer's Edit button is currently enabled identically regardless of whose profile is open. This is flagged as the single highest-value regression risk in the whole D-04 cluster per the test-plan's coverage focus. See TC-011, TC-018.
2. **No role/store scope check exists on the detail page's `id` lookup itself.** `const instructor = [...INSTRUCTORS, ...PERSONAL_TRAINERS].find((i) => String(i.id) === idParam) ?? INSTRUCTORS[0]` performs no scoping by role or store — any logged-in role can open any instructor's detail page by direct id, and an unrecognized id silently falls back to `INSTRUCTORS[0]` rather than a not-found/blocked state. FR-005's detail-half scoping (Manager/Staff/Observer store-scope, Trainer self-only) is entirely unimplemented here, mirroring D04-01's list-side finding. See TC-005–TC-007, TC-015–TC-018.
3. **The Deactivate/Activate button carries NO role gating at all.** Unlike Delete and Edit (both wrapped in `RoleGatedButton`), the status-toggle button at the bottom of the ステータス card is a plain `<Button>` with no `allowedRoles` check — per FR-016 and the 権限マトリクス, only Headquarters/Manager should be able to use it, but the current mockup exposes it, fully clickable, to every role that can reach the detail page (including Staff, Trainer, Observer). See TC-044.
4. **The CRM Account Link card always renders unconditionally.** The code comment above it reads "CRMアカウント紐づけ（紐づけあり場合のみ表示）" ("shown only when linked"), documenting the intended conditional, but the JSX has no `if`/conditional guard — it always renders `STAFF_LIST[0]` regardless of whether the open instructor actually has a link. FR-008's "optional" linkage cannot be observed in its absent state on this screen. See TC-031, TC-032.
5. **Photo, buffer settings, performance summary, Assigned Lessons, Upcoming Schedule, and Change History are all hardcoded literals or module-level constants, independent of which instructor id is open.** Every instructor's detail page currently renders byte-identical content in these sections (same stock photo URL, same "15分/15分/24時間前まで" buffer values, same 9/87%/4.6/156 performance figures, the same 5-row `ASSIGNED_LESSONS` array, the same 9-entry `upcomingSchedules` array, the same 4-entry history array). None of these sections are wired to per-instructor data in the current static prototype. Flagged individually at each affected case (TC-024, TC-027, TC-033, TC-039, TC-051, TC-057, TC-088) rather than only once, since each is its own display slice this doc must independently confirm once real per-instructor data exists.
6. **Booked/capacity tier-color logic differs between the inline Upcoming Schedule card and the Sheet's individual schedule list for the exact same entries.** The inline (first-3) card uses `booked>=capacity ? destructive : ratio>=0.8 ? success : muted` (3 tiers), while the Sheet's individual list uses `isFull ? destructive : ratio>=0.8(not full) ? warning : booked>0 ? success : muted` (4 tiers). For the first 3 entries (the only ones visible in both places at once): 14/16 (87.5%) and 16/20 (80%) render **success** inline but **warning** in the Sheet. This is flagged as a likely unintentional implementation drift — see the new common-gui-validate-checklist cross-rendering-consistency row and TC-066.
7. **No entry across all 9 `upcomingSchedules` rows reaches `booked >= capacity`** (max ratio is 15/16 = 93.75%) — the "full" / destructive tier is unreachable with current seed data in both the inline card and the Sheet. Noted in the Test data reference and TC-066's notes rather than a separate row.
8. **The Trainer demo account (`U-007`, `demo-users.ts`) carries no field tying it to a specific `INSTRUCTORS`/`PERSONAL_TRAINERS` row.** Same limitation as D04-01 Source note #9 — confirm at execution which Trainer test identity (if any) the real environment provides before running the self-vs-other cases. See TC-010, TC-011, TC-018.
9. **Confirming delete on a 0-assigned-schedule record only closes the dialog** (`onClick={() => setDeleteOpen(false)}`) — no actual record removal, redirect, or success message is wired, unlike `common-function-checklist.md`'s Delete section (`"[Deleted record name] deleted successfully"` + record-count decrease + redirect). Must be re-verified fully against the real API. See TC-070.
