**Spec-vs-mockup gaps and notable findings flagged here (and again inline in the affected cases' Notes):**

1. **No role-based data-scope filtering exists anywhere in the list mockup.** `useCurrentUser` is never imported or called inside `InstructorListView`/`InstructorTable` — the static `INSTRUCTORS`/`PERSONAL_TRAINERS` arrays render in full regardless of the logged-in role. FR-005 (System/HQ: all; Manager: managed-store; Staff/Observer: own-store; Trainer: own profile only) is entirely unimplemented in this prototype screen. Cases are written to the spec's required behavior (oracle) and flagged individually as unverifiable against the current static mockup — see TC-018–TC-024.
2. **The Instructor entity carries no store/brand field to scope by in the first place.** Per the spec's Key Entities section and Out of Scope list, store/brand assignment is deliberately **not** stored on the Instructor record — it is derived from D-01 schedule assignments. This means Manager/Staff/Observer store-scoping for this screen cannot be verified in isolation from D-01 schedule data even once the real API is wired up; testers need to know which schedule-derived store an instructor belongs to before they can confirm scope exclusion. Flagged as a cross-feature dependency, not a simple data-seeding gap. See TC-020–TC-022.
3. **Role filter offers a "dead option" per tab pool.** The 役割区分 filter Select lists all 3 role values (トレーナー/インストラクター/ボディケアセラピスト) identically on both tabs, but each tab's underlying pool only contains a subset: `INSTRUCTORS` (Studio Instructor tab) has no トレーナー row at all; `PERSONAL_TRAINERS` (Personal Trainer tab) has no インストラクター row at all. Selecting トレーナー on the Studio tab, or インストラクター on the PT tab, is structurally guaranteed to return zero rows — this is exactly the "dead filter option" pattern already documented in `common-function-checklist.md`'s Search section (no new checklist row needed). See TC-039.
4. **Tab badge counts are static totals, not live-filtered or scope-derived.** The `TabsTrigger` badges render `{INSTRUCTORS.length}` / `{PERSONAL_TRAINERS.length}` directly from the raw array — they do not react to the active search/filter state on that tab (unlike the footer's "N件中 …" text, which does), and (per finding #1) they are not derived from any role scope either. This is a distinct, deliberate design (tab badge = total-in-scope count; footer text = currently-visible count) rather than a bug, but the two must not be confused when authoring/executing cases. See TC-010.
5. **Tab-local filter/search state persistence across tab switches is unverifiable from the design mockup's text alone.** Each `InstructorTable` instance owns independent `useState` for its own search/filter values; whether Base UI's `Tabs`/`TabsContent` keeps an inactive tab's panel mounted (preserving its filter state) or unmounts it (resetting on return) is a library-internal detail this skill does not read (per gen-testcases sourcing rules — no implementation code). Recorded as an open verification item, not assumed either way. See TC-011.
6. **Search placeholder text under-describes the actual/spec'd search fields.** The input's placeholder reads "氏名・ニックネーム・IDで検索..." (name/nickname/ID), but both FR-002/US1-AS2 and the mockup's actual filter predicate also match on romaji name (a 4th field). Minor UI-copy gap, not a functional defect — flagged, not blocking. See TC-030, TC-032.
7. **Pagination controls are static and non-functional.** The footer always renders "前へ" (disabled), page "1" (active), page "2", and "次へ" regardless of the actual filtered row count — no real page-size slicing occurs and the buttons carry no `onClick`/state wiring. Combined with the current 6-row-per-tab seed (never exceeding one page), true pagination mechanics cannot be exercised on this screen at all right now. See TC-049–TC-051.
8. **The true "empty" (zero-record, unfiltered) state is unreachable with current seed data.** Both tabs always contain 6 rows; the only reachable `Empty` variant is `"filtered"` ("条件に一致する指導者がありません" + "条件をクリア" action). The `"empty"` variant ("指導者がまだありません") exists in the shared component but has no seed scenario to reach it here. See TC-042.
9. **Trainer's "self" instructor record is not derivable from demo/seed data.** `demo-users.ts`'s Trainer account (`U-00x`, position "社員トレーナー") carries only a `single_store` scope — no field ties it to a specific row in `INSTRUCTORS`/`PERSONAL_TRAINERS`. Per test-plan §6, confirm at execution which Trainer test identity (if any) the real environment provides before running the Trainer-self-scope case. See TC-020.
