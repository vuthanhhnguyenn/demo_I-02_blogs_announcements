## Guiding principle

**UI first.** Where the real API cannot yet back a UI element, the element **stays as it is
today**: rendered, but disabled with a short 「API未対応」 note where leaving it live would
silently lose input, and stripped from every request body where sending it would be rejected.
Each such point carries a `TODO(round2)` comment naming its blocker id (`B1`…`B16`). No UI is
deleted to fit the current API surface. Round 2 closes those TODOs once the API is fixed —
nothing else.

**The UI is first brought up to the latest prototype (Phase 0)**, because the prototype has moved
on since the feature was built (8/13 → 9/17 design updates) and most of those changes move the UI
_towards_ the real contract (structured address, card token, guardian name/consent time, 未審査
KPI = submitted only, mandatory campaign, page size ≤ 100). Wiring the stale UI first would mean
wiring several surfaces twice.

Mock API routes under `src/app/api/crm/membership-applications/**`, the mock Zod schemas and the
`_mock-db` tables/seeds are **left untouched** (same convention as the positions / staffs /
domains / stores integrations) — they simply stop being called by this feature.

## Decisions

- **D1 — DTOs consumed directly, no mapper layer.** Components import from `@/lib/api-real/types.gen`; renames (`applicant_name` → `member.lastName/firstName`, `application_date` → `appliedAt`, …) happen in place. Precedent: staffs/stores integrations.
- **D2 — Six UI statuses kept, derived in one place.** `_utils/application-status.util.ts` exports `toUiStatus(status, approvalMethod)`: `submitted`→`pending`, `under_review`→`review`, `approved`+`auto`→`auto_approved`, `approved`(other)→`approved`, `rejected`, `cancelled`. `STATUS_LABELS` / badge classes keep their keys, so every label stays type-checked.
- **D3 — URL vocabulary unchanged.** nuqs keeps `status=pending|…`, `route=…`, `blacklist=…`, `sort_by=…` so bookmarks survive; `queryParams` translates: `auto_approved` → `status=approved&approvalMethod=auto`, `approved` → `status=approved&approvalMethod=manual`; `blacklist=match|no_match` → `blacklistFlagged=true|false`; `brand` → `brandGroup`; `store` → `storeId`; `date_from/to` → `appliedFrom/To`; sort `id`→`applicationNumber`, `applicant_name`→`memberNameKana`, `application_date`→`createdAt`, `usage_start_date`→`usageStartDate`, `status`→`status`.
- **D4 — Page size `[25, 50, 100]`, default 50.** Matches both the 9/8 prototype and the API clamp (1–100). A `limit=200` URL falls back to the default via the existing parser.
- **D5 — Counts.** KPI from `kpi.pendingReviewCount` / `kpi.blacklistFlaggedCount`; filtered count from `pagination.totalItems`; baseline from `pagination.totalAllItems` (`includeTotalAll: true`) — no second query needed.
- **D6 — 対応超過 from the API.** `isReviewOverdue` drives the badge, the tooltip renders `reviewOverdueHours`; `PENDING_OVERDUE_THRESHOLD_HOURS` and the client clock comparison are removed.
- **D7 — Name lookups.** `_hooks/use-application-lookups.ts` builds `storeById` (with `brandGroup`), `planById`, `campaignById` maps from the list endpoints (stores `limit: 100`, plans `limit: 200`, campaigns `limit: 100`) — same pattern as the transfers banner. An unknown id renders 「—」. Applicant name falls back to 「—」 when the API degrades `member` to `{ memberId }`.
- **D8 — Age checks client-side.** API `isMinor` is always false and `ageEligible` always true; the checklist uses `member.ageAtApplication` against the existing `BRAND_MIN_AGE` map (brand from `storeById`). Commented `TODO(round2)` is **not** needed — this is a documented placeholder the FE is told to compute.
- **D9 — Exemption UI is server-driven.** `enrollmentFeeWaiver` (`campaign|reenrollment|staff`) and `reenrollmentWaiver` (`ruleDays`, `eligible`, `daysSinceWithdrawal`) replace the provisional client precedence (FR-025a): the server decides which waiver applies. 「個別に免除する」 shows only when reviewable ∧ `enrollmentFeeWaiver == null` ∧ `calculatedAmounts.enrollmentFee > 0` (per the DTO description); the reason goes in `approve.enrollmentFeeWaiver.reason` (1–1000). The 180-day constant goes away (render `ruleDays`).
- **D10 — Optimistic concurrency.** approve/reject send `expectedStatus` = current API status; cancel sends `expectedStatus: 'approved'`.
- **D11 — Errors by code; no local error toasts.** `E-ENR-002`/`E-ENR-007` → invalidate detail + list (state changed); `E-ENR-005` (daily limit) and `E-ENR-201` (usage started) → existing `cancel-error-dialog` (with `meta: { suppressErrorToast: true }`); `E-ENR-204` (BL unchecked) and `E-ENR-018` (waiver conflict) → shared toast; `E-ENR-012` → not-found state; `E-ENR-016` → shared toast. Every local `onError: toast.error` on these mutations is deleted.
- **D12 — Create body.** `applicationSource: 'proxy'` (C-01 FR-M009 「代理申請として記録（FR-M010 を適用）」), `proxyStaffId` = signed-in staff id, `proxyAgreedAt` = 合意日時 (ISO); `phoneNumber` with hyphens stripped; `address.prefectureCode` = JIS code from `PREFECTURES` index + 1, zero-padded; `gender` `no_answer` → `prefer_not_to_say`; payment `credit_card` → `sbps_credit` (+ `sbpsCardToken`), `bank_transfer` → `jaccs_bank`; minors send `parentName` + `parentApprovalAt`; 紹介コード resolved to `promotionCodeId` via `promotion-codes?codePrefix=` exact match (unresolved code → inline field error, nothing sent). If the smoke run shows `proxy` is rejected for this route, fall back to `crm_direct` and record it here.
- **D13 — Rejection reason mapping.** `identity_incomplete` → `identity_verification_failure`; others identical. The UI keeps its key set; a drift assertion against `RejectApplicationDto['rejectReasonCode']` fails `tsc` if the BE enum changes. Same assertion for gender and payment method maps.
- **D14 — 会員詳細 link.** After approval (and for 自動承認済), 会員ID = `member.memberNumber`, link = `/members/[id]` with `member.memberId` (uuid).
- **D15 — Read-only gating unchanged.** Existing `Permission.MembershipApplications*` gates stay; the cancel menu shows only for 承認済/自動承認済 (Phase 0).
- **D16 — Mocks untouched; one cross-screen link left on mock ids.** `visit-experiences/[id]/_components/permit-actions.tsx` still links with mock `AP-…` ids (visit screens are not integrated); it is noted, not changed.
- **D17 — Campaign decides the plan (2026-10-15, 案1).** Live run hit `400 E-VAL-001` 「planId must equal the campaign plan」 on `price-estimate` / create when plan Fit365 Family (dev) was sent with campaign 会員紹介 (FIT365 dev), whose plan is Fit365 Standard (dev) — correct per API-098 §5.2 / §12 and C-01 L212. BE declined a `planId` filter on `GET /admin/stores/{id}/campaigns` (API-088 §10.2 has none; it would reverse 「キャンペーン選択→主契約が決まる」); the customer (Otaki) chose 案1, no FR / API change. Form: 適用キャンペーン lists `isAccepting=true&recruitmentActiveOn=<today>` rows with `isPublished` (API-088 §19.1a, so the pick never answers E-CMP-021); picking one sets `plan_id = campaign.planId`; プラン sits after 適用キャンペーン, read-only, showing `campaign.planName`; the store-plan picker (`GET /admin/stores/{id}/plans`) is no longer used. Usage period vs 利用開始日 stays server-side (`E-CMP-022` → 利用開始日); a residual `E-VAL-001` on `planId` maps to 適用キャンペーン. Deliberate deviation from the prototype (independent selects) until the separate UI instruction arrives.
