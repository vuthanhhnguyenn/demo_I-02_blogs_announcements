## 1. Scope

**In scope**: the three screens of this feature, each driven by one prototype file.

- **Application list** (C-01): KPI cards, search, filter panel, 5 sortable columns, overdue badge, BL row treatment, pagination, empty states, store scoping, the 管理画面から入会登録 entry point.
- **Approval detail** (C-01-01): applicant info with masked PII and face photo, BL card, contract info, fee breakdown with the server-decided 入会金 waiver, pre-approval checklist, companion-upgrade banner, status/meta cards, timeline + memos, **and** the approve / reject / cancel dialogs that live only inside this screen.
- **Admin enrolment form** (FR-M009/FR-M010 under C-01): route display (手動 / 紹介経由), applicant + address + guardian, contract selection, 紹介コード, card token, 規約同意, proxy record, BL precheck, `price-estimate` fees, confirm + completion dialogs.

**Out of scope**: navigation targets or separate specs. Do not expand into these.

- **Mobile-app enrolment and auto-approval**: 自動承認済 rows are created upstream. Read only the ones that already exist; never try to cause one (FR-060).
- **審査中 as a transition**: `POST …/review-start` exists in the API but has no UI control in the app or the prototype (integration-plan endpoint table). 審査中 is tested as a rendered / filterable / sortable / reviewable value on **pre-existing** rows only.
- **FR-S001 見学・体験 screens**: only the inbound pre-fill hand-off (FR-058) is in scope, and the visit screens are not integrated (D16). See §7.
- **FR-S002 / FR-S003 corporate and employee-discount enrolment**: removed by v5. Their absence is a positive assertion in unit D (FR-043).
- **A-01 member screens**: approval creates a member there. Assert the CRM side only: 会員ID, link presence and link target URL. The member page itself is still mock-backed on `dev` (integration-plan "Deviations"); do not judge its content. Since Round 2 the detail's PII reveal reads the A-01 **API** (`GET /api/v1/admin/members/{memberId}`): judge what C-01-01 renders from it, not the A-01 screen.
- **F-01 billing / real payment settlement**: the CRM shows statements about payment. Assert the wording only.
- **Blacklist master screens** (`specs/blacklist-management`): since Round 2 the BL card renders 「該当BLエントリの詳細を確認 →」 links to `/members/blacklist/<blacklistId>` (B5 done). The BL screen is still mock-backed and may show not-found: judge the link URL only, never the target page.
- **Y-01 staff/role master**, **G-01/G-02/G-03 plan / option / campaign masters**: they supply data and are **never edited** by this run (see §9).
- **FR-025a**: a source-comment obligation. Checked by code review, not by a TC row.

## 5. Coverage focus per unit

Added to, never a replacement for, `gen-testcases`' full coverage walk. **Every unit** also covers:

- **Real-API behaviours**: server validation beyond the client's, the error codes the screen can receive, 401 session expiry mid-action (sign out in another tab, then act: expect the shared re-login path, no silent data loss), server-enforced role/scope (direct URL, not just hidden buttons), real totals, persistence after reload **and** after re-login.
- **UI breakage under stress at 1024×768**: long and variable-length values in **every place they render**. For each value, use (a) a max-length full-width Japanese string, (b) an equally long unbroken ASCII token, (c) a long e-mail, (d) the longest enum/badge label. A validation message must quote the field's **exact label**. Values this run writes (applicant names, address, e-mail, memo, reasons, 紹介コード, card token) are created at max length by unit D or C. Master values (store / plan / campaign / option names) are **never edited**: use the longest name that already exists and say so in Notes. **Values newly rendered in Round 2** get the same treatment in every place they render: staff `displayName` (承認者 / 否認者 / 取り消し者 / timeline operator / 代理申請者), BL `reason`, the 一致条件 list, store / plan / campaign / option names (now read off API-098 rows), `cancelReason`, and the revealed e-mail / address.

**Unit A — List**

- **KPI is server-computed** (D5): 未審査 = `submitted` only (FR-004 as updated). BL要注意 = server count across all statuses (§4.2). Prove each by cross-checking against filtered totals: status = 未審査 with a wide date range; BL = 一致のみ with no status filter. Treatment switch at 0 vs ≥1 as two cases. KPI does not change with paging, page size or filters.
- **Counts come from the server**: result banner "filtered N / 全 M 件" uses `totalItems` / `totalAllItems`. Assert N matches the rows over all pages for a small filter, and M stays constant across filter changes.
- **Status sort is review-flow order** (FR-010): exact sequence asc and its exact reverse desc, across a page boundary.
- **Sort × filter × page** (FR-014): filter / search / sort / page-size change each return to page 1 (four cases); out-of-range page clamps; page sizes are exactly 25/50/100, default 50; `?limit=200` in the URL falls back to 50 (D4).
- **URL state** (D3): bookmark with status / route / BL / brand / store / date / sort params reloads to the same result. 自動承認済 vs 承認済 are distinct filters (`approvalMethod`).
- **Default 7-day range** (FR-007) computed against the execution clock; two-month Japanese calendar.

## 6. Case-marking rules for this feature

- **`known gap Bn → expect Block`** (Round 1 name: `known Round 1 gap Bn`): a case written to the spec whose behaviour the API cannot yet back. Recorded `Block (Bn)` while Bn is listed in §7. When Bn is done in Round 2, the case **drops** its Block guidance and becomes a normal OK/NG case, its expectation aligned with the shipped behaviour.
- **`Block (MR !nnn)`**: the FE is done, but the BE fix is merged-pending-deploy on dev (MR !643 / !644 / !646 / !648, §7). Re-smoke once the MR is on dev.
- **`[R1-fallback Bn]`**: a case that checks the **substitute UI** for blocker Bn: the 「—」 cell, the 「参考」 tag, the derived route, the JACCS toast. It runs **OK/NG**, so a broken fallback (crash, blank card, live control that loses input) is caught. When Bn is done (Round 2: B3, B5, B7, B9, B18 names; B8 closed; B1's disabled 手動 option), the case is **rewritten** into an `[R2]` case or **retired**. It is never left expecting UI that no longer exists (e.g. a 「API未対応」 tooltip). Cases of still-open blockers (B13 「参考」, B19 「—」, B20 toast) keep the marker.
- **`[R2]`**: a case added or rewritten for Round 2 behaviour. New cases take the next free ID in their doc; the marker goes in Remarks + Trace.
- **`[Retired R2 — <why>]`**: keep the row and ID (never renumber); expected result = "N/A — superseded by TC-xxx" so `execute-testcases` skips it. Clear stale result cells on retired rows only. Prefer rewriting into a useful `[R2]` case over retiring.
- **`[Spec-only]`** and **`[Decided: …]`**: see §4.1 and §4.2. A `[Decided]` case's expected result is the decided behaviour; its Notes quote the spec line it overrides.
- **`Block — data limitation`**: the shared dev data cannot reach the state and this run cannot create it (e.g. a companion applicant, a 審査中 row in scope, overdue boundary rows).
- **`Block — dependency …`**: a target screen of another, not-yet-integrated feature (FR-S001 pre-fill, A-01 member page content).
