## Screens

| Screen               | Route                                   | Prototype                | API (`/api/v1/admin/…`)                                                                             |
| -------------------- | --------------------------------------- | ------------------------ | --------------------------------------------------------------------------------------------------- |
| List                 | `/surveys`                              | `survey-list`            | `GET questionnaires`, `PATCH questionnaires/{id}/status`                                            |
| Create / Edit        | `/surveys/create`, `/surveys/[id]/edit` | `survey-form`            | `POST questionnaires`; `PUT questionnaires/{id}` (+ `PATCH …/status`); `GET questionnaire-triggers` |
| Detail               | `/surveys/[id]`                         | `survey-detail`          | `GET questionnaires/{id}`, `PATCH questionnaires/{id}/status`                                       |
| Store visibility     | `/surveys/[id]/visibility`              | `survey-visibility`      | `PUT questionnaires/{id}/questions/{questionId}/visibility`, `PUT …/choices/{choiceId}/visibility`  |
| Responses (付属画面) | `/surveys/responses`                    | `survey-responses`       | `GET questionnaire-responses`, `GET questionnaire-responses/export`                                 |
| Response detail      | `/surveys/responses/[responseId]`       | `survey-response-detail` | `GET questionnaires/{id}/responses/{answerId}`                                                      |
| Analytics (付属画面) | `/surveys/analytics`                    | `survey-analytics`       | `GET questionnaires/{id}/responses/aggregate`, `GET …/aggregate/export`                             |

Responses / analytics are not in the sidebar; they are reached from the list and detail headers (G-04 UI 設計方針). Exception — a **Trainer** cannot open the list (G-04 権限表: only 個別回答の参照 △), so the sidebar 商材・施策設定 parent and its アンケート管理 sub-item take the Trainer straight to `/surveys/responses` (`fallbackHrefs` in `app-sidebar.tsx`; decision 2026-11-03). Every other role keeps `/surveys`; Observer stays disabled.

## Requirements

### List (`/surveys`)

- **FR-L01** Header: title アンケート管理, **no count badge**. Actions: 回答データ, 集計分析, **新規登録** (permission-gated, create; deny tooltip アンケート作成の権限がありません).
- **FR-L02** Search by survey name (`nameQuery`); expandable 詳細フィルター with 種別 (ライフサイクル / オペレーション → `category`; URL `type`, `counseling` or any other value is ignored) / ブランド (brand **group**: すべてのブランド / JOYFIT / FIT365 → `brandGroup`; URL `brand=joyfit|fit365`, an unknown or stale value such as `brand=joyfit24` is ignored) / 状態 (有効 / 無効 → `status`) selects. An active select is highlighted (`border-primary bg-primary/10`). The filter button shows the count of active selects (search text not counted) in an outline badge.
- **FR-L03** `FilterResultBanner` sits **inside the Card between the filters and the table**; it carries the summary (`"search"・type・brand・status`) and the clear action. There is no separate すべてクリア button. Clearing does not reset page size or sort.
- **FR-L04** Columns, in order: ID (80, shows `code`), アンケート名, 種別, 発動トリガー (`triggerName`, falls back to `triggerCode`, `—` when none), ブランド (one badge per group: the four JOYFIT sub-brands collapse into one JOYFIT badge; any other stored sub-brand keeps its own badge, so a legacy partial set hides nothing; `—` when empty), 設問数, 回答件数, 回答率 (1 decimal, `—` when `null`), 最終回答日 (`YYYY/MM/DD`, `—` when none), 状態, actions. Sortable server-side (`sort` / `order`): all except 発動トリガー and ブランド. No sort is the default: nothing is sent and the API returns newest first (`createdAt` desc); a third click on a header clears the sort (back to that default); URL key → `sort`: `id→code`, `name`, `type→category`, `question_count→questionCount`, `response_count→responseCount`, `response_rate→responseRatePct`, `last_response_date→lastAnsweredAt`, `status`. No 配信数 column (not provided by API). A `counseling` row renders with the label カウンセリング even though the filter does not offer it.
- **FR-L05** Row actions 編集 / **無効化** on a 有効 row, 編集 / **有効化** on a 無効 row (no hard delete — the agreed off switch is `inactive`, qa-143; the same `PATCH …/status` turns it back on). 有効化 is not destructive (no `text-destructive`, CheckCircle2 icon). Both share one gate by type: オペレーション → survey edit / delete permission (badge 権限なし); ライフサイクル → Headquarter / System only (badge 本部).
- **FR-L06** 無効化 opens the same disable dialog as the detail screen (FR-D03), without its trigger button. Confirm sends `PATCH …/status` `{ status: 'inactive', reason? }`; success toast アンケートを無効化しました; a failure shows only the global toast (the server's `userMessage`, no screen-specific title); the list is refetched.
- **FR-L06a** 有効化 sends `PATCH …/status` `{ status: 'active' }` **directly, without a dialog** (nothing is lost; the prototype defines no copy for one). Success toast アンケートを有効化しました; the list and that survey's detail cache are refetched. A second active survey on the same trigger and an intersecting brand scope is refused with 409 `E-QST-010` (FR-F07 (2)): only the global toast shows the server's `userMessage`, the row stays 無効. Repeat clicks while the request is in flight send one request.
- **FR-L07** Empty state: `filtered` variant with 条件をクリア when filters are active, `empty` otherwise. Pagination footer always shown (no error); page-size options 25 / 50 / 100, default 50. A row click opens the detail by `questionnaireId`.

### Create / Edit (`/surveys/create`, `/surveys/[id]/edit`)

- **FR-F01** Basic info: アンケート名; 種別 (create: ライフサイクル only; edit: only the survey's stored category is offered, since the save carries no `category`); ブランド — a single required Select of the brand **group** JOYFIT / FIT365 (G-04: ブランド = the group), sent as the group's sub-brands in `brandEnums`: JOYFIT → `['Joyfit','Joyfit24','JoyfitYoga','JoyfitPlus']`, FIT365 → `['Fit365']`; **no default**, error `ブランドを選択してください`. On edit a stored set equal to a whole group (any order) shows that group; any other stored set (legacy `['Joyfit']`, `['Joyfit24']`, mixed groups) is appended as an extra option labelled with its sub-brands joined with `/` and is kept untouched until the operator picks a group (legacy data is never rewritten silently). 発動トリガー — options come from `GET /admin/questionnaire-triggers?triggerType=<種別>` (`code` → `name`), **no default**, error `発動トリガーを選択してください`; a stored code missing from the master shows the raw code.
- **FR-F02** Questions are cards: index, text input, move up / down, delete; format Select (placeholder `選択`; 単一選択 / 複数選択 / 自由記述) and a required toggle. New questions start with **no format** and **任意**. Choosing a choice format adds one empty choice row; 自由記述 sends no choices. The form never offers 評価（星） (FR-S002 ④, Phase 2): a stored `rating` question loads as 評価（星） with its format Select disabled, carries no choices, and is saved unchanged.
- **FR-F03** Deleting a question that has responses (`hasResponses`) opens `この設問を削除できません` with `非表示にする` (removes it from the form, toast `設問を非表示にしました`); otherwise `この設問を削除しますか？`. Either way the question is left out of the save body. The server retires a left-out question (`inactive`), answered or not: past answers are kept and still aggregate, nothing is deleted (G-04 FR-002 logical delete) — see Known gap 19.
- **FR-F04** Status switch 有効 / 無効. Edit shows the info banner (本部テンプレート…) above the existing warning.
- **FR-F05** Footer: `未入力の項目があります` after a failed submit; the first invalid field scrolls into view (the ≥ 1 question error and the choice-list error are rendered as invalid blocks so they are reached too). Back link `アンケート管理に戻る` and キャンセル both confirm discarding unsaved changes. Both create and edit return to the **list** after saving.
- **FR-F06** API-required validation kept (non-empty question text and format, choice text, ≥ 1 question) with inline errors.
- **FR-F07** Save. **Create** → `POST /admin/questionnaires` with `name`, `category`, `triggerCode`, `brandEnums`, `status`, `questions[]` (`text`, `format`, `required`, `choices[]`; array position is the order — no `displayOrder`); `code` is generated by the server. `brandEnums` stays the API's sub-brand list (1–5 unique): the form expands the picked group (FR-F01); the list / analytics / responses filters use `brandGroup` instead. **Edit** → `PUT /admin/questionnaires/{id}` (API-090 EP4b, one transaction / one history entry, **system / headquarter only**) with the `version` the form was loaded with (required; a stale one is refused with 409 `E-QST-016`, nothing is written — the toast shows the server message and the detail is refetched, which reloads the form with the new version; not in G-04, added by BE) and the whole form as the desired end state (existing questions / choices carry their `id`, new ones none; a left-out choice is retired; `category` and `status` are not part of it), then `PATCH …/status` only when the 有効 / 無効 switch changed. Success toasts アンケートを登録しました / アンケートの変更を保存しました. API errors show the server message (`resolveApiErrorMessage`) — notably 409 `E-QST-010` (another active survey already owns the trigger **and an intersecting brand scope**, API-090 §7.3: it conflicts when either side has no brand (= all brands) or the two brand sets share a sub-brand, so a JOYFIT and a FIT365 survey can both be active on one trigger). It is raised at three moments: (1) create as 有効; (2) the 無効 → 有効 switch (`PATCH …/status`, also from the detail / list re-activation); (3) an edit of an already-active survey that changes the trigger or the brand set (`PUT` on save). Editing only name / description / questions of an active survey, or editing an inactive one, is never checked. On a rejected `PUT` nothing is saved: the form keeps its values and shows the server message, with no `PATCH` status sent. Rule (3) is not written in API-090 §6.4 yet (BE behaviour, pending PO confirmation).

### Detail (`/surveys/[id]`)

- **FR-D01** Title with status badge with dot (有効 / 無効). 基本情報 ブランド shows the same group badges as the list (FR-L04). Header actions: 回答データ (HQ/System/Manager/Staff; a Trainer cannot open this page — it reads answers through `/surveys/responses`, reached from the sidebar アンケート管理, decision 2026-11-03), 集計分析 (HQ/System/Manager/Staff; opens analytics with `survey_id=<id>`), 店舗別表示設定 (Eye icon; HQ/System/Manager/Staff → visibility screen; deny tooltip 店舗別表示設定は本部・マネージャー・スタッフが操作できます), 編集 (gated like the list row: ライフサイクル → HQ/System, オペレーション → permission). **No 削除** (no hard delete, see FR-L05). Basic info shows 発動トリガー as `triggerName` (falls back to `triggerCode`).
- **FR-D02** No in-page store selector. The page follows the header's current store: all-stores shows the whole template with no scope text; a selected store hides the questions / choices whose `hiddenStoreIds` contains it and shows a scope sentence in the questions card header (hidden question / choice counts, or すべての設問・回答選択肢を使用), with the empty row この店舗で使う設問はありません.
- **FR-D03** Disable dialog (このアンケートを無効化しますか？) has an optional textarea labelled 無効化の理由（履歴に記録されます）, max **500** chars (`QnrStatusDto.reason`). The value is trimmed; empty is omitted from the request. The textarea is cleared every time the dialog opens.
- **FR-D04** Status card action follows the status: 有効 → 無効化する (opens the FR-D03 dialog); 無効 → **有効化する** (outline button, same gate as 無効化する: ライフサイクル → HQ / System with badge 本部, オペレーション → survey edit / delete permission with badge 権限なし). 有効化する behaves as FR-L06a (no dialog, toast アンケートを有効化しました, 409 `E-QST-010` → global toast only, button disabled while in flight); on success the status card, title badge and the list cache switch to 有効.

### Store visibility (`/surveys/[id]/visibility`)

- **FR-V01** Replaces the store selector / visibility card that used to live in the edit form. Uses the header's current store; shows a role notice for non-editors and `ヘッダーで対象店舗を選択` in the all-stores view. Questions and choices are listed by `displayOrder`; Q-numbers are the list position.
- **FR-V02** Each question and choice toggle saves immediately as **one request for this store only**: question → `PUT …/questions/{questionId}/visibility`, choice → `PUT …/choices/{choiceId}/visibility`, body `{ showStoreIds: [storeId] }` or `{ hideStoreIds: [storeId] }`; success toast names what changed; a failure shows only the global toast (the server's `userMessage`) and the switch falls back to the stored value; the detail query is refetched either way. All switches are disabled while a save is in flight. A question turned off collapses its choices; the last ON choice is locked with a tooltip.

### Responses list / detail

- **FR-R01** Filters: date range, ブランド (group: 全ブランド / JOYFIT / FIT365 → `brandGroup`, the group of the answering store; hidden for a Trainer), 店舗, 会員区分, テンプレート種別 (ライフサイクル / オペレーション → `category`; URL `template_type`, `counseling` or any other value is ignored), search. Active filters highlighted; banner inside the Card (summary excludes the search text); empty state offers the clear action only when conditions are active; no すべてクリア button; the filter count excludes search text and counts the date range once. Clearing keeps `survey_id` (the list stays scoped to the survey it was opened from).
- **FR-R02** 回答日時 shows date and time. Subtitle `対象: <アンケート名>`. Back link is `アンケート詳細に戻る` when a survey id is in the URL, else `アンケート管理に戻る` — the latter only when the user holds `Permission.SurveysView` (no back link for a Trainer, who would land on `/403`). 状態 column: 完了 / 未完了 / 辞退 / 回答中, derived from `responseStatus` (`declined`, `in_progress`) else `isComplete`. ブランド: the store master spelling (`JOYFIT`, `FIT365`, …) is normalised to the questionnaire spelling before rendering the badge.
- **FR-R03** CSV 出力 downloads `questionnaire-responses/export`; the file arrives without a BOM, so the client adds one for Excel. Toast CSVを出力しました.
- **FR-R04** A row opens `/surveys/responses/[answerId]?questionnaireId=<id>`; the detail needs both ids (`GET questionnaires/{id}/responses/{answerId}`). Without `questionnaireId` it shows 回答が見つかりません.
- **FR-R05** Detail: title `<会員名> の回答` with the status badge (same four statuses). Basic info: 会員番号, 会員名 (`lastName firstName`), アンケート名, アンケートID (`code`), ブランド, 店舗, 回答日時 (`submittedAt`, full date-time; also in the status card). Answers are listed by `displayOrder`: picked choices as badges, free text as a block, `rating` as its value; 未回答 when nothing was answered.

### Analytics

- **FR-A01** No count badge by the title; breadcrumb `アンケート管理 > 集計分析`. Filters: 期間 (全期間 / 今月 / 先月 / 過去3ヶ月 / 過去6ヶ月 / 過去1年 → `from` inclusive / `to` exclusive local-midnight instants), ブランド (group: 全ブランド / JOYFIT / FIT365 → `brandGroup`; the aggregate echoes `filters.brandGroup`), 店舗, 会員区分 (real member types), 入会後経過期間 (入会後全期間 / 入会後〜3ヶ月 / 入会後3〜6ヶ月 / 入会後6ヶ月〜1年 / 入会後1年以上 → `enrolledFrom` / `enrolledTo` as `YYYY-MM-DD` computed from today in JST; URL `tenure`), 性別 (全性別 / 男性 / 女性 → `gender`; URL `gender`), in that toolbar order; the CSV carries the same params (G-04 FR-S006). No テンプレート種別 filter (qa-148 §2). The toolbar also holds a questionnaire dropdown (FR-A02); it is a picker, not a filter, so it is not counted in the filter count and there is no name-search box.
- **FR-A02** The aggregate is per questionnaire, chosen with a dropdown (searchable select) at the start of the toolbar. The trigger shows the name of the selected questionnaire; opening it lists questionnaires (name + code), has a filter box 「アンケート名・コードで検索...」 (server-side `GET questionnaires?limit=20&nameQuery=…`), loads more on scroll, and shows 「該当するアンケートがありません」 when nothing matches. Choosing one writes `survey_id` to the URL and the aggregate follows. The target is the `survey_id` in the URL (carried in from the detail screen or picked here); without it the page aggregates the first questionnaire of the list (`GET questionnaires?page=1&limit=1`). There is no `search` URL parameter. すべてクリア resets the six filters and `survey_id` (back to the first questionnaire).
- **FR-A03** KPIs: 総回答数 = `submittedCount` (辞退 is not an answer), 回答率 = `responseRatePct` (1 decimal). Question cards are numbered by position; a retired question (`status: inactive`, removed from the form but still answered in the period) is listed after the active ones with a 無効 badge (FE decision, not in prototype); choice questions show bars per choice; a `rating` card shows the mean `avgRating` (1 decimal, `—` while unanswered) and `answeredCount`; free-text cards show the latest `samples` (date `YYYY/MM/DD`) and link 回答一覧で全件を見る → `/surveys/responses?survey_id=<id>`.
- **FR-A04** CSV出力 (export permission) downloads `…/aggregate/export` with the same filters, adds a BOM client-side, success toast 集計結果CSVをダウンロードしました, a failure shows only the global toast (the server's `userMessage`); disabled while no questionnaire is resolved.

## Removed (not in prototype / no API)

List count badge; list すべてクリア; analytics count badge; form store selector, form visibility card and its PUT on save; duplicate-trigger confirmation (`replace_existing_survey_id` — the server now rejects with `E-QST-010` per trigger and brand scope, see FR-F07); `use-survey-form` hook; detail `?storeId=` selector and the `店舗: {id}` / `（選択肢は非表示）` texts; form defaults of single-choice / required; **hard delete** — list row 削除, detail overflow 削除 and `survey-delete-dialog` (replaced by 無効化, qa-143); fixed 発動トリガー option list (now the trigger master); analytics テンプレート種別 filter.

## Known gaps (prototype vs API / app)

1. **下書き status** — in prototype, absent from the API status (`active|inactive`); no filter, label or badge. Needs BE.
2. ~~**Banner baseline「全 N 件中」**~~ — resolved (2026-10-23): both queries send `includeTotalAll=true` and the banner reads `pagination.totalAllItems` (no fallback to the filtered total when it is missing: `totalCount={null}` drops the prefix). List: N = every survey with all filters reset. Responses: N = the answers within the reader's role scope (staff: own stores, trainer: booked members' counseling answers) **for the survey the screen was opened from** when `survey_id` is present, all optional filters reset, whole scope otherwise. The CSV export does not carry the flag.
3. **Brands** — resolved 2026-10-26: G-04 and the prototype treat ブランド as the brand **group** (JOYFIT / FIT365), so the form, the list, the responses and the analytics filters all offer exactly those two. The API stores sub-brands (`brandEnums`, 5 values) and accepts `brandGroup=JOYFIT|FIT365` on the list, the response lists, the aggregate and their CSV exports (the group of the answering store for answers; `brandEnum` still works and, sent with `brandGroup`, intersects). A survey saved for JOYFIT stores all four JOYFIT sub-brands, so it shows under the JOYFIT group filter; legacy surveys that store one sub-brand (e.g. only `Joyfit24`) are still found by JOYFIT through the group. A Trainer is refused `brandGroup` (403 `E-AUTH-100`) like `brandEnum`, so the responses filter hides it for that role. The answer rows' ブランド badge still comes from the store's `brandEnum` (the payload carries no group); with the two local stores this is already JOYFIT / FIT365.
4. **Phase 2 UI** — オペレーション creation, 手動配信 / 条件トリガー, 評価 / NPS formats, 配信設定 card: not rendered. A `rating` answer that arrives anyway is shown as its value (評価（星）).
5. **Response filters** — decision (2026-10-23): the responses list does **not** get 状態 / 性別 / 入会後経過期間 filters. They are prototype-only (`survey-responses.tsx`) and outside G-04 FR-004, which lists only the period, ブランド, 店舗 and template type for the list (FR-R01 adds 会員区分); the API already accepts `responseStatus` / `gender` / `enrolledFrom` / `enrolledTo` on the list, so nothing blocks them if the client asks later. Member-type options stay limited to the API enum. (The 「この会員の回答履歴」 card on the response detail is built — `survey-response-history-card.tsx`, `GET /admin/questionnaire-responses?memberId=…`, 25 per page — and is no longer a gap.)
6. **Role-based access (Trainer / Observer)** and the 店舗 column in single-store view. (a) **Observer**: G-04 権限表 gives Observer × on every row and Observer is not in the 対象ユーザー list, so every `/surveys/**` → `/403` (`E-AUTH-100` from the API) is correct per spec, **not a gap** (the prototype lets Observer into list / detail and only blocks the response detail — the spec wins). (b) **Trainer**: the 担当予約者 scope is built in the BE (members with a booking on the trainer's schedule, `counseling` only; a detail outside the scope → 404 `E-QST-001`); the FE opens only `/surveys/responses` and `/surveys/responses/[responseId]` (`Permission.SurveysResponsesView`) ; the sidebar アンケート管理 (and its 商材・施策設定 parent) lands the Trainer on `/surveys/responses` (decision 2026-11-03, replacing the earlier direct-URL-only entry), and that screen shows no `アンケート管理に戻る` link; `/surveys`, `/surveys/[id]`, analytics and visibility stay `/403`, CSV stays refused. The prototype instead lets the Trainer into the list / detail, but survey-svc refuses both reads to a Trainer (`READ_ROLES`), so the spec + API win. Pending PO confirmation: counseling-only vs the member's whole lifecycle set, and whether past / cancelled bookings count. (c) Hiding the 店舗 column in single-store view — still not implemented (needs store-scope state).
7. **Question reorder** — prototype buttons are inert; kept working here (order is the array position of the body; no `displayOrder` is sent; decision pending).
8. **Response rate format** — 1 decimal (`0.0%`) vs prototype `0%`.
9. **Row permission** — operational rows use edit/delete permission rather than the prototype's literal `survey.create` (same underlying flag).
10. **Not run** — screens were verified by `tsc` and `eslint` only, not exercised in a browser.
11. **Prototype still shows 削除** on the list row and detail overflow; the app shows 無効化 per qa-143. Waiting for the prototype update.
12. **Disable reason length** — prototype allows 1000 chars, the contract (`QnrStatusDto.reason`) 500; the app uses 500.
13. **`counseling` category** — exists in the API data / enum (Phase 1 member-app counseling, APP-C-04 managed in G-04), absent from G-04's 種別 definition and the prototype's two labels. Rows render the label カウンセリング (pending the client's label, report QA #1); the list 種別 and responses テンプレート種別 filters do **not** offer it (decision 2026-11-03, G-04 FR-001 + prototype), so `counseling` rows are reached under すべての種別 only.
