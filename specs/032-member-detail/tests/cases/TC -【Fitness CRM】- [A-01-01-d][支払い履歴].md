# TC -【Fitness CRM】- [A-01-01-d][支払い履歴]

**Scope (Unit 5 of the [test plan](../test-plan.md))** — the **支払い履歴** (Payment history) tab of the member detail screen, `/members/{memberId}?tab=payment`: **入出金明細** (transaction ledger, with its 期間 / 種別 filters and pagination), **請求一覧** (billing list) and the right-column **支払いサマリー** (payment summary).

**Out of scope** — the head-up card, banners and 基本情報 (Unit 1), the header menus (Units 2–3), the other eight tabs (Units 4, 6–10), and the **F-01 売上管理** screens that produce this data (a case may assert a figure, never how F-01 produced it). The tab is read-only: there is no create / edit / delete flow, and this unit writes nothing to the backend.

**Re-authored 2026-09-24** from the phase-2 test plan. It replaces the 2026-07-29 mock-run version (members `M-000xx`, prototype `426a9b3` line numbers, "Unit 4"). TC ids are kept where the case survives, so earlier results and bug ids still resolve; see [Retired case ids](#retired-case-ids).

**Updated 2026-10-14** — 入出金明細's period Select gains 期間指定 + a date-range picker (tabs Amendment T12, `A-01 FR-009` 「日付・種別」): TC-008, 025, 112 rewritten; TC-125 – TC-145 added.

### Vocabulary the tester must match character-for-character

- **期間 filter**: `全期間` / `今月` / `先月` / `過去3ヶ月` / `過去6ヶ月` (default `全期間`)
- **種別 filter**: `全種別` / `売上` / `返金` (default `全種別`)
- **Ledger columns**: `日付` / `種別` / `内容` / `金額` / `決済方法` · **Billing columns**: `請求月` / `請求種別` / `金額` / `ステータス` / `請求日`
- **種別 badge**: `売上` default · `返金` secondary · **請求種別 badge**: `月次` default · `都度` outline
- **請求ステータス**: `入金済み` success · `確定` info · `未確定` warning · `未回収` destructive · `貸倒` destructive
- **Amounts**: `¥9,900` · refunds `-¥2,200` in destructive colour · **Dates**: `YYYY/MM/DD`, 請求月 `2026年4月`
- **Empty states**: `入出金履歴はありません` · `請求履歴はありません` · filtered `該当する履歴はありません`
- **Summary**: title `支払いサマリー（<期間>）`; items `売上合計` / `返金合計` / `差引合計` / `最終入金日` / `決済方法`

### Data limitations

1. Long / full-width / unbroken / markup 内容, long 決済方法 labels, 7-digit amounts, ¥0 and null amounts, rows on the period cutoff date and unknown statuses can only come from existing F-01 data → the affected cases are `Block (fixture)` unless such data exists; ask BE to seed them if the gap matters.
2. The period windows use the **real** date in JST — compute 今月 / 先月 / cutoffs at run time.
3. Request failures (TC-087 – TC-090, TC-112) are forced with DevTools / Playwright request blocking on the one endpoint; the backend is not touched.
