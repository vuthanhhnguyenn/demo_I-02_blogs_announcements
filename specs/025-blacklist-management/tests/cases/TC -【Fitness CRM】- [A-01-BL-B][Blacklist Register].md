# TC -【Fitness CRM】- [A-01-BL-B][Blacklist Register]

**Unit B** of the Blacklist Management test plan — the ブラックリスト手動登録 Sheet opened from the list's 手動登録 button, including its member-number lookup, member-search combobox, identity card, reason/memo inputs and registration.

**Scope**: Sheet contents and layout, the two lookup paths and the identity card, 登録理由 / メモ, the 登録 gate and submission, duplicate guards, reset on close, layout at 1024px, real-API behaviour of the registration and lookup requests.

**Explicitly out of scope** (per [test-plan.md](../test-plan.md) §1):

- The list's table, filters and pagination → Unit A (a new row is only checked here for appearance).
- Detail and release → Unit C. The member detail's own BL dialog → Unit D.
- A-01 FR-018 data deletion itself — only its warning copy (FR-045) is tested.
- Selecting the registration path — not offered by design (FR-049).

## Test-data reference & limitations

- **Throw-away members (PC-G)** are the main data: one per registering case — about **19** are needed if every registering case is run (cases marked with a `QA-BL-<yyyymmdd>-<n>` data value). Create them via the application flow before the run and keep the list. Registration cannot be repeated for the same member without a release (Unit C).
- **Pre-existing blacklisted members** are used **read-only** (duplicate pre-check, withdrawn-member lookup). Never submit the Sheet for them.
- Members without a photo / birthdate: application-flow members normally have neither — good for the fallback case.
- Prefix search needs members whose name, kana, phone and e-mail are known: create the throw-away members with known values and reuse them.
- Real `E-MEM-001` / `E-AUTH-100` cannot be produced from the UI on the shared backend → route-faked (PC-E); real twins are `Block` ("cannot remove a member / denied roles cannot open the Sheet").
- Created entries stay active until released: hand the list of `QA-BL-` entries to Unit C (release them there) or note them as left.
