# TC -【Fitness CRM】- [A-01-BL-D][Blacklist Register Caller]

**Unit D** of the Blacklist Management test plan — a **contract regression** on the member detail's ブラックリスト登録 dialog (`/members/{memberId}`). The blacklist feature re-contracts the registration endpoint, so it carries the mechanical update of the endpoint's second caller (FR-073 – FR-075). The only question is: does this caller still work against the real endpoint with its visible behaviour unchanged?

**Scope**: reachability and role gate of the dialog, the dialog's current content and gating, registration for every reason against the real endpoint (request shape), the resulting entry, duplicate and error handling, layout at 1024px.

**Explicitly out of scope** (per [test-plan.md](../test-plan.md) §1):

- Everything else on the member detail `A-01-01` — tabs, cards, other menu items, the 強制退会 flow, the personal-data-deletion block (「ブラックリスト登録者のため削除できません」, A-01 FR-018). Only observed, never judged here.
- Changing this dialog: every case asserts **no change**. Do **not** import the list Sheet's copy, field set or submit gate (the Sheet gates on a resolved member and has the FR-050a pre-check; this dialog gates on the reason).
- The blacklist list, the Sheet and the detail → Units A, B, C.

## Test-data reference & limitations

- **Throw-away members (PC-G)**: one per registering case — about **15** (`QA-BL-<yyyymmdd>-D1 … D15`), created through the application flow. They stay 仮 and carry no blacklist entry until the case registers them.
- **Never submit the dialog for a pre-existing blacklisted member** — a missing server guard would create a duplicate on real data. Duplicate cases first register a `QA-BL-` member through the Sheet.
- The member detail must be reachable for the throw-away member in the signed-in role's scope (HQ/System: all).
- Created entries stay active until released (Unit C) — list them for cleanup.
- Removal of the old list-scoped route (FR-075) is only observable through requests; the code-level confirmation is a review note.
