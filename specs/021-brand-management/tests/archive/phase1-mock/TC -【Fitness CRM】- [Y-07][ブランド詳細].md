# TC -【Fitness CRM】- [Y-07][ブランド詳細] (Brand Detail)

**Scope**: Unit 2 of `specs/021-brand-management/tests/test-plan.md` — ブランド詳細 (Brand Detail) screen, route `/brands/[id]`, covering all three tabs (基本情報／費用／変更履歴), the fee edit Sheet, the disable/delete confirmation dialogs, and the Trainer/Observer access-denied state — all conditional UI within this single route. The ブランド一覧 (Brand List) screen, its search, and its brand-name edit Sheet are covered by Unit 1 (`TC -【Fitness CRM】- [Y-07][ブランド一覧].md`) and are out of scope here except as a navigation entry point.

## Source note

Sources used: `specs/021-brand-management/spec.md`, `.cache/fitness-spec/crm/requirements/Y-07.md`, `.cache/fitness-crm-ui/src/pages/brand-detail.tsx`, and the supporting mockup components it composes (`role-gated-button.tsx`, `status-card.tsx`, `page-header.tsx`, `back-link.tsx`, `field-marker.tsx`). All present and readable; no sources were missing for this unit.

**Discrepancies / open questions flagged** (raise to PO, not to log as `NG` on their own):

1. The reviewed mockup's `CHANGE_HISTORY` array is a single flat list not filtered by brand/sub-brand — the same 3 entries (all targeting "JOYFIT / JOYFIT24") appear to render regardless of which brand's detail page is open. The spec (FR-013) implies a per-brand log. TC-010 and TC-058/059 test the rendering of the entries as designed; if the real app doesn't scope history to the open brand, that is a genuine defect, not just a mock-data artifact — confirm which.
2. Every fee card in the mockup renders an identical, static "キャンセルポリシー" (cancellation policy) alert block that is not mentioned anywhere in `spec.md` or `Y-07.md` and reads as unrelated to brand/fee-master maintenance (it describes a membership cancellation window). TC-028 flags this as a content-accuracy question for the PO — confirm whether it's an intentional shared component or stray content from another feature.
3. The reviewed `FeeItemSection`/`RevisionRow` mockup code only shows an HTML `min={0}` attribute on the amount `<input type="number">` and no visible blocking validation message for a blank/negative/non-integer amount or a blank effective date. FR-009 requires an explicit validation message. TC-043/044/045 are written to the spec's requirement; note in each case that the mockup itself doesn't demonstrate the message, so confirm the running app actually surfaces one rather than relying on the native input's silent constraint.
4. Neither the spec nor the mockup defines an empty-state message for the 変更履歴 tab when a brand has zero history entries (unlike the 費用 tab, which has an explicit empty state per FR-014). TC-060 is marked `Block` pending this clarification.
