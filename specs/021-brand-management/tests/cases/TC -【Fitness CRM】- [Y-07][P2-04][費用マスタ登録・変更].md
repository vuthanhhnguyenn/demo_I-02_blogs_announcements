# TC -【Fitness CRM】- [Y-07][P2-04][費用マスタ登録・変更]

**Unit 4 of 5** in [`../test-plan.md`](../test-plan.md). These are Phase 2 (real-API) cases for the **費用マスタ Sheet** on `/brands/[brandGroup]` (費用 tab), in both of its modes:

- **変更 mode**: opened from a registered card's 変更 button. It covers the prefill, the fixed 費用項目名, 現行設定, adding/editing/removing 予約中の改定 rows, the 20-row cap, the live プレビュー, the past-date warning, validation, and the save (`PATCH …/fees`).
- **登録 mode**: opened from ［＋登録］ on a 未登録 slot. It saves with `POST …/fee-master`.

**Out of scope here** (other units own them):

- the fee-card display, the ⋯ menu, the 無効化 / 削除 dialogs and 有効化 (Unit 3)
- the 変更履歴 rows these writes produce (Unit 5, checked against this doc's write log)
- ブランド編集 (Units 1/2; used here only to set up the long-name window)

Everything in the plan's global **Out of scope** list also applies: no brand create, no sub-brand edit, no B6 editor, no ADD-09, and no auto-cutover batch beyond its caption.

**Δ ids covered**: Δ4, Δ5, Δ7, Δ8, Δ9, Δ10, Δ11, Δ12, Δ13, Δ18 (Δ2 for routes only).
**Known-gap / decision ids covered**: B1 (closed, so a failure is a regression), D12, D13, G3, NL-1, P1, R2-D2, R2-D3, R2-D4, R2-D5, R2-D6, R2-D8. **No open `Bn` blocker applies to this unit.** `Block` is expected only as `Block (DATA)`, where the data policy prevents a case, and when Unit 3's precondition (PC-I) is missing.

**Prototype ↔ spec conflicts** (each is flagged in the case's Notes):

- **[Conflict-1] Duplicate date.** The prototype's `RevisionRow` shows the duplicate alert, but `handleSaveFeeEdit` / `validateRevisions` do **not** block the save. Spec FR-009 / SC-002 / G-05 FR-008 and Δ12(c) require the save to be blocked. The case follows the spec: blocked (TC-035).
- **[Conflict-2] e-notation.** The prototype's `parseFeeAmount` uses `Number(raw)`, so `1e3` parses to `1000` and passes. Δ13 requires a rejection. The case follows Δ13 (TC-028, TC-040).
- **[Conflict-3] Invalid-amount message.**
  - The prototype's 「定価は0円以上の整数で入力してください」 omits the field's label.
  - Δ13 and the label rule require 「定価（税込）」 in the message, so the expected text is **「定価（税込）は0円以上の整数で入力してください」**.
  - Any wording that names 「定価（税込）」 with the same meaning is `OK`. A message starting 「定価は…」 is `NG` (TC-026).
- **[Prototype-only] Empty-amount preview.** While 定価 is empty, the prototype's preview shows `¥0` (`currentAmount ?? 0`). The spec says nothing about this, so it is not enforced (TC-018, TC-079).
- **[Prototype-only] No success toast in 変更 mode.** The prototype shows no toast on a 変更 save. On 登録 it shows 「「{card}」の費用マスタを登録しました」. The spec is silent on both (TC-056, TC-086).
- **[Spec-only]**: none in this unit. Every requirement mapped here has a prototype control. The BE date and size rules (Δ11, Δ12) come from the integration decisions and are judged against the plan's "How to test" column.

## Validation-label rule (applies to every validation case)

- Each message renders **directly under its own field**, inside that field's column. It never appears under the neighbouring field, and never only in a toast.
- The message names the field by its **exact on-screen label**:

| Field (both items, the 現行 row and every 予約 row) | Label on screen                  | Empty                              | Invalid value                                                                                                                                                                                                                                                       | Other                                                                                                                            |
| --------------------------------------------------- | -------------------------------- | ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| 定価                                                | 「定価（税込）」 + required mark | 「定価（税込）を入力してください」 | 「定価（税込）は0円以上の整数で入力してください」 (Conflict-3). Above 2,147,483,647 → 「定価（税込）は2,147,483,647以下で入力してください」 (Y-07 - Bug No.1)                                                                                                       | Server `E-VAL-001` `invalid_format` → one Japanese toast (R2-D5)                                                                 |
| 有効開始日 (現行)                                   | 「有効開始日」 + required mark   | 「有効開始日を入力してください」   | A future date → 「将来日付は「予約中の改定」に登録してください」 (Δ11)                                                                                                                                                                                              | Changed to a past date → the non-blocking warning 「過去の日付が指定されています。登録は可能ですが、即座に適用が開始されます。」 |
| 有効開始日 (予約 row)                               | 「有効開始日」 + required mark   | 「有効開始日を入力してください」   | Duplicate within the same item → 「有効開始日が重複しています。別の日付を指定してください。」<br>Past and not after the 現行 start → a Japanese message tied to this row's 有効開始日. The wording is unspecified, but no API key (e.g. `effectiveFrom`) may appear | Past but after the 現行 start → the same warning as above                                                                        |

- Item ① and item ② have identically labelled fields, so **errors must land on the item that is wrong**. The multi-error case triggers both items at once (TC-032).
- A server error must be mapped to Japanese. Any of these on screen is `NG` (app-wide rule since `e7da69de`):
  - a raw English BE message
  - an `E-XXX-nnn` code on its own
  - an API key (`priceInclTax`, `scheduledChanges`, `effectiveFrom`)
