## Phase 2 execution context (binding — from the test plan's Data policy)

- **R-0. Real master data.** The backend has exactly two brands, **JOYFIT** and **FIT365**, shared with other people. No case can create a throw-away brand. Any case may read them.
- **R-1. Rename only JOYFIT**, only to values prefixed **`ZZQA_`** (or **`ＺＺＱＡ`** for the full-width fixture). **Restore to exactly `JOYFIT` in the same case.** The restore is a **numbered step** in each write case, not a cleanup note. Keep the renamed window to minutes. **Never rename FIT365.** FIT365 is opened read-only (Sheet opened, then キャンセル).
- **Long-name window.** The stress cases (TC-059, TC-060, TC-078–TC-083) and the long-name places of Units 2–4 run in **one** renamed window (plan Suggested Order step 6): rename JOYFIT to F-JP100, walk every place, rename to F-TOK100, walk every place, restore.
- **R-5. Write log.** Every write case appends one line per write to **Write log** at the end of this doc: `time · account · action · target · before → after`. Unit 5 checks each line against 変更履歴. History rows are permanent by design.
- **R-7. No residue.** If a run stops mid-case, rename JOYFIT back to `JOYFIT` and note it.
- **Baseline snapshot** before the first case: the two brand names as the server returns them (expected `JOYFIT` / `FIT365`). Restores are checked against it. A value that changed between two cases may be another user's write. Re-read it before recording `NG`.
- **Error-language rule** (app-wide since `e7da69de`): every error the operator sees must be **Japanese**. A raw English BE message or an API field key (`displayName`) on screen is an `NG`.
- **Account safety.** Real Cognito accounts lock for ~15 min after repeated wrong passwords. This doc has **no wrong-password case**. 401 cases clear or expire the session token; they never use failed sign-ins.
- **Viewport.** 1024×768 for every layout and stress case; ≥1440px for the wide re-check. Below 1024px is out of scope.
- **Known-gap policy.** A failure matching **D4** → `Block (D4)`. A case the data policy forbids → `Block (DATA)`. Behaviour matching a Δ row's "How to test" is `OK` even where it differs from the prototype.

## Validation-label rule (binding for every message in this unit)

Every validation or error message must **name the field by its exact on-screen label**: **「ブランド名」**. Concretely:

- Empty / whitespace-only → 「ブランド名を入力してください」 (prototype copy, verbatim).
- Over 100 characters → a Japanese message containing 「ブランド名」 and the limit (e.g. 「ブランド名は100文字以内で入力してください」; the exact wording is unspecified, so only the label and the language are asserted).
- A server-side rejection surfaced in the UI → Japanese, names 「ブランド名」. **Never** the API key `displayName`, the English BE message, a raw JSON body, or a generic message with no field name when the error is field-specific.
- A message that omits the label, uses a different label (e.g. 「名前」, 「表示名」), or is English is an `NG`.
