## Guiding principle

**UI first.** Where the real API cannot back a UI element, the element stays as it is today:
rendered, disabled with a short 「API未対応」 note where leaving it live would lose input, and
the injection point carries a `TODO(round2)` comment naming the blocker. No UI is deleted to fit
the API. The two exceptions in this feature are **spec-driven removals**, not API-driven ones:
the two notification checkboxes (FR-006-01 / FR-008-01) and the memo author line (FR-011-01)
were reworded in `spec.md` (Clarifications 2026-10-07) because D-01 itself does not have them.

Mock routes under `src/app/api/crm/lesson-schedules/**`, the mock Zod schemas in
`src/app/api/_schemas/lesson-reservation.schema.ts` / `lesson-schedule.schema.ts`, and the
mock-db tables/seeds are **left untouched** (same convention as positions / staffs / domains).
They stop being called by this screen's API-113 surface; the API-112 dialogs keep calling them.

## Decisions

- **D1 — Entry point.** The lesson-schedules list stays on mock, so its links carry mock ids. Round 1 is tested by opening `/lesson-schedules/{uuid}/reservations` with a real dev schedule UUID. The list's read is not moved (API-112 territory).
- **D2 — Manual-create body.** Per member: `lessonScheduleId`, `memberId`, `statusOnCreate: 'reserved'`, and
  - `paymentType: 'monthly_plan'` + `optionContractId` when `lesson.feeType === 'monthly_plan'` and the member's `lesson-remaining.contracts[]` has an entry with `effectiveRemaining > 0` (highest `effectiveRemaining` wins when several);
  - otherwise `paymentType: 'per_use'`, with `feeCharged: 0` only when `lesson.fee` is null (free lesson, B2) and omitted otherwise so the BE snapshots `lessons.fee`;
  - `studioSeatId` for `lessonType === 'studio'` only: the chosen seat, or for 自動割り当て the first `seats[]` cell with `seatType === 'normal'` and `bookingStatus === null` (a `pending` hold has `bookingId === null` but `bookingStatus === 'pending'` and is not free), taking the next free cell per member in the same batch;
  - never `trial`, never `isTrial`; `notes` only when the operator typed a 備考 (R501, 2026-10-09 — FR-006 入力項目, API-113 §7.1 max 2,000; one note per batch, written on every booking of that submit).
    The BE month-allowance rule (§6.1 #6) is authoritative: a 422 `E-LSB-006` / `E-LSB-009` / `E-LSB-010` on one member leaves that member's chip in the list and the dialog open; members that succeeded are removed from the chip list. `feeType === 'monthly_plan'` with no qualifying contract is the existing 残回数が不足しています block (no request).
- **D3 — Trainer own-session scope.** `isOwnSessionScope(user, scheduleLoaded)`: non-Trainer → `true`; Trainer → `true` once `GET /lesson-schedules/{id}` succeeded, `false` when it failed with 404 `E-LSC-001` (mapped to the existing `/403` redirect). The `instructor_id` comparison is deleted. `scopedManageRoles` is unchanged.
- **D4 — Penalty source.** The add dialog reads `lesson-remaining.activePenalty` (`{ penaltyType, endAt }`), filtered to `penaltyType === lesson.lessonType`, for the 予約不可期間中 block. `activePenalties` is never read. On a 422 `E-LSB-007` the end date is not parsed from `details`; the shared toast shows `userMessage`, which already names the date.
- **D5 — No mapper layer for API-113 data.** Components take `LessonBookingListItemDto`, `BookingStatsResponseDto`, `LessonBookingSeatStatusDto`, `LimitedMemberProfileResponseDto`, `SessionMemoResponseDto` directly from `@/lib/api-real/types.gen`; renames happen in place. Label maps move to `_constants/booking-status.constants.ts` with the 7-value enum (`reserved` 予約済, `pending` 仮予約, `attended` 出席確認済, `no_show` 無断キャンセル, the three `cancelled_by_*` キャンセル済) and a type-level assertion against the DTO's `status` union so a BE enum change fails `tsc`.
- **D6 — Attendance column.** Derived from `status`: `attended` → 出席確認済, `no_show` → 無断欠席, anything else → 未確認. The three dropdown items call attend / no-show / revert-attendance; a 422 `E-LSB-013` (e.g. 無断キャンセル before the session starts, or on a non-`reserved` booking) surfaces through the shared toast.
- **D7 — One adapter seam for the API-112 dialogs.** `_utils/legacy-schedule.util.ts` exports `toLegacyScheduleItem(detail, history)` building the mock `LessonScheduleListItem` shape the four API-112 components expect (`lesson_name`, `lesson_type` (`personal_training` → `'personal'`), `start_time`, `end_time`, `studio_name`, `instructor_id`/`instructor_name` (first `trainerRows[]` entry), `capacity`, `booked_count = reserved + pending + attended` (D-01 spec: `bookedCount` is not a spec key), `status`, `cancelled_at`/`cancelled_by` (from the history `cancelled` entry), `cancel_reason`, `cancel_reason_detail`). One `TODO(api-112)` comment; the API-112 integration deletes the file and retypes the dialog props.
- **D8 (Rounds 1–3, superseded by D16) — API-112 writes stay on mock and stay live.** Their mutations will 404 on the mock routes with a UUID and the shared toast reports it; no input is lost silently, so they are not disabled. `getCrmLessonSchedulesQueryKey` invalidations in those dialogs are left as they are.
- **D9 — Counts.** Header badge and stats 予約数 use `booking-stats.confirmed` (= reserved + attended, §4.3) plus `pending` for the 予約済 figure; 残り席 uses `available` (the §6.6 trial-mode formula) — the client never recomputes it. The grid footer keeps counting from `seats[]`. `{total}件` uses `pagination.totalItems`; no baseline query is needed because the list has no filters.
- **D10 — Pagination.** `limit: 7` (within the API's 1–100), `page` from nuqs as today. Sorting stays client-side over the page (unchanged behaviour); the server order is `createdAt asc` so row numbers are stable across reloads.
- **D11 — Memo card shape.** One entry: date = `updatedAt` (M/D(曜)), content, delete button. PT form keeps joining its five fields into one string (spec §5.2). Save = POST when the GET returned 404 `E-LSB-030`, PATCH with `expectedUpdatedAt` otherwise; a 409 `E-LSB-017` / `E-LSB-031` surfaces via the shared toast and refetches. Optimistic insert/rollback is removed (the memo is a single server value; a refetch is cheaper and cannot desync). Length cap from `lessonType`: PT 10,000 / studio 5,000 replaces `TEXTAREA_MAX_LENGTH` for the memo field.
- **D12 — Limited profile.** Fetched lazily on popover open / PT card mount, with `enabled` only while open. `visit_frequency` is rendered as `直近30日 {visitsLast30Days}回` and 最終来館 from `lastVisitAt`; lesson history maps `status === 'attended'` → 出席, else 欠席; body data from `bodyData` (hidden when `hasBodyDataConsent` is false or `bodyData` is null, with a one-line 本人の同意なし note); `sex` gets labels for `other` / `unknown`; `facePhotoUrl` replaces the initial avatar when present. An Observer gets 403 `E-LSB-101` → the popover shows 閲覧権限がありません instead of the profile.
- **D13 — Errors by code.** Every mapping reads `ErrorResponseDto.code`; no Japanese substring matching. Local `onError: toast.error(...)` on the migrated mutations is deleted (shared `MutationCache` already toasts). Success toasts stay.
- **D14 — Invalidation.** Every booking write invalidates the booking list, booking-stats and (for memo) the memo query together, fixing today's stale header/grid after add / cancel / attendance.
- **D15 — Deep links.** The grid popover's 予約取消 looks the booking up by `bookingId` across the loaded page only (as today); when the booking is on another page the popover falls back to a detail fetch (`adminLessonBookingControllerDetailOptions`) so the cancel dialog still opens.

- **D16 — API-112 writes are integrated in this MR (Round 4).** quyndh's MR !194 covered the same dialogs but is being closed; nothing is merged from it. This branch wires `reservation-page-actions.tsx`, `change-instructor-dialog.tsx`, `change-time-dialog.tsx`, `change-studio-dialog.tsx` and `cancel-lesson-wizard.tsx` onto `PATCH /lesson-schedules/{id}`, `POST …/cancel`, `POST …/cancel-from-here` directly, following the same rules as the API-113 writes (D13 errors by code, D14 invalidation, shared toast, no local `onError`). The D7 legacy-item seam and `session-scope.util.ts` shim are deleted: the dialogs take `LessonScheduleDetailDto` (+ `recurrence`) as props. Seed option: `origin/feat/lesson-schedule-detail-integration-api` still exists — commit `ae5bef7f` may be cherry-picked as a starting point for the dialog bodies and then adapted, but the plan below does not depend on it.
