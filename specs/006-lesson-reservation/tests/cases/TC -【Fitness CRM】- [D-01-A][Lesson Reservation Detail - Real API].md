# Test Cases: Lesson Reservation Detail (D-01-A) — Round 1 (real API-113)

> Driven by [test-plan.md](../test-plan.md), unit 1 "Reservation Detail — read + profile". Covers the single `/lesson-schedules/[id]/reservations` screen's read surface: page header, space grid + legend + cell popover, reservation list + pagination, 予約統計, レッスン情報, the cancelled-schedule card, the member limited-profile popover, the PT limited-profile card and the session memo card. **Unit 2** (add / cancel / attendance writes) is a separate doc. The API-112 schedule-write dialogs are out of scope (still mock).

## ⚠️ Data-safety rule — read before executing

The dev backend (`https://api.dev.fitness-v2.okamoto-hd.com`) is real, shared and never reset.

- **Read-only on seeded schedules** (`…a401`, `…a301`, `…a405`, `…a11681`): open, scroll, open popovers. Do **not** save or delete a memo there, do not cancel or add bookings there, never run the API-112 dialogs there.
- **All writes in this doc (memo create / replace / delete, long-value fixtures, the Trainer assignment) go to records this run creates**, prefixed `QA-D01-`: a published future studio schedule, a PT schedule, a lesson with a 100-char name, a member with a 20-char name. Bookings on them are created by unit 2 (or by the same run before unit 1's pagination / badge cases).
- If a case would need a seeded record to be modified, mark it `Block — no fixture` instead of improvising.
