# Test Cases: Lesson Reservation Booking Writes (D-01-B) — Round 1 (real API-113)

> Driven by [test-plan.md](../test-plan.md), unit 2 "Reservation Detail — booking writes". Covers the write surface of `/lesson-schedules/[id]/reservations`: the 予約を追加する dialog (member search, eligibility pre-checks, seat select, chips, confirm), the 予約をキャンセル dialog (row 取消 and grid-popover 予約取消) and the 出席 attendance dropdown. Read surface = unit 1 (D-01-A). API-112 schedule-write dialogs are out of scope (still mock).

## ⚠️ Data-safety rule — read before executing

The dev backend is real, shared and never reset.

- **Every booking, cancellation and attendance change in this doc targets records this run creates** under the `QA-D01-` prefix: a published future studio schedule on a per-use lesson, one on a monthly-plan lesson, one PT schedule, one unpublished schedule, and QA members A–E (plus a 20-char-name member and, optionally, a markup-name member). Create them before TC-001; most dev seeds are **unpublished** and refuse manual booking by design.
- Never add, cancel or change attendance on the seeded schedules (`…a401`, `…a301`, `…a405`, `…a11681`). The only seeded interaction allowed here is **looking** at `…a405` as Observer and `…a11681` for disabled controls.
- Attendance changes need a schedule whose start time has passed; create a QA schedule dated in the past (or wait past the start) for TC-058…TC-067 — never use a seeded past schedule.
- Finish with the cleanup case (last row).
