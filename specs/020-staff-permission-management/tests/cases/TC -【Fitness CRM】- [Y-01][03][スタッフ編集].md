### Source note

All four sources were readable — no `Block`-by-missing-source cases in this document.

- `specs/020-staff-permission-management/spec.md` — User Story 3 (Acceptance Scenarios 1–7), Edge Cases (affiliation re-switching, trainer/observer view-only note under US4 — referenced only as contrast), FR-012, FR-013, FR-014, FR-015, FR-016, FR-017, FR-022, Assumptions.
- `.cache/fitness-spec/crm/requirements/Y-01.md` — 6-role table, 3-層権限構造, 職位マスター table, スタッフの紐づき構造 (Pattern A/B), FR-003/FR-005/FR-007/FR-008 text, 権限マトリクス (row `スタッフアカウント作成`/`ロール付与・変更`/`職位割り当て`/`店舗・FC企業紐づけ設定` all `Manager=×` except 職位割り当て which is `Manager=○ 担当店舗分`).
- `.cache/fitness-crm-ui/src/pages/staff-form.tsx` (`mode="edit"` branch) — `EDIT_DATA` sample record, `canChangeRole` gate, role-change confirmation `AlertDialog`, `PositionCombobox`, affiliation radio + `handleAffiliationTypeChange`, email duplicate-check button, discard-guard `AlertDialog`.
- `tests/checklists/common-function-checklist.md` and `tests/checklists/common-gui-validate-checklist.md`.

**⚠️ Important gap flagged up front** (affects TC-045–TC-047 below): the reviewed `staff-form.tsx` edit-mode branch renders the entire form unconditionally — there is no code path that checks `user.role` / managed-store scope against the target account before allowing the form to open or submit. The **only** role-based gate implemented anywhere in this component is the `canChangeRole` check on the **role select field alone** (disabled + tooltip for non-HQ users). FR-013's whole-form restriction ("a manager can edit only 'Staff'-role accounts affiliated with a store they manage; all other roles cannot edit accounts... via this screen") and US3 Acceptance Scenario 4's "blocked with an explanation" have **no visible mockup implementation** to ground a UI-detail assertion on. Per Test Philosophy #1, these cases are written to the requirement doc's/spec's stated intent, but their Notes call out that the mockup shows no such gating — a real app implementing only the role-select-level gate observed here would be a genuine FR-013 defect, not a tester mistake.

### Checklist gap fixed first

Two gaps found while authoring this unit, fixed in the shared checklists (per the checklist-first rule) before expanding into the cases below:

1. `common-gui-validate-checklist.md` → **Dialog / Confirmation Message**: added a row for a save/update flow where confirmation is required only when one specific _governed_ field actually changes (e.g. role), not for edits to any other field — distinct from the existing "long value" / "branching content" dialog rows, neither of which captured this "conditional on one field's before/after diff" pattern. Expanded into TC-020–TC-026.
2. `common-function-checklist.md` → **Update (Edit)**: added a row for editing a record restricted by a business rule beyond a blanket view/edit permission (record-attribute-gated edit access with an explanation on block), distinct from the existing blanket "no view permission → 404" row in Other Cases. Expanded into TC-045–TC-047.
