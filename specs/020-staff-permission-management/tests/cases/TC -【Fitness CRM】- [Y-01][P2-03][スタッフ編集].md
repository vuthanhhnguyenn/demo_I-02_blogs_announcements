# TC -【Fitness CRM】- [Y-01][P2-03][スタッフ編集]

**Unit 3 of 5** — Phase 2 (real-API integration) test cases for the staff edit screen (スタッフ編集), route `/staffs/[id]/edit`.

**Scope**: the edit form only — its 基本情報 (name, email + duplicate check), 権限設定 (role + position), 所属設定 (affiliation pattern and selector), 備考, the role-change confirmation dialog, the footer actions and the unsaved-changes guard. Reaching the form (the list's row action, the detail screen's 編集 button) is verified only as far as "the form opens for the right account"; those entry points' own gating belongs to Units 1 and 4.

**Out of scope** (per the test plan): 職位マスター管理 (`/positions` — the source of 職位 names only); Y-02 店舗管理 / Y-03 FC企業管理 master screens; `PUT /admin/staff/{id}/managed-stores`, which no screen drives; the account-lifecycle actions (無効化 / 有効化 / 削除 / マジックリンク), which live on the list and detail screens (Units 1 and 4).

## ⚠️ Read first — two contract gaps define this unit

> **UPDATE 2026-11-04 (Y-01 - Bug No.16) — the email half is closed.** `UpdateStaffRequestDto` now carries `email` (API-070 v0.11.1 §6.5.3) and `StaffDetailDto` carries `authProvider`. The email input is editable unless the target is a Google-route staff; `email` is sent only when changed; the FE does not re-invite (backend's job). See `spec.md` › "Email change on the edit screen". TC-025–TC-029 and TC-063 were re-specified and TC-073–TC-078 added; the contract-gap grading below now applies to `role` only.

> **UPDATE 2026-11-05 (Y-01 - Bug No.19) — the role half is closed too.** `UpdateStaffRequestDto` now carries `role` (BE 案A, MR !932, deployed to dev 2026-11-03; API-070 still v0.15). A role change with 職位 left empty saves and lands on the new role's 「未割当」; `role` is sent only when it changed. See `spec.md` › "Role change without a position". TC-021 was re-specified and TC-079–TC-082 added; the contract-gap grading below is now historical.

`UpdateStaffRequestDto` (the body of `PATCH /api/v1/admin/staff/{id}`) contains **no `email` field and no `role` field**:

```
isActive, deactivatedReason, positionId, storeId, fcCompanyId,
lastName, firstName, lastNameKana, firstNameKana, phone, memo
```

So three requirements have nothing to write to:

- **FR-012** — "view and edit a staff account's name, **email**, role, position and affiliation"
- **FR-014** — "restrict changing a staff account's role to headquarters users only"
- **FR-015** — "require an explicit confirmation step before a role change is saved"

Meanwhile the form still renders an email input **with a 「重複確認」 button**, and (for HQ) a live role `Select` **with a confirmation dialog** behind it. The spec's own _Known Implementation Gaps_ section already flagged the email half; the role half is new to Phase 2.

**How to grade these** (TC-021, TC-022, TC-033, TC-034): check **the request payload and the reloaded record**, never the toast.

| Observed                                                                                                                                | Grade                                                           |
| --------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------- |
| The field is absent from the request **and** the UI reports success anyway                                                              | **`NG`** — the screen is lying to the user                      |
| The field is absent from the request **and** the UI says so (disabled control, explanatory message, or an explicit "not yet supported") | `Block` — contract gap, note the endpoint and the missing field |
| The field **is** sent and persists                                                                                                      | `OK` — the contract has moved on; record the new shape          |

A fourth possibility — the control is not rendered at all — is a spec-vs-implementation finding against FR-012/FR-014; record it as such.

Additionally, `PATCH` declares **`403` E-AUTH-103 "Caller is not HQ"**. Taken at face value the backend permits **no** Manager edit at all, contradicting FR-013's Manager exception and 権限マトリクス L284's Manager 職位割り当て.

> **決定 2026-09-18 — Y-01 is authoritative.** `Y-01.md` (the FR text plus 権限マトリクス L284) is the requirement of record; the endpoint's HQ-only gate is a **backend defect**, not a narrowing of the requirement. So:
>
> - A Manager editing a `Staff`-role account inside their managed stores **must be able to save** (FR-013), and **must be able to assign a 職位** (権限マトリクス L284 職位割り当て（担当店舗分） = ○).
> - A `403` in either case is an **`NG`** against the backend, logged with the response body as evidence — not a `Block`, and not a reason to soften the expected result.
>
> This is the same rule the test plan's 決定 applies to the gap rows: the spec wins, the implementation is measured against it.

## Phase 2 execution context

- **🚨 The dev backend holds REAL staff records — they are not fixtures.** Treat every account you did not create yourself as production data.
  - **Read-only / display cases** (list rendering, search, filter, sort, pagination, badges, layout, tab visibility, viewing a detail or history) may use **any** account, real dev staff included.
  - **Data-changing cases** (create, edit, 無効化, 有効化, 削除, 再招待, magic link, session revoke) may act **only** on an account you invited yourself during this run, or on one of the five seeded test accounts below. **Never on a real dev staff record.**
- **Seeded test accounts** (user-provided 2026-09-18, `Password@123` for all five) — **sign in as these**, not the older `src/lib/auth/demo-users.ts` set:

  | Role        | Address                            |
  | ----------- | ---------------------------------- |
  | Headquarter | `lodu4289+test_hq@gmail.com`       |
  | Manager     | `lodu4289+test_manager@gmail.com`  |
  | Staff       | `lodu4289+test_staff@gmail.com`    |
  | Trainer     | `lodu4289+test_trainer@gmail.com`  |
  | Observer    | `lodu4289+test_observer@gmail.com` |

- **These five are also your login identities**, so an irreversible or access-removing action on one destroys the role pass that still needs it. For 無効化 / 有効化 / 削除 / session revoke, **invite a fresh account in Unit 2 and target that** — never a seeded account, never a demo-user account, never a real record.
- **No `test_system` account was seeded.** System-role cases have no safe identity: run them as `lodu4289+1@gmail.com` **read-only**, or mark them `Block — no safe System account`. **Never attempt the last-system-admin guard cases against a real System account** — locking the environment out is not recoverable from the UI.
- **Real backend**, cross-origin. Capture every request **body** as well as every 4xx/5xx response — for this unit the outgoing payload is the primary evidence.
- **No seed reset.** Edits are permanent against shared dev data. **Edit the Unit 2 fixtures, never a demo-user role account** — changing a role account's role or affiliation will break later cases in every other unit.
- **Grading.** Beyond the table above: `NG` = wrong gating against the 権限マトリクス, a save that reports success without persisting, a confirmation dialog that fires on the wrong condition, or an error body swallowed into a stock toast.

### Why 03-01 / 03-02(職位) / 03-04 were rolled back

All three come from one root cause, now fully characterised:

1. A staff's **ロール is derived from their 職位**. `UpdateStaffRequestDto` has no `role` field and no
   other endpoint changes a role; sending a `positionId` that belongs to another role moves the staff
   to that role (verified live).
2. Each role has a 「未割当」 position row (`…0001`–`…0006`). They carry **`isSystemManaged: true`**, and
   `GET /admin/positions` excludes system-managed rows **by contract** — that endpoint serves the
   職位マスター screen, which must not list them. So the value a staff actually holds matches no option
   in the picker, and there is no id to send to put a staff back on 未割当.
   `includeSystemManaged` / `isSystemManaged` / `includeUnassigned` are all rejected with `400`.

**Product decision (user, 2026-09-18): the edit screen will not offer 「未割当」 at all.** Assignment
becomes one-way — a staff can be moved between positions but not returned to 未割当 from this screen.
Under that rule the write-side problem disappears without any hard-coded ids, and the read side is
served by `StaffDetailDto.positionName`, which the API already returns. Implementation is deferred
until the backend items below are agreed.
