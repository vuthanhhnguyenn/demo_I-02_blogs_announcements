# TC -【Fitness CRM】- [Y-13][P2-05][ログイン履歴・セッション]

**Unit 5 of 5** — Phase 2 (real-API integration) test cases for the **ログイン履歴** tab and the **アクティブセッション** panel on the staff detail screen, route `/staffs/[id]` (third tab).

**Scope**: the tab's visibility gate, the アクティブセッション card (rows, current-session marking, per-row and bulk force-termination, the concurrency-cap footer), and the ログイン履歴 table (columns, ordering, footer, pagination, empty state) — plus the server-side gate on both underlying endpoints.

**Scope boundary with Unit 4**: this tab renders inside the same screen as Unit 4 but is governed by a separate spec (`specs/031-staff-login-history`, Y-13 FR-M009 / FR-S002) and a stricter role gate. Unit 4 asserts only that the tab is _present or absent_; everything inside it is here.

**Out of scope**: account lockout (Y-13 FR-M008) and its HQ unlock action — the 031 spec records that no unlock endpoint exists under `/api/v1/admin/staff/*`, so it is a backend gap, not a descope, and there is nothing to test; the anomaly-detection notification in Y-13 FR-M009 (a system-level alert delivered outside this screen); 無効化 / 有効化 (account status, a different operation from session termination — Unit 4); the login flows that _produce_ these records (auth-flow passes `023` / `028` / `029`).

## Phase 2 execution context

- **🚨 The dev backend holds REAL staff records — they are not fixtures.** Treat every account you did not create yourself as production data.
  - **Read-only / display cases** (list rendering, search, filter, sort, pagination, badges, layout, tab visibility, viewing a detail or history) may use **any** account, real dev staff included.
  - **Data-changing cases** (create, edit, 無効化, 有効化, 削除, 再招待, magic link, session revoke) may act **only** on an account you invited yourself during this run, or on one of the five seeded test accounts below. **Never on a real dev staff record.**
- **Seeded test accounts** (user-provided 2026-09-18, `Password@123` for all five) — **sign in as these**, not the older `src/lib/auth/demo-users.ts` set:

  | Role        | Address                            |
  | ----------- | ---------------------------------- |
  | Headquarter | `lodu4289+test_hq@gmail.com`       |
  | Manager     | `lodu4289+test_manager@gmail.com`  |
  | Staff       | `lodu4289+test_staff@gmail.com`    |
  | Trainer     | `lodu4289+test_trainer@gmail.com`  |
  | Observer    | `lodu4289+test_observer@gmail.com` |

- **These five are also your login identities**, so an irreversible or access-removing action on one destroys the role pass that still needs it. For 無効化 / 有効化 / 削除 / session revoke, **invite a fresh account in Unit 2 and target that** — never a seeded account, never a demo-user account, never a real record.
- **No `test_system` account was seeded.** System-role cases have no safe identity: run them as `lodu4289+1@gmail.com` **read-only**, or mark them `Block — no safe System account`. **Never attempt the last-system-admin guard cases against a real System account** — locking the environment out is not recoverable from the UI.
- **Real backend**, cross-origin. Capture request bodies and all 4xx/5xx bodies.
- **⚠️ Session termination signs real people out.** Every case below acts on a **fixture** account's sessions. Terminating the **Headquarter** demo account's own session will sign the tester out mid-run — TC-027 does this deliberately and must be run last in its group.
- **Producing test data requires signing in.** Login-history rows and active sessions exist only for accounts that have actually signed in. Before this unit, sign in as each demo role at least once (which the earlier units already do), and note that each sign-in adds a row.
- **`204 No Content`** is the success response for revoke — a UI that waits for a JSON body will appear to hang. TC-022 exists for exactly this.
- **Grading.** `NG` = the UI misreports the backend (success over a failed call, an unmapped `authProvider` rendered raw, a hard-coded value where the contract serves one, a terminated session still shown as live). `Block` = the endpoint is unimplemented, the data cannot be produced, or a raw API call the harness cannot issue is required.

### Endpoints this unit exercises

| Action          | Endpoint                                        | Contract detail driving cases below                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| --------------- | ----------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Login history   | `GET /api/v1/admin/staff/{id}/login-histories`  | Params `page` (default **1**), `limit` (default **20**, clamped 1–100). Response `{ items[], pagination }`; items are **newest first (`logged_in_at DESC`) and explicitly not client-sortable**. `StaffLoginHistoryItemDto`: `id`, `loggedInAt` (UTC), `authProvider` (`google` \| `cognito` \| `magic_link`, **nullable**), `sessionId` (nullable), `ipAddress` (**nullable**), `userAgent` (**nullable**). **No `result` field.** `PaginationWithPageItemsDto`: `page`, `limit`, `totalItems`, `totalPages` (**minimum 1, even when empty**), `totalPageItems`. Responses `200 / 401 / 403 / 404` |
| Active sessions | `GET /api/v1/admin/staff/{id}/sessions`         | Response `{ sessions[], session (deprecated), maxConcurrent }`. `StaffActiveSessionDto`: `sessionId`, `createdAt`, `lastSeenAt` (**refreshed at most once a minute — may trail real activity by up to 60s**), `expiresAt`, `loggedInAt`, `authProvider`, `ipAddress`, `userAgent` (**"render the device / browser label from this"**), `isCurrent` (**"true when this is the CALLER's own session"**). All but `sessionId` and `isCurrent` are nullable. Responses `200 / 401 / 403 / 404`                                                                                                          |
| Terminate       | `POST /api/v1/admin/staff/{id}/sessions/revoke` | Body `{ sessionId? }` — **optional**: "Omit (or send no body) to end EVERY session the staff holds, which is the pre-multi-session behaviour and the right answer for a lost account." **`204`** = "Session(s) terminated, **or there was nothing to terminate**". `400` E-VAL-001 = `sessionId` present but not a UUID, or an unknown body key. `403` E-AUTH-103 = caller is not System/Headquarter. `404` E-STF-001 = staff not found                                                                                                                                                             |

## Test data reference

| Fixture        | Shape needed                                                                | How to produce it                                                                                                               | Used by                |
| -------------- | --------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- | ---------------------- |
| `S-ACTIVE`     | An account with **at least one** live session                               | Sign in as that account in one browser and leave it signed in                                                                   | TC-018–TC-031          |
| `S-MULTI`      | An account with **2–3** concurrent sessions                                 | Sign in as the same account from two or three distinct browsers/profiles                                                        | TC-019, TC-023, TC-033 |
| `S-NONE`       | An account with **no** live session                                         | Sign in then sign out, or wait for the TTL to lapse                                                                             | TC-021, TC-025         |
| `S-HISTORY`    | An account with **more than 20** login-history rows (the default page size) | Repeated sign-ins, or an account in long use                                                                                    | TC-013–TC-016          |
| `S-FRESH`      | An 招待中 account that has **never** signed in                              | A Unit 2 fixture whose invitation was never accepted                                                                            | TC-017, TC-026         |
| `S-GOOGLE`     | An account whose domain resolves to the **Google** lane                     | Determined by the Y-14 domain master                                                                                            | TC-007                 |
| `S-MAGIC`      | An account that has signed in via **マジックリンク**                        | Issue a link via Unit 4 TC-049 and use it — **note this crosses into the auth flow**; if not permissible, mark the case `Block` | TC-007                 |
| `S-LONG-TOKEN` | The Unit 2 unbroken-name overflow fixture, signed in at least once          | Unit 2 + a sign-in                                                                                                              | TC-035–TC-038          |

**Data limitations to carry into Notes**:

- (a) Every row and session below is produced by a **real sign-in**. If the environment forbids signing in as a fixture account, most of this unit is `Block` — say so once, at the top of the run, rather than per case.
- (b) `S-MULTI` needs 2–3 genuinely distinct browser sessions; separate browser profiles or private windows, not two tabs.
- (c) **失敗 / ロック rows cannot be produced** — the endpoint records successful sign-ins only and the DTO has no `result` field. Any case expecting them is `Block — no backend field` by construction, not a defect (item **B** above).
- (d) `authProvider` is nullable; a `null` row may not exist in the live data. If it cannot be produced, mark the null-handling case `Block`.
- (e) `lastSeenAt` is refreshed at most once a minute, so a freshly-active session may legitimately show a value up to 60 seconds stale — never grade that as a defect.

## Decisions applied (2026-09-18) and remaining open questions

### Resolved — these are no longer open

1. **Item A — 031 FR-005 rewritten.** FR-005 previously read "no session list or per-device detail is shown". That described a backend gap which has since closed (`sessions[]` + served `maxConcurrent`, `session` deprecated, optional `sessionId` on revoke). **FR-005 now requires** the session list, per-row termination, **bulk termination**, and a cap taken from the served value. `specs/031-staff-login-history/spec.md` has been updated with a dated revision note. TC-026, TC-027, TC-032 and TC-040 are written to the revised text.
2. **Retention footer (TC-021) — sourced after all.** 「保持期間1年間」 comes from **Y-13 FR-M009 L253「ログ保持期間: 1年間」**. It is a stated product requirement, not an invented claim, so the footer asserting it is correct and hard-coding it is appropriate (unlike the concurrency cap, no API field serves this number). 031 SC-004's vaguer "whatever retention the backend enforces" does not override Y-13. TC-021 raised from Low to Medium and its expected result inverted accordingly.
3. **Page-size control (TC-023).** Neither Y-01 nor Y-13 FR-M009 asks the UI to expose a page-size control for this tab, so its presence or absence is not itself a defect. The shared control **is** rendered here, and since 2026-09-21 its options are bounded app-wide by the endpoint's own `limit` clamp (`API_PAGE_SIZE_OPTIONS = [25, 50, 100]`) rather than by the prototype's PAR041 set — the FE follows the backend contract. Any option offered above 100 is a defect.
4. **Bulk revoke (TC-040) — now required.** Since revised FR-005 requires bulk termination, a missing "end all sessions" control is an **`NG`**, not an unused capability. TC-040 raised to High.

### Still open

5. **TC-028** — the contract instructs "render the device / browser label from `userAgent`", while the 031 Assumptions still state there is "no client-side derivation". The two disagree; the contract is the more recent. The Assumptions wording should be corrected alongside the FR-005 revision.
6. **TC-011, TC-017, TC-019** — `authProvider`, `ipAddress` and `userAgent` are all nullable in the contract, but no source states which placeholder to render for a null.
7. **TC-012, TC-013 — 結果 remains a backend to-do.** Y-13 FR-M009 L249 requires 結果（成功 / 失敗 / ロック）among the recorded fields, but `StaffLoginHistoryItemDto` has no `result` field and the endpoint records successful sign-ins only. The column is built forward-compatibly and defaults to 成功; delivering real 失敗/ロック values needs a backend data-model change. This stays visible as a sign-off item against Y-13, not as a frontend defect.
8. **TC-053** — Y-13 L243's HQ lockout-unlock action on this screen has no endpoint and is unbuilt; it needs to stay visible as a sign-off item rather than quietly dropping out of scope.
