# TC -【Fitness CRM】- [Y-01-01][P2-02][スタッフ新規登録]

**Unit 2 of 5** — Phase 2 (real-API integration) test cases for the bulk staff registration screen (スタッフ新規登録), route `/staffs/create`.

**Scope**: the creation form only — its 基本情報 person-list table, the shared 権限設定 (role + position) and 所属設定 (affiliation) sections, the 備考 field, the initial-password notice, the footer actions, and the unsaved-changes guard. Verification that a created account appears correctly in the list belongs to Unit 1; editing it afterwards belongs to Unit 3.

**⚠️ Scope boundary — the invite ends at "issued".** This unit's success criterion is that the invitation request is accepted **and** the new account appears in `招待中` status with the right role / position / affiliation. The invitation email arriving, the invite link opening, initial-password set, first login, and the `招待中 → 有効` transition are **out of scope** — they are covered by the auth-flow passes `023-first-time-login`, `028-subsequent-login` and `029-password-reset`. Do not author cases for them here.

**Other out-of-scope items** (per the test plan): 職位マスター管理 (`/positions` — referenced only as the source of 職位 names); Y-02 店舗管理 / Y-03 FC企業管理 master screens (consumed as option sources); Y-14 ドメインマスタ (the source of the `E-DMN-006` domain rule — this unit only asserts how the resulting error surfaces).

## Phase 2 execution context

- **Real backend**, called cross-origin from the browser at `https://api.dev.fitness-v2.okamoto-hd.com/api/v1/…`. Capture every 4xx/5xx body — for this unit the per-row `details.processed[]` array _is_ the evidence for most abnormal cases.
- **🚨 The dev backend holds REAL staff records — they are not fixtures.** Treat every account you did not create yourself as production data.
  - **Read-only / display cases** (list rendering, search, filter, sort, pagination, badges, layout, tab visibility, viewing a detail or history) may use **any** account, real dev staff included.
  - **Data-changing cases** (create, edit, 無効化, 有効化, 削除, 再招待, magic link, session revoke) may act **only** on an account you invited yourself during this run, or on one of the five seeded test accounts below. **Never on a real dev staff record.**
- **Seeded test accounts** (user-provided 2026-09-18, `Password@123` for all five) — **sign in as these**, not the older `src/lib/auth/demo-users.ts` set:

  | Role        | Address                            |
  | ----------- | ---------------------------------- |
  | Headquarter | `lodu4289+test_hq@gmail.com`       |
  | Manager     | `lodu4289+test_manager@gmail.com`  |
  | Staff       | `lodu4289+test_staff@gmail.com`    |
  | Trainer     | `lodu4289+test_trainer@gmail.com`  |
  | Observer    | `lodu4289+test_observer@gmail.com` |

- **These five are also your login identities**, so an irreversible or access-removing action on one destroys the role pass that still needs it. For 無効化 / 有効化 / 削除 / session revoke, **invite a fresh account in Unit 2 and target that** — never a seeded account, never a demo-user account, never a real record.
- **No `test_system` account was seeded.** System-role cases have no safe identity: run them as `lodu4289+1@gmail.com` **read-only**, or mark them `Block — no safe System account`. **Never attempt the last-system-admin guard cases against a real System account** — locking the environment out is not recoverable from the UI.
- Every role-gated case must be run **as** the named role, not inferred from another role's result.
- **⚠️ This unit creates real accounts on a shared dev backend.** Every created email must be a disposable, clearly-marked address (see Test data). Accounts created here are the fixtures Units 3, 4 and 5 consume — create them deliberately, not incidentally.
- **No seed reset.** A created account cannot be un-created except via Unit 1's 削除. Plan the fixture set before starting.
- **Grading.** `NG` = the UI misreports the backend (success toast over a failed call, per-row error collapsed into a stock message, created account with the wrong role/position/affiliation, unmapped enum). `Block` = the endpoint is unimplemented, or a failure mode cannot be induced.

### Endpoints this unit exercises

| Action              | Endpoint                                            | Contract detail that drives cases below                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| ------------------- | --------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Duplicate pre-check | `GET /api/v1/admin/staff/email-availability?email=` | Returns `EmailAvailabilityResponseDto` for **both** outcomes (200, never 404): `{ email, authProvider: "google" \| "cognito" \| null, available: boolean, reason: "duplicate" \| null }`. `available` is explicitly **advisory only** — the authoritative check is the unique constraint at invite time. `authProvider` is `null` when the domain is not registered in the domain master                                                                                     |
| Submit the batch    | `POST /api/v1/admin/staff/invite-bulk`              | Body: `{ staff: BulkInviteRowDto[], role, positionId?, storeId?, fcCompanyId?, memo? }`. **`staff` has `minItems: 1`, `maxItems: 50`**; emails must be unique within the request. `BulkInviteRowDto`: `lastName` 1–50 chars, `firstName` 1–50 chars, `email` ≤ 254 chars, all three required. `role` is a lowercase enum: `system / headquarter / manager / staff / trainer / observer`. Response carries `processed[]` (per-row outcome, in request order) plus a `summary` |
| 職位 options        | `GET /api/v1/admin/positions`                       | Source of the 職位 names and their ids                                                                                                                                                                                                                                                                                                                                                                                                                                       |

| `400` E-VAL-001  | Schema validation, **duplicate emails within the request**, affiliation **XOR** violation, unknown store / FC company, or an FC company spanning zero or several brands | TC-039, TC-046, TC-060 |
| `403` E-AUTH-103 | Caller is not HQ                                                                                                                                                        | TC-005                 |
| `404` E-STF-009  | Position does not exist                                                                                                                                                 | TC-061                 |
| `409` E-STF-002  | A row collides with an existing staff email + provider; `details.processed[]` names the row                                                                             | TC-036                 |
| `422` E-DMN-006  | A row's email domain is not registered for CRM access (Y-14 domain master); `details.processed[]` names the row                                                         | TC-040                 |
| `502` E-STF-005  | Cognito user creation failed — **users created earlier in the batch were deleted again** (full rollback); `details.processed[]` names the row                           | TC-041                 |

**Field limits — use the contract's numbers, not the defaults.** `BulkInviteRowDto` states 姓 1–50, 名 1–50, メールアドレス ≤ 254. These override the shared checklist's "single-line text = 255" fallback. 備考 has no contract limit stated; the mockup caps the textarea at 1000, matching the checklist default — note it **Contract-confirmed**: `UpdateStaffRequestDto.memo` is `maxLength: 1000` — a real limit, not an assumed default.

**Batch cap**: `staff` accepts 1–50 rows. 50 is the boundary; 51 must be rejected.

**Data limitations**: (a) 職位 options are role-dependent and come from the master — the exact option set per role must be read at execution time; (b) the store and FC-company option lists come from the Y-02/Y-03 masters and are not knowable from the spec; (c) `E-DMN-006` (unregistered domain) requires an email on a domain absent from the Y-14 domain master — confirm which domains are registered before writing the address for TC-040; (d) inducing `502` (E-STF-005) may not be possible on demand.
