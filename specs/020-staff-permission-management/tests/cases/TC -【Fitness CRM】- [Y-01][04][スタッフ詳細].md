# TC -【Fitness CRM】- [Y-01][スタッフ詳細]

**Screen**: スタッフ詳細 (Staff Detail — 基本情報 / 変更履歴 tabs)
**Route**: `/staffs/[id]`
**Unit**: 4 — Staff Detail, per `specs/020-staff-permission-management/tests/test-plan.md`
**Scope**: Basic-info display (name/email/role/position/affiliation/note), status card + deactivate, delete, magic-link issuance, permission-history tab, tab mechanics, role-gated action controls, layout robustness. Out of scope (per test plan): 職位マスター管理 CRUD, 職位別権限プレビュー screen content (only the reference link's navigation is checked here), FC企業管理/店舗管理 master screens, Y-13 invite-token internals.

## Source note

- **Spec**: `specs/020-staff-permission-management/spec.md` — User Story 4 (all scenarios), User Story 5 (all scenarios), Edge Case "What happens if a trainer or observer opens a staff account's detail page?"; FR-012 (view portion), FR-013 (button gating), FR-018, FR-019, FR-020, FR-021.
- **UI mockup**: `.cache/fitness-crm-ui/src/pages/staff-detail.tsx` (design source for exact Japanese copy, layout, and the role-gating logic actually wired into the reviewed prototype — `RoleGatedButton` allowedRoles/denyTooltip props, `StatusCard`, dialog content). Cross-referenced shared components `.cache/fitness-crm-ui/src/components/role-gated-button.tsx` (confirms the deny treatment is uniformly **disabled + tooltip**, never hidden, and that the _default_ deny tooltip text is `本部権限が必要です` when no `denyTooltip` prop is supplied) and `.cache/fitness-crm-ui/src/components/status-card.tsx` (confirms the status card's own title is `ステータス`).
- **Requirement doc cross-reference**: `.cache/fitness-spec/crm/requirements/Y-01.md` — 6-role definitions, 3-layer permission model, 権限マトリクス (permission matrix): account deactivation/deletion and role change are HQ-only; edit is HQ (any) / Manager (managed-store Staff only).
- **Shared checklists**: `tests/checklists/common-function-checklist.md` (View Detail, Action History/Audit Trail, Dialog branching, Computed/Time-Derived n/a here, Unsaved-Changes n/a here — this screen has no form) and `tests/checklists/common-gui-validate-checklist.md` (General Layout, Dialog/Confirmation Message, Output Escaping, Tabs).
- **Checklist added this run**: a row was added to `common-function-checklist.md` § View Detail — "Check a role-denied action control's exact treatment (hidden vs. visibly-disabled-with-tooltip)" — because the test plan's cross-cutting execution note calls out that different controls on this feature use different denial treatments, and the previous checklist wording didn't force verifying _per control_, only per screen. Expanded into TC-018 below.
- **Nothing was missing**: both the spec and the UI mockup were readable; no `Block`-only cases were required due to a missing Source. Cases below marked `Block`/open-question are flagged for a **data or spec-ambiguity** reason instead (see each case's Notes), not a missing Source.
