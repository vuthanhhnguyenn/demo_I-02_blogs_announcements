# TC -【Fitness CRM】- [Y-01][P2-04][スタッフ詳細]

**Unit 4 of 5** — Phase 2 (real-API integration) test cases for the staff detail screen (スタッフ詳細), route `/staffs/[id]` — **core**: the page header and its actions, the 基本情報 tab (基本情報 / 所属・権限 / 備考 cards + StatusCard), the 変更履歴 tab, and the account-lifecycle dialogs (無効化 / 有効化 / 削除 / マジックリンク).

**Scope boundary with Unit 5**: the **ログイン履歴** tab and the **アクティブセッション** panel render on this same screen but are governed by a separate spec (`031-staff-login-history` / Y-13, 8 FRs) and are covered by **Unit 5**. This document asserts only that the tab is _present or absent_ for the role under test (TC-016/TC-017) and leaves its contents entirely to Unit 5.

**Out of scope** (per the test plan): 職位マスター管理 (`/positions` — the 「この職位の権限を確認」 link's _target_; only the link's presence and navigation are checked here); the edit form itself (Unit 3); the list (Unit 1); Y-13 FR-S001 発行経路1 (self-service magic link from the login screen — auth-flow passes); the magic link's destination, expiry and one-time-use behaviour.

## ⚠️ Read first — magic link on this screen: HQ for others, anyone for themselves (gap G8, CLOSED 2026-09-18)

`020/spec.md` FR-020 reads: "System MUST let a headquarters user issue a one-time CRM login link for any staff account; **a staff member MUST also be able to issue this link for their own account regardless of role**."

**決定 2026-09-18 (user): Y-13 and Y-01 describe two different things and neither is wrong.**
Y-13's 発行経路1 is _the user requesting a login link for themselves_; Y-01's button is _a staff
member requesting one on behalf of another user_. They are separate acts, so the two documents
were never in conflict and there is nothing to fix. This supersedes the earlier reading (recorded
below for history) that took 発行経路2 to be the only path on this screen and therefore graded a
self-issue as a defect.

| 経路                      | Where                                                                              | Who                                                                                  | In this unit?                               |
| ------------------------- | ---------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ | ------------------------------------------- |
| **発行経路1** (Y-13 L270) | The **login screen** — 「マジックリンクでログイン」, user enters their own address | Any role, self-service                                                               | ❌ auth-flow passes (`023` / `028` / `029`) |
| **発行経路2** (Y-13 L271) | **Y-01 staff detail screen** — 「マジックリンク発行」 button                       | 「**HQがスタッフに代わって発行**」 — HQ/System only, _when issuing for someone else_ | ✅ this unit                                |
| **FR-020 self-clause**    | **Y-01 staff detail screen**, on the actor's **own** record                        | Any role                                                                             | ✅ this unit                                |

**How to grade this block**: on **another** account the button must be HQ/System only (TC-049–TC-051).
On the actor's **own** account it is enabled for every role (TC-052). That is exactly what the
screen and the backend both implement today.

The backend agrees: `POST /api/v1/staff/magic-link` returns **`403` E-AUTH-103 "Proxy issuance requires HQ"**.

**Therefore**: author the button as **HQ/System only** (TC-045–TC-052). A non-HQ role finding it enabled is an `NG` — even though the prototype currently allows every role to self-issue from here (`staff-detail.tsx` L174: 「自分自身のスタッフ詳細なら全ロール可」). `020/spec.md` FR-020 conflates the two 経路 and needs amending; that is recorded as an open question, not tested around.

## Phase 2 execution context

- **🚨 The dev backend holds REAL staff records — they are not fixtures.** Treat every account you did not create yourself as production data.
  - **Read-only / display cases** (list rendering, search, filter, sort, pagination, badges, layout, tab visibility, viewing a detail or history) may use **any** account, real dev staff included.
  - **Data-changing cases** (create, edit, 無効化, 有効化, 削除, 再招待, magic link, session revoke) may act **only** on an account you invited yourself during this run, or on one of the five seeded test accounts below. **Never on a real dev staff record.**
- **Seeded test accounts** (user-provided 2026-09-18, `Password@123` for all five) — **sign in as these**, not the older `src/lib/auth/demo-users.ts` set:

  | Role        | Address                            |
  | ----------- | ---------------------------------- |
  | Headquarter | `lodu4289+test_hq@gmail.com`       |
  | Manager     | `lodu4289+test_manager@gmail.com`  |
  | Staff       | `lodu4289+test_staff@gmail.com`    |
  | Trainer     | `lodu4289+test_trainer@gmail.com`  |
  | Observer    | `lodu4289+test_observer@gmail.com` |

- **These five are also your login identities**, so an irreversible or access-removing action on one destroys the role pass that still needs it. For 無効化 / 有効化 / 削除 / session revoke, **invite a fresh account in Unit 2 and target that** — never a seeded account, never a demo-user account, never a real record.
- **No `test_system` account was seeded.** System-role cases have no safe identity: run them as `lodu4289+1@gmail.com` **read-only**, or mark them `Block — no safe System account`. **Never attempt the last-system-admin guard cases against a real System account** — locking the environment out is not recoverable from the UI.
- **Real backend**, cross-origin. Capture every request body and every 4xx/5xx response body.
- **⚠️ This unit contains the most destructive cases in the whole plan.** 削除 soft-deletes **and masks PII** — it is not undoable through any screen. Use a dedicated Unit 2 fixture for it, distinct from the 無効化/有効化 fixture, and never a demo-user role account.
- **No seed reset.**
- **Grading.** `NG` = the UI misreports the backend (success toast over a failed call, a status that does not persist, an unmapped enum rendered raw), or gating that contradicts the 権限マトリクス / Y-13 FR-S001.
