## Scope

### Why a Phase 2 pass at all

Phase 1 executed 239 cases against the mock API: **213 OK / 0 NG / 26 Block**. Three things have moved since, so a re-run — not a spot-check — is warranted:

1. **The screens now call the real backend.** Every Phase 1 `OK` was observed against mock route handlers under `src/app/api/crm/staffs/**`. Response shapes, enum casing, pagination, scoping and error codes are now the backend's, so each behavioural assertion has to be re-observed, not inherited.
2. **The prototype moved (`b223fef` → `6bc1f1c`, 2026-09-08).** `staff-list.tsx` +73/−19, `staff-detail.tsx` +94/−28, `staff-form.tsx` +134/−114. These are behavioural changes, not cosmetics — see the drift table below.
3. **26 Phase 1 `Block`s were mock-layer limitations** (no per-role accounts, no fixture records with long/XSS values, empty change-history, one-way destructive flips). Real Cognito gives all six roles (`src/lib/auth/demo-users.ts`), so most of these are now executable and must be re-graded rather than carried forward as `Block`.

### Contract-level risks to confirm on the live API (open going in)

These are read off `src/lib/openapi.real.json` and must be **observed**, not assumed, then graded per the rules in Execution Notes:

- **`UpdateStaffRequestDto` carries neither `email` nor `role`.** FR-012 (edit email) and FR-014/FR-015 (HQ role change + confirmation dialog) have no field to write to. The spec's own _Known Implementation Gaps_ already flagged the email half; the role half is new and more serious, since FR-015's confirmation dialog is a core Phase 1 pass.
- **`DeactivateStaffRequestDto` requires `deactivatedReason`**, while the spec's Assumptions state deactivation reason capture is optional. A no-reason deactivate will 422 if the UI lets it through.
- **`GET /admin/staff` exposes filters Phase 1 never had**: `emailDomain`, `isActive`, `inviteStatus`, `area`, `positionId`, `storeId`, plus `sort`/`order` and real server-side pagination.
- **`UpdateStaffRequestDto` carries fields the spec calls out of scope** (`lastNameKana`, `firstNameKana`, `phone`), and `StaffDetailDto` returns them — drift in the opposite direction from the spec's out-of-scope list. **決定 2026-09-18: Y-01 is authoritative — these stay out of scope.** The existing UI is not removed; each rendering site carries a comment citing the spec source so the divergence is visible in the code rather than only in this plan.
- **`PATCH /admin/staff/{id}` declares `403` "Caller is not HQ"**, which would deny FR-013's Manager exception and 権限マトリクス L284's Manager 職位割り当て outright. **決定 2026-09-18: Y-01 is authoritative — the endpoint's HQ-only gate is a backend defect.** A `403` for a Manager editing an in-scope `Staff`-role account, or assigning its 職位, is graded `NG` with the response body as evidence.
- **`POST /staff/magic-link` takes `linkType: mobile_app | crm_login`** — the CRM screen must always send `crm_login`.
- **Field limits: `Y-01.md` defines none, so the contract governs (決定 2026-09-18).** Y-01 lists required vs optional fields (FR-002) but states no lengths or formats anywhere, so the API's `minLength` / `maxLength` / `minItems` / `maxItems` are the **real, enforced** limits — not assumptions, and they override the shared checklist's 255 / 1000 fallbacks. Now recorded in `spec.md` › "Field Validation Constraints". The enforced set: 姓 / 名 **1–50**, email **≤ 254**, 備考 **≤ 1000**, 無効化理由 **≤ 500**, batch **1–50 rows**; out-of-scope-but-carried: フリガナ **≤ 50** each, 携帯電話番号 **≤ 15**.
  - **⚠️ 無効化理由 is 500, not 1000.** Earlier drafts of these docs assumed the project's generic 1000-character textarea default. The mockup's textarea also caps at 1000, so a UI inheriting that cap is **looser than the contract** and lets a user type a reason the backend rejects with `400`. Corrected in Unit 4 TC-037.
  - Every boundary case must also check the UI's cap is **not looser** than the DTO's — that mismatch is the finding, independent of the number itself.

## Coverage Focus per Unit

These are **added to**, not a replacement for, `gen-testcases`' full coverage walk (field-level validation, empty/loading/error states, etc. per `tests/checklists/common-function-checklist.md` and `common-gui-validate-checklist.md`).

### 0. Cross-cutting — layout-breaking text (apply in EVERY unit)

**This is the highest-value area of the Phase 2 pass and the one most likely to be under-authored.** Phase 1 blocked every long-value case for lack of fixtures; on the real API the data is user-supplied and unbounded in practice, so these now have to be run. The relevant checklist rows are already **High** priority — `common-gui-validate-checklist.md` L27 (long dynamic string in every place it is echoed), L272 (long value in a table cell), L49 (long value interpolated into a dialog), L61 (long value in a read-only display field), L153/L163/L176 (long option text in select/combobox). Do not collapse them into one generic "long text" case per screen.

**Rules for every long-value case in this feature:**

1. **Test both shapes.** A value with word-break points (spaces) _and_ a single unbroken token of the same length. Most layouts survive the first and break on the second — this is the single most common miss.
2. **Follow the value to every surface it is echoed on, not just where it is entered.** One long 氏名 must be checked in: the list table cell, the list row's dropdown menu, the detail page header/`PageHeader` title, the 基本情報 card, the StatusCard, the 無効化 / 有効化 / 削除 / マジックリンク confirmation dialogs (each interpolates the name), the success/error toast bodies, and the 変更履歴 / ログイン履歴 rows' operator column. A cell that truncates cleanly proves nothing about the dialog that does not.
3. **Name the strategy, then judge it.** Truncation-with-ellipsis (full value reachable via tooltip/expand), wrap, or horizontal scroll are all acceptable — silently clipping with no way to read the full value, overlapping an adjacent column, breaking row height/alignment, or pushing a button off-screen or out of reach is a finding.
4. **Where the mockup and spec state no limit, apply the checklist defaults** (single-line text = 255, textarea = 1000) and note `assumed default; confirm with PO/schema owner`. Accepting input past the default with **no cap and no error** is itself a finding, not a pass — the real backend will truncate or 500.
5. **Fixtures are self-created.** No seed data carries these values; build them via Unit 2 (create) + Unit 3 (edit), per Execution Notes.

### 2. Staff Registration
