# TC -【Fitness CRM】- [Y-13][01][ログイン] (Regular Login)

> Covers `specs/028-subsequent-login/` User Stories 1–3 and all Edge Cases — the regular
> (second-login-onward) sign-in screen: Google + email/password always shown together, plus its
> session-expired / account-locked / domain-unregistered(-not-active) / generic-error banner states,
> post-login redirect targeting, and the already-authenticated guard. Driven by
> `specs/028-subsequent-login/tests/test-plan.md`, Unit 1 (single unit — one screen, one route).

## Source note

- **Spec**: `specs/028-subsequent-login/spec.md` (read in full).
- **Requirement doc**: `crm/requirements/Y-13.md` — FR-M001/FR-M002 (excl. MFA), FR-M003,
  FR-M005, FR-M007/FR-M008/FR-M009 referenced for cross-check only; not used as a copy source.
- **UI mockup** (read in full): `login.tsx` (props-driven `variant`: `""`, `"error"`,
  `"session-expired"`, `"locked"`, `"domain-unregistered"`).
- All sources were available — no `Block — needs spec/mockup` cases in this document.
- **Mockup/spec divergence noted, not treated as a defect to test for**: the mockup's demo
  `handleLogin()` navigates to a `mfa-verify` route after a successful email/password submit. The
  spec's own Assumptions section explicitly excludes MFA from this feature's scope (undecided item
  `Y-13-Q01`) and the real app's route tree has no `mfa-verify` route at all. Cases in this document
  therefore assume the real app completes sign-in directly (no second step) per the spec, not per
  the mockup's demo wiring — flagged here so a tester isn't confused by the mockup's extra hop.
- **No test environment for Google OAuth or real Cognito credential verification** (per user
  instruction) — every case whose outcome depends on that live round-trip is marked `Block`-eligible
  in its Notes column; the CRM-side form, client-side validation, banner-state rendering, and
  redirect-targeting logic around them are written as real, executable cases.

| Active, email/password (経路②) staff                     | `staff@joyfit.co.jp` / `CorrectPass1!` | Assumed sample credentials — not stated by spec/mockup |

**Data limitations**: The spec/mockup describe no concrete lockout threshold (number of failed
attempts) or lockout duration figure — the mockup's locked-state copy hardcodes "約15分後" but the
spec only says accounts unlock "automatically" with no number. Confirm both the actual threshold and
duration against the real app at execution; treat the mockup's "15分" as an unconfirmed UI detail,
not a spec requirement to assert on strictly.

## Common pre-conditions

| ID   | Pre-condition                                                                                                  |
| ---- | -------------------------------------------------------------------------------------------------------------- |
| PC-A | Staff account is active and Google-linked (経路①), with a working Google session available.                    |
| PC-B | Staff account is active and email/password-based (経路②), with known correct credentials.                      |
| PC-C | Staff account has been deactivated (applies to either sign-in path).                                           |
| PC-D | No staff record exists for the identity being used (unregistered email/domain).                                |
| PC-E | Staff account is currently locked (already in the locked state — no need to trigger it live).                  |
| PC-F | Signed out, arriving at `/login` via a redirect from a specific protected page the staff member tried to open. |
| PC-G | Signed out, arriving at `/login` via a session-expiry redirect.                                                |
| PC-H | Currently signed in with a valid, non-expired session.                                                         |
| PC-I | Staff account normally uses Google (経路①) and has no email/password credential on file.                       |
| PC-J | Staff account normally uses email/password (経路②); its email has no corresponding Google-linked staff record. |

> **Viewport scope:** testing targets a **tablet-and-up** viewport (tablet-landscape / desktop).
> Mobile/phone width is out of scope. This screen has no role/permission matrix (pre-authentication)
> and no dynamic long-string display or user-echoed free text (all banners are fixed copy; email/
> password are masked/not redisplayed) — layout-robustness and XSS-escaping dimensions are therefore
> not applicable and are omitted rather than padded with no-op cases. The spec also does not require
> email-format validation on this screen (FR-010 only requires both fields be filled in — unlike
> `029-password-reset`'s request screen, which does validate format) — no invalid-email-format case
> is written here for that reason, not by oversight.
