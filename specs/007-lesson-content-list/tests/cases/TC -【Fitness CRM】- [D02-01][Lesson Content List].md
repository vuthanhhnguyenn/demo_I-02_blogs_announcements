**Checklist rows added while authoring** (checklist-first rule): two rows in `common-function-checklist.md` → Search section — (1) verifying every filter option is reachable in every data pool it's offered against when one filter component is reused across tabs backed by different datasets, (2) confirming exactly what a "Clear all" action resets vs. leaves untouched. Both are exercised below (TC-030, TC-041).

**Spec-vs-mockup gaps and notable findings flagged here (and again inline in the affected cases' Notes):**

1. **Data-scope axis mismatch (store vs. brand).** `007-lesson-content-list/spec.md` FR-001-P1-07 ("scope visible... rows to accessible stores and current store selection from user context") and the `lesson.tsx` code (`accessibleStores`, `currentStoreId`, `inScope(store)`) both implement **store-based** scoping. The parent `D-02.md` requirement doc's permission matrix instead states data scope by **brand** ("Manager/Staff/Trainer/Observer: 所属ブランドのマスタ"). This doc writes scope cases to `007`'s own store-based wording (the direct oracle for this unit) and flags the brand-vs-store conflict for the PO to reconcile — see TC-053–TC-056.
2. **"New Lesson Creation" role gating is cross-spec-sourced.** `lesson.tsx` hardcodes `RoleGatedButton allowedRoles={["Headquarter","System"]}`, matching D-02's permission matrix and `009-lesson-content-form`'s FR-009-P1-01 — but `007`'s own spec text never states this gating explicitly. Per test-plan §5, FR-009-P1-01 (from the 009 sources) is treated as the oracle for this button. See TC-004–TC-006.
3. **Personal-tab row click does not pass the selected record's id.** Studio/Body-care rows call `navigate("lesson-detail", undefined, { id: lesson.id })`, but the Personal-tab row handler calls `navigate("lesson-detail", "personal")` — no `id` of any kind is passed, for any row. Every Personal-plan row, regardless of which is clicked, drives the same call. This directly fails the common-function-checklist's "View Detail → identifier in the URL matches the selected record" check. Flagged as a likely defect, not silently normalized — see TC-046 (High).
4. **A filter option that can never match within its own tab.** The `LessonTable` component is instantiated once for the Studio tab (data = `scopedLessons`) and once for the Body-care tab (data = `scopedBodyCare`), but both instances offer the same 4-way "レッスン区分" (lesson-kind) filter (全区分/スタジオレッスン/パーソナルトレーニング/ボディケア). Since `scopedLessons` contains no `パーソナルトレーニング`/`ボディケア` items and `scopedBodyCare` contains only `ボディケア` items, selecting the "wrong" kind value on either tab is structurally guaranteed to return zero rows, in every case, regardless of any other filter or search value. See TC-030 (new checklist row applied).
5. **"Clear all" does not clear the search box.** In both `LessonTable` and `PersonalTrainingTable`, the "すべてクリア" button's `onClick` resets `category`/`brand`/`status`/`lessonCategory`(/`showDeleted` for Studio/Body-care) but never touches `searchQuery`. See TC-041 (new checklist row applied).
6. **Personal tab lacks the "include deleted" toggle and the lesson-kind filter present on the other two tabs.** `PersonalTrainingTable`'s filter row has only category/brand/status + Clear all — no `Checkbox`/`showDeleted` state at all, unlike `LessonTable`. `007`'s spec text (FR-001-P1-04) doesn't scope the toggle to specific tabs, so this asymmetry is grounded only in the mockup; flagged rather than assumed intentional. See TC-034, TC-038.
7. **Static/placeholder counts, per spec's own Edge Case #3.** Personal tab's badge is hardcoded `45`, the page-header total is `scopedLessons.length + 45`, and the Personal-tab footer always reads "全 45 件中…" regardless of the actually-filtered row count. `007-lesson-content-list/spec.md`'s own Edge Cases section states this is expected Phase-1 behavior ("some counts are static placeholders in UI") — cases below (TC-008, TC-026) document this as **expected**, not a finding, distinguishing it from the general common-gui-checklist "stale badge" flag.
8. **Pagination controls are visually static, not wired.** Only the "前へ" button carries a `disabled` attribute (always disabled); the "1"/"2"/"3"/"次へ" buttons have no `onClick` handlers at all in the mockup. FR-001-P1-09 only requires pagination controls to be **displayed** (unlike search/sort/filter, which `007`'s clarifications explicitly required to be functional) — cases below test only the display requirement and flag the non-functional buttons as an open item to confirm with the PO/dev, not an automatic NG. See TC-042–TC-044.
9. **Loading/Error states have no mockup source at all.** `007-lesson-content-list/spec.md` FR-001-P1-14/FR-001-P1-15 explicitly require a skeleton loading state and an error state "using the project's existing components," and the spec itself notes the `lesson.tsx` prototype has neither. Cases below (TC-047–TC-049) are written from the spec text alone since the mockup provides zero executable detail (no component name, no exact copy) — mark `Block` at execution if the as-built screen's loading/error UI can't be located, rather than guessing.
