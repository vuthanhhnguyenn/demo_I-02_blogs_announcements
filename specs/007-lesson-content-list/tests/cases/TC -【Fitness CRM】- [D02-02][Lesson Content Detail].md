## Source note

Sources used: `specs/008-lesson-content-detail/spec.md` (full document, oracle), `.cache/fitness-crm-ui/src/pages/lesson-detail.tsx` (full file, 819 lines, UI executable detail), `tests/checklists/common-function-checklist.md`, `tests/checklists/common-gui-validate-checklist.md`. All four sources were fully readable — no source-missing `Block` cases; the `Block` cases below are either **spec-mandated but absent from the current mockup** (per skill philosophy — write from spec, don't invent code) or **data-limitation** (no seed value reaches the boundary/tier in question).

Findings surfaced while authoring (flag, don't silently normalize — per skill philosophy #1):

1. **Deactivate/re-activate control is not role-gated in the mockup.** The spec's Clarification Q1 explicitly resolves "gate the Deactivate ('無効化する') action to `[\"Headquarter\", \"System\"]`" (FR-003-P1-17), but the status-card button in the code (`lesson-detail.tsx:433-442`) is a plain `<Button>` with no `RoleGatedButton` wrapper and no role check at all — every role can click it. See E2.
2. **Deactivate dialog's confirm button ignores the reason field.** FR-003-P1-14 requires a deactivation reason before confirmation succeeds. The mockup's `AlertDialogAction` (`lesson-detail.tsx:759`) has no `disabled` binding to the `Textarea`'s content — it closes unconditionally on click regardless of whether any reason was typed. See M3.
3. **Delete dialog's confirm button (unused branch) ignores the reason field.** FR-003-P1-16 requires a delete reason before enabling confirmation for a usageCount = 0 master. The mockup's confirm button is `disabled={usageCount > 0}` only (`lesson-detail.tsx:807`) — once usage is 0 the button is already enabled with no reason typed. See O2.
4. **No inactive/soft-deleted rendering exists in the mockup at all.** Spec Clarification Q4 and FR-003-P1-21 require the header badge + status card to reflect an inactive/soft-deleted state with a re-activation ("有効化する") control. The code hardcodes the Active/"有効" badge (`lesson-detail.tsx:358-361`) and `StatusCard tone="success" label="有効"` (`lesson-detail.tsx:427-430`) with no conditional branch. E4/E5 are written from spec text alone and marked `Block` pending an as-built inactive-state view.
5. **Schedule instructor is plain text, not a D-04 link, and never multi-valued.** Spec Clarification Q3 and FR-003-P1-09a require the instructor to render as a clickable link to the D-04 master with multi-instructor ("n名") support. The recurring-pattern summary (`lesson-detail.tsx:589-620`) renders `setting.instructor` as plain text, single value only. See I3 (flagged as a gap) and I11 (`Block` — no clickable element exists to exercise).
6. **Loading skeleton and error/not-found states have zero mockup grounding**, same situation as D02-01 — the detail data renders synchronously from a hardcoded object. P1/P2 are written from spec text only (FR-003-P1-22/23) and should be marked `Block` at execution if the as-built component/copy cannot be located.
7. **`usageCount` for `type="personal"` is hardcoded to `5`** regardless of any `id` param (`lesson-detail.tsx:261-263`), while studio's usageCount is looked up per-id from `LESSON_USAGE_COUNT`. This means the delete dialog's "unused, usageCount = 0" branch is structurally unreachable for a personal-type record in this prototype. See O3 — data limitation, not a functional bug to fix here.
8. **`allSchedules` (34 rows) is a single hardcoded array shared by both studio and personal sample data**, and none of its rows reach `booked === capacity` (max is 18/20 = 90%, 14/16 = 87.5%) — the sheet's spec'd "full = destructive" coloring tier (Edge Cases, spec.md) is unreachable with current sample data. See I8 — data limitation.
9. **`changeHistory` (5 entries) is likewise one hardcoded array, not varied by lesson type** — the same 5 entries appear whether viewing the studio or the personal sample. Per the spec's own Assumptions ("Sample/mock values in the prototype ... represent data shape only"), this is expected Phase-1 behavior, not a defect.
10. **Neither sample record's `name` or `description` approaches the assumed-default 255/1000-char boundary.** Boundary-layout cases (A8, D3, Q1) are marked `Block`/data-dependent per the shared **Default field constraints** fallback table.
11. **The header's Duplicate/Edit `RoleGatedButton`s pass no explicit `denyTooltip` prop** (`lesson-detail.tsx:380-391`), unlike Delete which passes `denyTooltip="削除権限がありません"`. The exact tooltip text shown to a non-privileged user on Duplicate/Edit depends on the `RoleGatedButton` component's internal default, which is outside this source set — A4 flags this as an open question rather than inventing wording.

**Checklist rows added** (checklist-first workflow, per standing preference): a new **"Reason-Required Lifecycle / Destructive Actions"** section in `common-function-checklist.md` (confirm button must actually be wired to the required-reason field's content, not just show a `*` marker) — motivated by findings #2/#3 above; and a new **"Tiered / Threshold Color-Coded Values"** section in `common-gui-validate-checklist.md` (exercise every color tier near its real boundary, note unreachable tiers as data limitations) — motivated by the schedule-capacity coloring in H3/I5-I8.
