## Source note

Sources used: `specs/009-lesson-content-form/spec.md` (full document, oracle), `.cache/fitness-crm-ui/src/pages/lesson-form.tsx` (full file, 658 lines, UI executable detail), `.cache/fitness-spec/crm/requirements/D-02.md` (権限マトリクス cross-check only), `tests/checklists/common-function-checklist.md`, `tests/checklists/common-gui-validate-checklist.md`. All sources were fully readable — no source-missing `Block` cases; the `Block` cases below are either **spec-mandated but absent from the current mockup** or **data-limitation** (the mock's hardcoded pre-fill never reaches the state in question).

Findings surfaced while authoring (flag, don't silently normalize — per skill philosophy #1):

1. **The create-mode confirmation dialog does not interpolate the actually-typed lesson name.** FR-002-P1-16 requires the dialog to summarize "the lesson type, lesson name, pricing type, and status." The mockup's dialog body (`lesson-form.tsx:634`) renders `{isEdit ? (isPersonal ? "パーソナルボディメイク" : "ヨガ基礎クラス") : "（入力内容）"}` — in create mode (including duplicate, which is `mode="create"`) it **always** shows the literal placeholder text "（入力内容）" instead of the live `lessonName` state, regardless of what the user entered. Pricing type (`{pricingType || "（選択内容）"}`) does correctly bind to live state. See TC-061/TC-062/TC-070. New checklist row added to `common-gui-validate-checklist.md` → **Dialog / Confirmation Message**.
2. **The description toolbar implements only Bold, Italic, and a bullet-List toggle — not Bold/Italic/Underline/Strikethrough as the spec's Requirements prose states.** `lesson-form.tsx:548-551` imports and renders `Bold`, `Italic`, `List` from lucide-react; there is no Underline or Strikethrough control, and a List (bullet) toggle exists that the spec text never mentions. See TC-046.
3. **The per-use fee value is not cleared when pricing type changes away from 有料（都次）**, contradicting the spec's own Edge Case ("changing away from it hides the field, and a previously entered value is not retained once hidden"). The `pricingType` `onValueChange` handler (`lesson-form.tsx:327`) only updates `pricingType`/clears its own error — it never resets `perUseFee`. See TC-025.
4. **The 所要時間 (duration) selection is not reset when レッスン区分 changes mid-fill.** Switching from a studio-only option (e.g. 90分/120分) to パーソナルトレーニング leaves the previously-selected out-of-range value in state with no visible re-validation or clearing, even though it is no longer among the rendered options. See TC-016.
5. **Edit-mode pre-fill values are hardcoded per-mode (not per source-master id) and diverge from the sibling D02-02 (`008`) detail-screen sample data** — `brand` is always `"JOYFIT"` (008's studio/personal samples are both `"FIT365"`); `duration` is always `"60分"` (008's studio sample is `"45分"`); `pricingType` is always `"月払"` regardless of type (008's personal sample is `有料（都次）`, so the per-use fee field is structurally unreachable in this form's edit mode); `perUseFee` state (`"550"`) exists but is never visible for that reason; `images` is a fixed 3-item sample array regardless of type (008's studio sample has 6, personal has 4). Per the spec's own Assumptions ("Sample/mock values in the prototype ... represent data shape only"), this is expected Phase-1 behavior — testers should not assume 008's sample values carry over into this screen. See test data reference below and TC-004/TC-018/TC-021/TC-041.
6. **Skeleton loading state (FR-007-P1-01) has zero mockup grounding.** No `Skeleton` import, loading state, or simulated async fetch exists anywhere in the component; edit/duplicate render their hardcoded pre-fill synchronously, identically to create. Same situation as the D02-01/D02-02 findings. See TC-071/TC-072.
7. **Duplicate-mode name pre-fill does not strictly render the `name` query param verbatim**, contradicting FR-006-P1-02/Q1's explicit "the form renders the name query parameter verbatim; no form-side suffixing." Code (`lesson-form.tsx:146`) appends "（コピー）" itself whenever the incoming `name` does not already end with that suffix: ``const initialCopyName = copyName && !copyName.endsWith("（コピー）") ? `${copyName}（コピー）` : copyName``. Under the normal navigation path (from `lesson-detail.tsx`, which already appends the suffix before navigating) this is unobservable, but a direct URL with an unsuffixed `name` produces a form-added suffix — a genuine spec/mockup conflict, not silently resolved either way. See TC-065/TC-066.
8. **The form screen itself carries no role/permission guard.** This matches the spec's stated design intent (gating lives only at the list/detail entry points per FR-009-P1-01), but it means direct URL access to `lesson-form` by any of the 6 roles renders the full, usable form with no in-screen block. Documented as intentional, but flagged since it is a direct-URL bypass of the entry-point gating tested in D02-01/D02-02. See TC-075.

**Checklist rows added** (checklist-first workflow, per standing preference): a new **"Sortable Multi-Image Gallery (Add / Delete / Drag-Reorder + Main Marker)"** section in `common-function-checklist.md` (distinct from the existing single-file-attachment and bulk-import sections) — motivated by the lesson-images section having no prior checklist coverage for multi-item drag-reorder + main-marker semantics; and a new row in `common-gui-validate-checklist.md`'s **Dialog / Confirmation Message** section (a create-mode confirmation dialog must reflect the live typed value, not a static placeholder) — motivated by Finding #1 above.
