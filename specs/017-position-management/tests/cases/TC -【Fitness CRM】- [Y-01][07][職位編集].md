# TC -【Fitness CRM】- [Y-01][07][職位編集]

**Scope**: Test Plan **Unit 3** — the position edit form (`職位 編集`) at `/positions/[id]/edit`,
reached from the list row's ⋯ menu (`編集`) and from the preview pane's `権限を編集` button. Covers
prefill completeness, the **immutable 対象ロール**, `PATCH` semantics (omitted = unchanged /
explicit `null` = clear), rename uniqueness, the unsaved-changes guard, role gating, and the
real-API behaviours of the update path.

> ⛔ **Every case in this document runs on a position this run created itself.** Editing, renaming
> or re-permissioning a pre-existing master position is forbidden (test plan → Data policy). A
> master position may be **opened** in the edit form to look at the prefill and then left via the
> discard guard **only if nothing was touched** (TC-043).

**Out of scope for this document** (per the test plan): the list/preview screen (`Unit 1`,
`[Y-01][05]`), the create/clone form (`Unit 2`, `[Y-01][06]`), all staff-account screens,
change-history writing (FR-019), role-master editing, and CSV enforcement in other features.

### Run outcome for these gaps (2026-09-17)

| ID     | Outcome at execution                                                                                                                                                                                                                                                                                                                                                                                          |
| ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **B1** | **Confirmed as expected → TC-007 `OK`.** No `ゲートストップ設定の変更` row exists anywhere in the form. **New evidence for spec Q5**: the live catalog describes `入退館設定の変更` as 「ゲートストップ設定の変更を含みます。自店舗のみ」 — the BE appears to have _folded_ Y-01 FR-006 v2 into that flag rather than dropping it. | **B3** | **CLOSED in the FE's favour — no case is `Block (B3)`.** The dev API accepts a string `description` on `PATCH`: a 500-character string returned `200` and was read back in full (TC-016), an explicit `null` cleared it (TC-021), and an omitted-vs-sent comparison was possible at all only because the string form works. The OpenAPI's `type: object` is a **BE documentation defect**, not a runtime one. |
| **G3** | **Confirmed → TC-032 `Block (G3)`,** and verified rather than assumed: the live list response carries `isSystemManaged` per record and **all 22 positions read `false`**. No system-managed record exists; none was touched.                                                                                                                                                                                  |
| **G6** | **Confirmed → TC-055 `Block (G6)`.** All nine run-created fixtures showed `割当スタッフ 「—」`, so no self-created record could carry assigned staff, and the only records that do are pre-existing master rows the data policy forbids editing.                                                                                                                                                              |
| **G5** | Applied throughout. Two 4xx/5xx results were checked against the spec's Input Validation Rules before being called: the `400 E-VAL-001` on an over-length name is the **server being right** (TC-035 records it as such), whereas the `500 E-SYS-001` on a duplicate rename is the **server being wrong** — the design requires `409 E-STF-010` there, and the create path already returns it (TC-028).       |

**Documented BE contract gap (do not file as a screen defect)**: the OpenAPI response list for
`PATCH /api/v1/admin/positions/{id}` documents `404` and `422` but **not** `400` (schema violation)
or `409` (duplicate name on rename), although FR-010 and the v0.3 design text both require the
rename uniqueness re-check. The FE must handle `E-STF-010` on update regardless — a `409` that
arrives as an unhandled generic error is an **`NG` in the FE handling**, not a contract problem.
