# TC -【Fitness CRM】- [AUTH-01][01][初回ログイン] (First-Time Login)

> Covers `specs/023-first-time-login/` User Stories 1–3 and all Edge Cases — the invitation-link
> first-time-login flow: token validation → temp-password or Google sign-in → (temp-password path
> only) forced new-password set → first-time-login completion. Driven by
> `specs/023-first-time-login/tests/test-plan.md`, Unit 1 (single unit — the whole flow, per the
> plan's split rationale).

## Source note

- **Spec**: `specs/023-first-time-login/spec.md` (read in full).
- **Requirement doc**: `crm/requirements/Y-13.md` (successor to `AUTH-01.md`) — FR-M002 (password
  policy), FR-M004 (invitation/first-time-login flow) referenced for cross-check only; not used as
  a copy source.
- **UI mockups** (all read in full): `login-initial.tsx`, `login-initial-expired.tsx`,
  `first-time-password-set.tsx`, `login-initial-success.tsx`.
- All four sources were available — no `Block — needs spec/mockup` cases in this document.
- **Spec/mockup conflict found and flagged** (see TC-021, TC-022): spec FR-005 requires a 4-rule
  password policy (length, upper+lower, number, **symbol**); the reviewed mockup
  (`first-time-password-set.tsx`) implements only 3 rules (length, upper+lower, number) with no
  symbol check at all. Written to the spec's intent per test philosophy; flagged for the real app's
  actual behavior to be confirmed at execution.
- **No test environment for Google OAuth or the real Cognito temp-password/new-password exchange**
  (per user instruction) — every case whose outcome depends on that live round-trip is marked
  `Block`-eligible in its Notes column; the CRM-side form, validation, and token-state branching
  logic around them are written as real, executable cases.

**Data limitations**: The spec/mockup describe no concrete invitation-token values or a token
delivery mechanism (real tokens are IDaaS-issued). Each token-state case (valid/expired/used/
revoked/malformed/deactivated-target/nonexistent-target) requires a way to construct or seed a
token in that state against the mock API — confirm the actual URL param name and how to fabricate
each state at execution time; note per-case if a given state cannot be reached with the current
mock data.

## Common pre-conditions

| ID   | Pre-condition                                                                                                                               |
| ---- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| PC-A | A valid, unused, unexpired first-time-login invitation link for a temp-password-path staff account (`invited@example.com`), account active. |
| PC-B | An invitation link whose token has expired.                                                                                                 |
| PC-C | An invitation link whose token was already fully consumed by a prior, completed first-time login.                                           |
| PC-D | An invitation link whose token was revoked (superseded by a newer invitation).                                                              |
| PC-E | A first-time-login URL with no token parameter, or a malformed/unparseable one.                                                             |
| PC-F | A valid, unused invitation link whose target staff account has been deactivated since issuance.                                             |
| PC-G | A valid, unused invitation link whose target staff record no longer exists.                                                                 |
| PC-H | A valid, unused, unexpired invitation link for a staff account configured for Google sign-in.                                               |
| PC-I | Having reached the New Password Set step via PC-A (i.e., temp-password authentication already succeeded).                                   |

> Mobile/phone width is out of scope. This screen has no role/permission matrix (pre-authentication)
> and no dynamic long-string display or user-echoed free text (the pre-filled email is a fixed short
> value, and password fields are masked/never redisplayed) — layout-robustness and XSS-escaping
> dimensions are therefore not applicable and are omitted rather than padded with no-op cases.
