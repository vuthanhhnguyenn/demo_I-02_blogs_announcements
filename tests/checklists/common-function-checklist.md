# Common Function Checklist

> Source: `Checklist_TCs.xlsx` — sheet `Common_Function`, translated to English.
> Purpose: a reusable base reference for writing test cases that cover generic functional behavior shared across screens/features (login, search, CRUD, bulk update, import/export, permissions, non-functional checks). Each row is a check point, not a finished test case — expand with concrete screens/data when authoring actual test cases.

| Test Item                                                          | Expected                                                           | Priority | Note |
| ------------------------------------------------------------------ | ------------------------------------------------------------------ | -------- | ---- |

## Time-Limited Single-Use Link (Invitation / Magic Link / Password-Reset Link)

> Applies to any flow entered via a token-bearing URL emailed or issued to a user, where the token
> is valid for a limited time and becomes unusable after either expiry or one successful use (e.g.
> first-time-login invitation link, magic-link sign-in, password-reset link). Distinct from a normal
> login form — here the token's own state gates whether a form is shown at all.

| Test Item                                                                                                      | Expected                                                                                                                                                                                        | Priority | Note                                                                                                                                                 |
| -------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| Check opening the link with a valid, unused, unexpired token                                                   | The intended form/action loads normally                                                                                                                                                         | High     |                                                                                                                                                      |
| Check opening the link after it has expired                                                                    | Shows the spec's "invalid or expired" state instead of the form — no form fields, no self-service retry from this same link                                                                     | High     |                                                                                                                                                      |
| Check opening the link a second time after it was already used once to complete the action                     | Shows the same "invalid or expired" state as a genuinely expired token — a used token is never distinguishable from an expired one to the end user, and never grants a second use               | High     | Core one-time-use guarantee — verify by actually completing the flow once, then reopening the identical URL                                          |
| Check opening the link with a missing or malformed token (no token param, or a token that doesn't parse/match) | Treated identically to expired/used — the same invalid-state screen, never the form                                                                                                             | High     |                                                                                                                                                      |
| Check opening the link if it was revoked/superseded (e.g. a new one was issued after this one)                 | Shows the same invalid-state screen as expired/used                                                                                                                                             | Normal   | Only applies where the spec supports issuing a replacement (e.g. re-invite)                                                                          |
| Check closing the browser mid-flow (after the token was already consumed) and reopening the same link          | Shows the invalid-state screen — a token consumed earlier in the flow does not remain valid just because the terminal step was never reached                                                    | High     | Common gap: token consumption is sometimes wired to the terminal screen instead of the actual state-changing step                                    |
| Check the invalid-state screen's recovery action (if any)                                                      | Matches the spec's stated recovery path exactly — either no self-service action (must contact an administrator) or a specific restart action (e.g. "start a new request") — never both mixed up | High     | Some flows in this codebase intentionally offer no retry (admin-issued invite); others offer a restart (self-service reset) — confirm which per spec |
| Check the token's target account no longer exists or was deactivated after the link was issued                 | Denies the action with a message distinct from the invalid/expired-link message, directing the user to contact an administrator                                                                 | High     | Distinct failure mode from token-state — the token itself may still be technically valid, but the account it points to is not                        |

## KPI / Summary Counter Cards (counts displayed above a list)

> Applies to any screen showing aggregate counters above its table (e.g. "未審査 13件", "要注意 3件").
> The counter is a second, independent computation over the same data as the table — most defects here
> are a mismatch between what the counter counts and what the requirement says it counts.

| Test Item                                                                                                                   | Expected                                                                                                                                                                                                                                          | Priority | Note                                                                                                                                                                                     |
| --------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Check the counter's population against the requirement's exact definition, including any restriction (a subset of a subset) | The count matches the spec's definition precisely — e.g. "matches within the pending queue" must exclude a matching record that is already in a decided status. Verify with a record that satisfies the inner condition but not the outer one     | High     | The classic defect: the counter is implemented as the inner condition only (all matches) and happens to agree with the spec on the current seed because no counter-example record exists |
| Check the counter against page navigation and page-size changes                                                             | The count is computed over the whole permitted data scope, not the currently visible page — it must not change when paging or changing page size                                                                                                  | High     |                                                                                                                                                                                          |
| Check whether the counter is affected by the screen's filters/search, and that this matches the spec                        | Confirm the intended coupling: a scope-level KPI must stay constant while filters narrow the table; a filter-aware KPI must move with it. Either is valid — but silently mixing them (one card scope-level, its sibling filter-aware) is a defect | High     | State the intended behaviour explicitly in the case's expected result so the tester is not left to infer it                                                                              |
| Check the counter under a restricted data scope (store/brand/role scoping)                                                  | The count reflects only the records the signed-in user is permitted to see; the same screen viewed by a wider-scoped role shows a correspondingly larger number                                                                                   | High     | A KPI computed server-side without the scope filter leaks the existence of out-of-scope records even when the table itself is correctly scoped                                           |
| Check the counter's zero state versus its non-zero state                                                                    | The zero case renders the spec's zero treatment (often a distinct colour and no alert border) and the non-zero case its alert treatment; the switch happens at exactly the boundary (0 → 1)                                                       | Normal   | See also the binary-threshold row in the GUI checklist                                                                                                                                   |
| Check the counter against the table it summarises, by applying a filter that reproduces the counter's own condition         | Filtering the table to the counter's exact condition yields a row count equal to the counter (when the counter is scope-level, compare against the unpaginated total reported by the pagination footer, not the visible rows)                     | High     | The cheapest end-to-end proof the two computations agree                                                                                                                                 |
| Check every counter the spec requires is present, and no extra counter is shown                                             | The set of cards matches the requirement exactly — a card removed by a spec revision must be gone, not merely relabelled or hidden behind a condition                                                                                             | Normal   | Prototypes commonly carry a stale card from an earlier revision                                                                                                                          |

## Aggregate Summary Panel beside a Paginated, Filtered List

> Applies to a summary card (totals, last date, method, counts) rendered next to a server-paginated table on
> the same screen and scoped by some of that table's filters — e.g. 支払いサマリー beside 入出金明細,
> ポイントサマリー beside a month-filtered history. The table shows one page; the summary must describe the
> whole filtered set, and must follow exactly the filter axes the spec names — no more, no fewer.
> Added 2026-09-24 (member-detail Unit 5).

| Test Item                                                                                         | Expected                                                                                                                                                                                                              | Priority | Note                                                                                                                                   |
| ------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| Check which filter axes move the summary — change each filter of the table in turn, one at a time | The summary follows exactly the axes the spec names (e.g. period only) and stays unchanged when any other filter changes. A summary that follows a filter the spec does not name, or ignores one it does, is a defect | High     | Where the spec and prototype disagree on the axes, write the case to the spec, flag the conflict and record `Block` until the PO rules |
| Check the summary while paging the table (page 1 → 2 → last)                                      | Every figure stays identical across pages — it aggregates the whole filtered set, not the visible rows                                                                                                                | High     | Needs a record with more than one page of rows; the page-sum bug is invisible on single-page data                                      |
| Check the summary against the rows on a single-page result, filtered to the summary's own scope   | The totals reconcile with the visible rows (sum of positive rows, sum of negative rows, their difference, the latest qualifying date)                                                                                 | High     | Cheapest end-to-end check; only valid when the whole result fits on one page                                                           |
| Check the summary's title / caption names the current scope                                       | The caption reflects the selected filter value in the same render as the figures, never the previous value                                                                                                            | High     |                                                                                                                                        |
| Check the summary for a scope with zero matching rows                                             | Every figure shows its zero or absent treatment (`¥0`, `—`) — never `NaN`, `undefined`, blank, or a value left over from the previous scope                                                                           | Medium   |                                                                                                                                        |
| Check a summary request failure while the table succeeds (and the reverse)                        | Only the failing card shows its error + retry; the other keeps its data. The summary never falls back to summing the visible page                                                                                     | Medium   |                                                                                                                                        |
