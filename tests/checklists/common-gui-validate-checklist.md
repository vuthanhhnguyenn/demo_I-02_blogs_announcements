# Common GUI & Validation Checklist

> Source: `Checklist_TCs.xlsx` — sheet `Common_GUI+Validate`, translated to English.
> Purpose: a reusable base reference for writing test cases that cover generic UI layout and field-validation behavior shared across screens. Each row is a check point, not a finished test case — expand with concrete input values/screens when authoring actual test cases.

## Default field constraints (fallback when the spec/design is silent)

Specs and mockups in this project routinely omit field limits. **When neither the spec nor the mockup states a limit, do not skip the boundary case** — apply the default below, and mark that case's Note `assumed default (…); confirm with PO/schema owner`. If the field accepts input beyond the default with **no cap and no error**, that is a **finding** (unbounded free text / numbers risk DB truncation or a 500), not a pass.

### Precedence — where a limit comes from (added 2026-09-18)

Check these in order and stop at the first that states a number. Only fall through to the table below when all three are silent.

1. **The requirement doc / feature spec** (`crm/requirements/*.md`, `specs/*/spec.md`) — a product decision, and authoritative over everything else.
2. **The API contract** (`src/lib/openapi.real.json` — `minLength` / `maxLength` / `minimum` / `maximum` / `minItems` / `maxItems` / `pattern` / `enum` on the request DTO). A numeric field with no stated maximum is still capped by its DB column (int32 = 2,147,483,647). On a real-API screen this is the limit the backend **actually enforces**: exceed it and the request is rejected, whatever the UI allowed. A contract-stated limit is a **real limit, not an assumption** — cite the DTO and field in the Note (`per UpdateStaffRequestDto.memo maxLength 1000`) and **do not** mark the case "assumed default".
3. **The UI mockup**, if it hard-codes one (e.g. a `maxLength` on an input).
4. The assumed defaults below.

**A hard `maxLength` on the input hides the validation message.** When an input carries `maxLength`, the browser silently refuses the extra characters: the user sees typing stop with no explanation, and the schema's message (「〜文字以内で入力してください」) never renders. Prefer enforcing the limit in the **schema** and letting the error show. So when testing a max-length boundary, first establish which of the two is in play:

| Implementation              | What n+1 looks like                                                                                 | How to test                                                                                                      |
| --------------------------- | --------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| Schema-enforced (preferred) | The extra characters **are** accepted into the field, and an error message appears on change/submit | Type or paste n+1, confirm the message text and that submit is blocked                                           |
| `maxLength` on the input    | Typing stops silently at n; no message                                                              | Confirm the cap by **pasting** an over-length value (paste is also truncated), and note that no message is shown |

Either can be correct, but a field that silently truncates a **pasted** value with no feedback is a finding — the user believes the whole value was entered.

Two more things to check while you are there, because they are findings in their own right:

- **The UI's limit must not be looser than the contract's.** A field that accepts more than the DTO allows lets the user type a value that will be rejected on save — or silently truncated by the backend.
- **A UI limit stricter than the contract's is not automatically wrong** (a product rule may be tighter), but it is unsourced unless the spec says so — note the divergence and who to ask.

| Field kind                                                 | Assumed default (spec silent)                                       | Boundary values (n−1 / n / n+1)                                                       |
| ---------------------------------------------------------- | ------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| Single-line text (name, title, label, short code, version) | max **255** chars; required ⇒ non-empty after trim                  | 1 char (min, ok) · 255 (at max, accepted) · 256 (over → blocked/capped/error)         |
| Multi-line text (textarea — notes, remarks, description)   | max **1000** chars                                                  | 1 · 1000 (accepted) · 1001 (over)                                                     |
| Integer input (count, display order, quantity)             | max **9 digits** (≤ 999,999,999); ≥ 1 unless spec allows 0/negative | max-digit value ok · 10 digits (over) · 0 / negative / decimal (rejected per context) |
| Money / decimal                                            | max **9 integer digits**; decimal places per spec (default 0)       | at max integer digits · one extra decimal place than allowed                          |
| Date pair (start / end)                                    | start ≤ end when both exist                                         | end = start−1 (invalid) · end = start (per spec) · end = start+1 (valid)              |

- **Full-width counting**: also reach the max using full-width/CJK characters — confirm the limit counts by character, not code unit (a full-width value at the limit must behave like a half-width one).
- **Whitespace-only** in a required field is treated as empty (trim before the required check).

## Tiered / Threshold Color-Coded Values

> Applies to any value whose display color is driven by a ratio or count against multiple threshold tiers (e.g. booked/capacity: full, ≥80% high, some, none) — distinct from a simple binary state check.

| Test Item                                                                                                                                                                                   | Expected                                                                                                                                                                                                                                                                                                                                                                         | Priority | Note                                                                                                                                                                                                                      |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Check each tier of a multi-tier, threshold-based color coding against real sample data at or near each boundary                                                                             | Every tier defined by the spec/mockup is exercised with at least one real record near its boundary (not only the extreme ends); a tier unreachable with the current sample data is a data limitation to note, not a check to silently skip                                                                                                                                       | Medium   | Distinct from a binary enabled/disabled check — multi-tier coloring commonly hides a boundary bug at the tier transition (e.g. exactly the 80% cutoff) or an entirely unreachable tier because seed data never reaches it |
| Check the same underlying record's tiered color-coded value across every place it is independently rendered (e.g. a compact/preview card and an expanded/detail list showing the same data) | The tier (and resulting color) assigned to the same ratio/count is identical in every rendering location; if two components independently compute the tier, verify they share the same thresholds — a drifted duplicate implementation is a real defect, not a design difference, unless the spec/mockup explicitly states the two views intentionally use different tier scales | High     | Two components that each reimplement the same threshold logic separately are prone to silently drifting out of sync (different boundaries, different tier count, different ordering)                                      |

| Check a **binary** threshold treatment (a value whose styling switches once, at zero versus non-zero, or at a single cutoff) at both sides of its single boundary | Both states are exercised against real data: the "safe" side renders its own treatment (colour, and the absence of any alert border/icon) and the "alert" side renders the alert treatment; the switch occurs exactly at the boundary (0 → 1), not at some other value | Normal | Simpler than the multi-tier rows above but skipped just as often — the alert state is usually visible in seed data while the zero state is never checked, so a hardcoded alert border goes unnoticed |
